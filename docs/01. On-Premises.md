
# 01. On-Premises 환경 구축

## 1. 프로젝트 목적

VMware Workstation을 활용하여 Ubuntu 24.04 기반 WEB/WAS/DB 3-Tier 인프라를 구축하고, 이후 AWS 마이그레이션을 위한 기존 운영 환경을 준비한다.

## 2. 서버 구성

| 구분 | Hostname | 초기 확인 IP | OS | 역할 |
|---|---|---|---|---|
| WEB | web01 | 192.168.111.147 | Ubuntu 24.04 | Apache HTTP Server |
| WAS | was01 | 192.168.111.148 | Ubuntu 24.04 | Spring Boot / Tomcat |
| DB | db01 | 192.168.111.149 | Ubuntu 24.04 | MySQL |

- 가상화 환경: VMware Workstation
- 네트워크 방식: NAT
- 네트워크 대역: 192.168.111.0/24
- 기본 게이트웨이: 192.168.111.2

※ IP는 최초 점검 시 확인한 값이며, 고정 IP 설정 후 최종 주소와 일치하는지 확인한다.

## 3. 네트워크 기본 점검

### 3.1 서버 이름 확인

`hostname`

현재 접속한 서버의 호스트 이름을 확인한다.

### 3.2 네트워크 인터페이스 확인

`ip -br addr`

네트워크 인터페이스의 상태와 할당된 IP 주소를 확인한다.

### 3.3 라우팅 테이블 확인

기본 게이트웨이와 로컬 네트워크의 라우팅 경로를 확인한다.

### 3.4 서버 간 통신 검증

- WEB → WAS
- WEB → DB
- WAS → DB
- 역방향 통신

검증 명령어 예시:

`ping -c 3 192.168.111.148`

- `ping -c 3 8.8.8.8`

## 4. Ubuntu 기본 보안 설정

### 4.1 패키지 업데이트

- `sudo apt update`
- `sudo apt upgrade -y`

설치된 패키지를 최신 보안 업데이트 상태로 유지한다.

### 4.2 사용자 권한 확인

- `whoami`
- `id`
- `sudo -l`

현재 사용자 및 관리자 권한을 확인한다.

### 4.3 SSH 서비스 확인

- `sudo systemctl status ssh`
- `sudo ss -tlnp`

SSH 서비스의 실행 상태와 리스닝 포트를 확인한다.

### 4.4 UFW 방화벽 기본 정책

- 기본 인바운드: Deny
- 기본 아웃바운드: Allow
- SSH: 실습용 관리 네트워크에서 TCP 22 허용

설정 예시:

- `sudo ufw default deny incoming`
- `sudo ufw default allow outgoing`
- `sudo ufw allow from 192.168.111.0/24 to any port 22 proto tcp`
- `sudo ufw enable`

설정 확인:

`sudo ufw status verbose`

SSH 접근을 허용한 후 방화벽을 활성화하여 원격 접속이 차단되지 않도록 한다.

### 4.5 리스닝 포트 확인

`sudo ss -tulpen`

실행 중인 서비스가 사용하는 TCP/UDP 포트를 확인한다.

## 5. 계층별 포트 설계

| 서버 | 포트 | 접근 대상 |
|---|---|---|
| WEB | 80/TCP | 사용자 |
| WAS | 8080/TCP | WEB |
| DB | 3306/TCP | WAS |
| 관리 | 22/TCP | 관리자 |

현재 단계에서는 SSH 기본 접근만 설정했으며, HTTP/Tomcat/MySQL 포트는 서비스 설치 시 필요한 출발지에 한해 추가 허용한다.

## 6. 학습한 핵심 개념

- NAT: 사설 네트워크에서 외부 네트워크로 통신할 수 있도록 주소를 변환하는 기술
- DHCP: IP 주소와 네트워크 정보를 자동 할당하는 기술
- Routing Table: 목적지별 패킷 전달 경로를 결정하는 정보
- SSH: 서버에 암호화된 원격 접속을 제공하는 프로토콜
- UFW: Ubuntu에서 방화벽 정책을 관리하는 도구
- Least Privilege: 필요한 사용자에게 필요한 권한만 부여하는 보안 원칙

# 02. On-Premises WEB / WAS / DB 서버 구축

## 1. 실습 목표

VMware Workstation 기반 Ubuntu 24.04 서버 3대에 Apache HTTP Server, Spring Boot 내장 Tomcat, MySQL을 구성한다.

각 서비스의 실행 상태와 네트워크 연결을 검증하고, Linux 서비스 관리 및 장애 대응 방법을 학습한다.

## 2. 서버 구성

| 구분 | Hostname | IP | 구성 |
|---|---|---|---|
| WEB | web01 | 192.168.111.147 | Apache HTTP Server |
| WAS | was01 | 192.168.111.148 | Java 21, Spring Boot, 내장 Tomcat |
| DB | db01 | 192.168.111.149 | MySQL Server |

※ IP는 실습 당시 확인한 주소를 기준으로 기록했다.

### 아키텍처

사용자 → Apache WEB01 (80) → Spring Boot WAS01 (8080) → MySQL DB01 (3306)

현재는 개별 서비스와 WAS → DB의 MySQL 클라이언트 접속을 검증했다. Apache Reverse Proxy 및 실제 애플리케이션 DB 연동은 3교시에서 검증할 예정이다.

## 3. WEB01 — Apache 구축

### 3.1 Apache 설치

`sudo apt update`

`sudo apt install apache2 -y`

Apache는 HTTP 요청을 수신하고 정적 콘텐츠를 제공하는 웹 서버다.

본 프로젝트에서는 추후 Reverse Proxy를 구성하여 Spring Boot WAS 서버에 HTTP 요청을 전달하는 역할을 수행한다.

### 3.2 실행 상태 검증

`sudo systemctl status apache2`

`sudo apache2ctl configtest`

`sudo ss -tlnp | grep ':80'`

`curl -I http://localhost`

**실습 결과**
- Apache 서비스: active (running)
- 설정 문법: Syntax OK
- TCP 80 포트: LISTEN
- HTTP 응답: 200 OK

### 3.3 주요 설정 디렉터리

| 경로 | 역할 |
|---|---|
| /etc/apache2/apache2.conf | Apache 기본 설정 |
| /etc/apache2/ports.conf | 수신 포트 설정 |
| /etc/apache2/sites-available/ | VirtualHost 설정 파일 |
| /etc/apache2/sites-enabled/ | 활성화된 VirtualHost |
| /var/www/ | 웹 콘텐츠 디렉터리 |
| /var/log/apache2/ | Apache 로그 |

### 3.4 쇼핑몰 테스트 VirtualHost

파일 경로: `/etc/apache2/sites-available/shopping.conf`

설정 예시:

```apache
<VirtualHost *:80>
    ServerName shopping.local
    DocumentRoot /var/www/shopping
    ErrorLog ${APACHE_LOG_DIR}/shopping_error.log
    CustomLog ${APACHE_LOG_DIR}/shopping_access.log combined
</VirtualHost>
```

**설정 이유**
- VirtualHost: HTTP 요청을 처리할 사이트별 규칙 지정
- ServerName: 가상 호스트 이름 지정
- DocumentRoot: 정적 파일 제공 위치 지정
- ErrorLog: 오류 분석
- CustomLog: HTTP 접근 기록

설정 활성화 및 반영:

`sudo a2ensite shopping.conf`

`sudo apache2ctl configtest`

`sudo systemctl reload apache2`

검증 명령어:

`curl -H 'Host: shopping.local' http://127.0.0.1/`

※ VirtualHost는 설정 실습을 진행했으며, 최종 응답 결과는 별도 확인이 필요하다.

### 3.5 방화벽

실습 네트워크에서 HTTP 80 포트를 허용했다.

`sudo ufw allow from 192.168.111.0/24 to any port 80 proto tcp`

## 4. WAS01 — Spring Boot 내장 Tomcat 구축

### 4.1 내장 Tomcat 선택 이유

별도 Tomcat을 설치하지 않고 Spring Boot에 포함된 Tomcat을 사용하도록 결정했다.

**장점**
- 별도 Tomcat 설치 및 관리 불필요
- JAR 단위 배포 가능
- 애플리케이션과 실행 환경을 함께 관리
- 서비스 구성 단순화

최종 쇼핑몰은 JSP에서 Thymeleaf로 변경 중이며, 해당 소스가 완성되기 전까지 기존 Marble 프로젝트로 WAS 운영 실습을 진행했다.

### 4.2 Java 설치

처음에는 Java 17을 설치했으나, Marble 애플리케이션이 Java 21로 컴파일되어 실행 오류가 발생했다.

Java 21 설치:

`sudo apt install openjdk-21-jdk -y`

버전 확인:

`java -version`

`javac -version`

### 4.3 JAR 배포

배포 디렉터리:

`/opt/marble/`

배포 파일:

`/opt/marble/app.jar`

실행 명령어:

`java -jar /opt/marble/app.jar`

### 4.4 HTTP 서비스 검증

`sudo ss -tlnp | grep ':8080'`

`curl -i http://localhost:8080/`

**실습 결과**
- Java 프로세스가 8080 포트에서 LISTEN
- HTTP 401 응답 확인
- JSESSIONID 쿠키 확인

HTTP 401은 요청에 유효한 인증 정보가 없거나 인증이 필요한 상태를 의미한다. Spring Security 설정에 의한 응답일 가능성이 있다.

HTTP 응답 확인과 실제 애플리케이션 기능 정상 동작 검증은 구분한다.

## 5. systemd 서비스 관리

### 5.1 systemd 도입 이유

터미널에서 JAR를 직접 실행하는 대신 Linux 시스템 서비스로 등록하여 관리한다.

주요 목적:
- 서버 재부팅 후 자동 시작
- 애플리케이션 비정상 종료 시 재시작
- 서비스 시작·중지·상태 확인
- journalctl 로그 확인

### 5.2 서비스 전용 계정

애플리케이션은 root가 아닌 전용 `marble` 계정으로 실행한다.

전용 계정을 사용하면 애플리케이션이 사용할 수 있는 시스템 권한을 제한할 수 있다.

### 5.3 서비스 설정

파일 경로: `/etc/systemd/system/marble.service`

```ini
[Unit]
Description=Marble Spring Boot Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=marble
Group=marble
WorkingDirectory=/opt/marble
ExecStart=/usr/bin/java -jar /opt/marble/app.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

주요 설정:
- User: 서비스 실행 사용자
- WorkingDirectory: 애플리케이션 작업 디렉터리
- ExecStart: 실행 명령어
- Restart: 비정상 종료 시 재시작
- WantedBy: 부팅 시 자동 실행 연결 대상

서비스 관리 명령어:

`sudo systemctl daemon-reload`

`sudo systemctl start marble`

`sudo systemctl enable marble`

`sudo systemctl status marble`

로그 확인:

`sudo journalctl -u marble -n 30 --no-pager`

## 7. 장애 대응 기록

### 장애 1 — Java 버전 불일치

**증상**

`UnsupportedClassVersionError`

`class file version 65.0`

`runtime only recognizes up to 61.0`

**원인**

Marble 프로젝트는 Java 21로 컴파일되었지만 WAS01은 Java 17로 실행하려고 했다.

- Java 21 클래스 버전: 65
- Java 17 클래스 버전: 61

**해결**

WAS01에 Java 21을 설치하고 실행 버전을 일치시켰다.

**배운 점**

Jenkins 빌드 환경과 운영 서버의 Java 버전 호환성을 배포 전에 검증해야 한다.

### 장애 2 — Logback 로그 파일 권한 오류

**증상**

```text
./logs/marble.log (Permission denied)
./logs/marble-error.log (Permission denied)
```

**원인**

기존 `ubuntu` 계정으로 실행하던 애플리케이션을 systemd의 `marble` 계정으로 실행하면서 로그 디렉터리의 쓰기 권한이 부족했다.

**해결**

로그 디렉터리 소유자와 접근 권한을 서비스 계정에 맞춰 조정했다.

```bash
sudo mkdir -p /opt/marble/logs
sudo chown -R marble:marble /opt/marble/logs
sudo chmod 750 /opt/marble/logs
```

서비스를 재시작하여 실행 오류를 해결했다.

**배운 점**

애플리케이션 운영 시 서비스 실행 계정과 로그 파일의 소유권 및 권한을 함께 고려해야 한다.

`chmod 777`로 전체 접근을 허용하기보다 필요한 권한만 부여해야 한다.

### 장애 3 — JDBC 연결 오류

**증상**

`CannotGetJdbcConnectionException: Failed to obtain JDBC Connection`

**상태**

Marble 애플리케이션에서 DB 연결 실패 로그가 발생했다. MySQL 클라이언트를 이용한 WAS01 → DB01 원격 접속은 성공했으나 Marble 애플리케이션의 실제 JDBC 연결은 추가 검증이 필요하다.

**점검할 항목**
- JDBC URL 및 DB 주소
- 데이터베이스 이름
- DB 사용자 및 비밀번호
- Spring Boot 프로파일과 환경변수
- 실제 예외 로그의 `Caused by` 내용

# 03. On-Premises 3-Tier 서비스 연동

## 1. 실습 목표

Ubuntu 24.04 기반 WEB/WAS/DB 서버를 연동하여 HTTP 요청이 Apache → Spring Boot → MySQL로 전달되는 3-Tier 구조를 검증한다.

**주요 학습 내용**
- Apache Reverse Proxy
- ProxyPass / ProxyPassReverse
- Spring Boot JDBC 연결
- systemd 환경변수 설정
- Apache 및 Spring Boot 로그 분석
- HTTP 기반 데이터베이스 헬스체크

이번 실습에서는 최종 쇼핑몰 애플리케이션 대신 기존 Marble Spring Boot 프로젝트를 사용하였다.

## 2. 서버 구성

| 서버 | IP 주소 | 역할 | 포트 |
|---|---|---|---|
| WEB01 | 192.168.111.147 | Apache HTTP Server | 80 |
| WAS01 | 192.168.111.148 | Spring Boot + 내장 Tomcat | 8080 |
| DB01 | 192.168.111.149 | MySQL | 3306 |

### 요청 처리 흐름

사용자 → WEB01(Apache:80) → WAS01(Spring Boot:8080) → DB01(MySQL:3306)

응답은 반대 방향으로 전달된다.

## 3. Apache Reverse Proxy 구축

### 3.1 Reverse Proxy를 사용하는 이유

Reverse Proxy는 클라이언트의 요청을 대신 받아 내부 애플리케이션 서버로 전달하는 구조다.

**도입 목적**
- WAS 주소 및 포트를 외부 접속 경로에서 분리
- Apache에서 HTTP 요청 처리 및 로그 관리
- 향후 WAS 이중화와 부하 분산을 위한 기반 마련

### 3.2 Apache 모듈 활성화

```bash
sudo a2enmod proxy proxy_http
```

- proxy: Apache 프록시 기능
- proxy_http: HTTP 프로토콜을 사용하는 프록시 기능

### 3.3 VirtualHost 설정

설정 파일:

`/etc/apache2/sites-available/shopping.conf`

```apache
<VirtualHost *:80>
    ServerName shopping.local

    ProxyPass / http://192.168.111.148:8080/
    ProxyPassReverse / http://192.168.111.148:8080/

    ErrorLog ${APACHE_LOG_DIR}/shopping_error.log
    CustomLog ${APACHE_LOG_DIR}/shopping_access.log combined
</VirtualHost>
```

**설정 설명**

| 설정 | 의미 |
|---|---|
| VirtualHost | HTTP 요청을 처리할 가상 호스트 정의 |
| ServerName | 가상 호스트 이름 |
| ProxyPass | HTTP 요청을 WAS 서버로 전달 |
| ProxyPassReverse | WAS의 일부 리다이렉트 응답 헤더를 프록시 주소에 맞게 재작성 |
| ErrorLog | Apache 오류 기록 |
| CustomLog | HTTP 접근 기록 |

### 3.4 설정 검증 및 적용

```bash
sudo apache2ctl configtest
sudo systemctl reload apache2
sudo apache2ctl -S
```

- configtest: 문법 검증
- reload: Apache 설정 반영
- apache2ctl -S: VirtualHost 설정 확인

## 4. WEB01 → WAS01 통신 검증

WAS01에서 WEB01의 HTTP 접근을 허용하였다.

```bash
sudo ufw allow from 192.168.111.147 to any port 8080 proto tcp
```

WEB01에서 직접 HTTP 요청을 전송하였다.

```bash
curl -i http://192.168.111.148:8080/
```

**실습 결과:** WEB01에서 WAS01의 HTTP 응답 확인.

애플리케이션의 인증 설정으로 HTTP 401 응답이 발생할 수 있으며, 이는 네트워크 연결 실패를 의미하지 않는다.

## 5. Spring Boot → MySQL JDBC 연결

### 5.1 발생한 문제

Spring Boot의 DB 헬스체크 호출 시 다음 응답이 발생하였다.

```json
{
  "status": "DOWN",
  "db": "DOWN"
}
```

HTTP 응답 코드: 503

오류 로그:

```text
CannotGetJdbcConnectionException
Failed to obtain JDBC Connection
```

### 5.2 문제 분석

MySQL 클라이언트에서는 DB01에 접속할 수 있었으므로 JDBC URL과 애플리케이션 실행 설정을 점검하였다.

`application.yml`의 DB 접속 설정 일부:

```yaml
spring:
  datasource:
    url: jdbc:mysql://${DB_HOST:localhost}:${DB_PORT:3306}/${DB_NAME:marble}
    username: ${DB_USERNAME:marble}
```

실제 프로젝트의 JDBC URL에는 추가 연결 옵션이 포함되어 있다.

`${DB_HOST:localhost}`는 DB_HOST 환경변수가 없으면 localhost를 기본값으로 사용한다.

WAS01에서 localhost는 WAS01 자기 자신이므로 DB01에 연결하려면 별도 DB_HOST 설정이 필요하다.

### 5.3 MySQL 클라이언트 검증

WAS01에서 MySQL 연결 테스트:

```bash
mysql -h 192.168.111.149 -P 3306 -u marble -p
```

MySQL에서 확인:

```sql
SHOW DATABASES;
SELECT USER(), CURRENT_USER();
```

**실습 결과**
- marble 데이터베이스 확인
- WAS01의 192.168.111.148 주소로 접속 확인
- marble 계정 인증 성공

### 5.4 systemd 환경변수 설정

설정 파일:

`/etc/systemd/system/marble.service`

수정 명령:

```bash
cd /etc/systemd/system
sudo nano marble.service
```

`[Service]` 항목에 다음 환경변수를 추가하였다.

```ini
[Service]
Environment="DB_HOST=192.168.111.149"
```

**설정 의미**

systemd가 Marble 애플리케이션을 실행할 때 DB_HOST 환경변수를 전달한다.

Spring Boot는 application.yml에 정의된 `${DB_HOST:localhost}`에서 전달받은 환경변수 값을 사용한다.

따라서 최종 DB 연결 주소는 다음과 같이 해석된다.

```text
jdbc:mysql://192.168.111.149:3306/marble
```

다른 DB 접속 옵션은 기존 application.yml 설정을 따른다.

### 5.5 설정 반영

```bash
sudo systemctl daemon-reload
sudo systemctl restart marble
sudo systemctl status marble
```

**명령어 설명**
- daemon-reload: 수정된 systemd 서비스 정의 다시 읽기
- restart: 변경된 환경변수로 Java 애플리케이션 재시작
- status: 서비스 실행 상태 확인

**중요:** JAR 파일을 다시 빌드하거나 배포하지 않고 실행 환경변수만 변경하여 접속 주소를 수정했다.

## 6. JDBC 연결 재검증

WAS01에서 실행:

```bash
curl -i http://localhost:8080/health/db
```

**검증 결과**
- HTTP 200
- status: UP
- db: UP

Spring Boot에서 MySQL 데이터베이스 연결을 확인하였다.

## 7. 전체 3-Tier 통합 테스트

WEB01에서 실행:

```bash
curl -i -H 'Host: shopping.local' http://127.0.0.1/health/db
```

### 요청 처리 과정

1. WEB01의 Apache가 HTTP 요청을 받는다.
2. Apache ProxyPass가 WAS01의 Spring Boot로 요청을 전달한다.
3. Spring Boot의 HealthController가 JDBC로 MySQL 연결을 확인한다.
4. MySQL 연결 결과가 Spring Boot로 반환된다.
5. Apache를 거쳐 클라이언트에 HTTP 응답을 반환한다.

**실습 결과**
- HTTP 200
- status: UP
- db: UP

Apache → Spring Boot → MySQL 전체 요청 경로의 정상 동작을 확인하였다.

## 8. 로그 검증

Apache 접근 로그:

```bash

```

```bash

```


## 9. 장애 대응 정리

### 장애 — JDBC 연결 실패

**증상**
- /health/db HTTP 503
- status DOWN, db DOWN
- CannotGetJdbcConnectionException 발생

**원인**
- Spring Boot datasource의 DB_HOST가 지정되지 않으면 localhost를 사용하도록 설정되어 있었음
- 실제 MySQL 서버는 별도의 DB01 VM에서 실행 중이었음

**조치**
- systemd marble.service에 DB_HOST=192.168.111.149 환경변수 추가
- daemon-reload 및 서비스 재시작

**검증**
- WAS01의 /health/db 정상 응답
- WEB01의 Apache Reverse Proxy를 통한 /health/db 정상 응답

**학습한 내용**

네트워크 연결이 정상이어도 애플리케이션의 JDBC 주소가 잘못되면 데이터베이스 연결 오류가 발생할 수 있다.

따라서 장애 분석 시 네트워크, DB 인증, 애플리케이션 설정을 구분하여 점검해야 한다.

## 10. 운영 및 보안 개선 사항

- DB 비밀번호를 GitHub 또는 공개 설정 파일에 포함하지 않기
- 운영 환경에서는 DB 접속 비밀번호의 기본값을 제거하고 안전한 비밀정보 관리 방식 적용
- MySQL 계정의 접속 Host를 필요한 WAS 서버로 제한
- AWS 이전 시 사설 IP 또는 내부 DNS를 사용하고 Security Group으로 접근 통제
- 실습에서 사용한 비암호화 MySQL 연결 옵션은 운영 환경의 TLS 요구사항에 맞게 재검토
- 향후 WEB/WAS 이중화 시 세션 처리 및 부하 분산 정책 추가 검증

## 4. 장애 시나리오 1 — MySQL 중단

### 4.1 장애 발생

DB01에서 실행:

```bash
sudo systemctl stop mysql
```

### 4.2 장애 확인

```bash
systemctl is-active mysql
sudo ss -tlnp | grep ':3306'
```

WEB01에서:

```bash
curl -i -H 'Host: shopping.local' \
http://127.0.0.1/health/db
```

예상 증상:

- MySQL 서비스 중단
- Spring Boot의 JDBC 연결 실패
- HTTP 503 / DB DOWN

WAS01 오류 로그 확인:

```bash
sudo tail -n 30 /opt/marble/logs/marble-error.log
```

### 4.3 복구

DB01에서:

```bash
sudo systemctl start mysql
systemctl is-active mysql
```

이후 WEB01에서 `/health/db`를 다시 호출한다.

### 4.4 학습 내용

Apache와 Spring Boot가 실행 중이어도 MySQL이 중단되면 데이터베이스 기능은 정상 동작하지 않는다.

따라서 애플리케이션 프로세스 상태와 DB 연결 상태를 구분하여 점검해야 한다.

## 5. 장애 시나리오 2 — Spring Boot 중단

### 5.1 장애 발생

WAS01에서 실행:

```bash
sudo systemctl stop marble
```

### 5.2 장애 확인

```bash
systemctl is-active marble
sudo ss -tlnp | grep ':8080'
```

WEB01에서 Apache를 통한 HTTP 요청을 수행한다.

```bash
curl -i -H 'Host: shopping.local' \
http://127.0.0.1/health/db
```

Apache 오류 로그를 확인한다.

```bash
sudo tail -n 30 /var/log/apache2/shopping_error.log
```

### 5.3 장애 분석

Spring Boot가 중단되면 Apache는 실행 중이더라도 WAS에 연결하지 못한다.

이 경우 Reverse Proxy 오류가 발생할 수 있다.

대표적인 점검 항목:

- WAS 서비스 실행 여부
- TCP 8080 LISTEN 상태
- Apache ProxyPass 대상 IP 및 포트
- Apache Error Log
- Spring Boot systemd 로그

### 5.4 복구

```bash
sudo systemctl start marble
systemctl is-active marble
```

복구 후 WEB01에서 정상 HTTP 응답을 재확인한다.

### 5.5 학습 내용

Apache에서 발생한 프록시 오류가 반드시 Apache 자체의 설정 문제를 의미하는 것은 아니다.

요청을 전달받는 WAS의 상태도 함께 확인해야 한다.

## 6. 장애 시나리오 3 — Apache 중단

### 6.1 장애 발생


### 6.2 장애 확인

```bash

```

HTTP 요청:


### 6.3 복구

```bash

sudo apache2ctl configtest
```

이후 정상 HTTP 응답을 확인한다.

### 6.4 학습 내용

현재 단일 WEB 서버 구조에서는 WEB01이 단일 장애 지점(SPOF)이다.

AWS 이전 후 ALB와 다중 WEB 서버를 통해 해당 위험을 줄일 계획이다.

## 8. AWS 마이그레이션 대상 정리

### 8.1 WEB 서버

이전 대상:

- Apache VirtualHost 설정
- Reverse Proxy 설정
- 필요한 Apache 모듈
- 접근 제어 및 로그 설정

주요 설정 파일:

`/etc/apache2/sites-available/shopping.conf`

AWS에서는 새로운 WAS Private IP 또는 내부 DNS 이름으로 ProxyPass 대상을 변경한다.

### 8.2 WAS 서버

이전 대상:

- Spring Boot 실행형 JAR
- systemd 서비스 정의
- 애플리케이션 환경별 설정
- 로그 설정

주요 파일:

- `/opt/marble/app.jar`
- `/etc/systemd/system/marble.service`

기존 systemd 환경변수:

```ini
Environment="DB_HOST=192.168.111.149"
```

AWS 이전 후에는 DB_HOST를 AWS DB 서버의 사설 주소로 변경할 예정이다.

비밀번호는 서비스 정의나 공개 저장소에 직접 기록하지 않는다.

### 8.3 DB 서버

이전 대상:

- 데이터베이스 스키마
- 테이블 데이터
- 필요한 DB 사용자 및 권한
- MySQL 버전과 설정

예정된 이전 방식:

1. 온프레미스 MySQL 데이터 백업
2. 백업 파일의 정상 생성 여부 확인
3. AWS DB01에 MySQL 설치
4. 백업 데이터 복원
5. 테이블 및 데이터 검증
6. WAS 연결 주소 변경
7. 애플리케이션 동작 확인

MySQL 백업과 복원은 실제 AWS 마이그레이션 교시에서 진행한다.

## 9. AWS 이전 시 주의할 점

- EC2의 IP 주소와 네트워크 구조가 달라진다.
- UFW 설정 외에 AWS Security Group을 설계해야 한다.
- WAS → DB 접속 주소를 변경해야 한다.
- Java 런타임 버전과 JAR의 호환성을 확인해야 한다.
- 서비스 계정의 로그 디렉터리 쓰기 권한을 확인해야 한다.
- MySQL 백업 데이터는 복원 후 실제 SQL로 검증해야 한다.
- 원본 데이터는 AWS 이전 검증이 끝날 때까지 보존한다.
- 최종 쇼핑몰의 기능 및 데이터 이전은 쇼핑몰 소스 완성 후 별도로 검증한다.

## 10. 4교시 결론

온프레미스 3-Tier 환경에서 WEB/WAS/DB 각각의 장애 발생과 서비스 복구를 실습하였다.

서비스 상태, 네트워크 포트, HTTP 응답, 애플리케이션 로그를 활용해 장애 발생 위치를 구분하는 과정을 학습하였다.

또한 AWS 이전에 필요한 설정 파일과 애플리케이션·데이터베이스 이전 대상을 정리하였다.
