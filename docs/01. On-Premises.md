
# 01. On-Premises 환경 구축

## 1. 프로젝트 목적

VMware Workstation을 활용하여 Ubuntu 24.04 기반 WEB/WAS/DB 3-Tier 인프라를 구축하고, 이후 AWS 마이그레이션을 위한 기존 운영 환경을 준비한다.

## 2. 서버 구성

| 구분 | Hostname | 초기 확인 IP | OS | 역할 |
|---|---|---|---|---|
| WEB | web01 | 192.168.111.147 | Ubuntu 24.04 | Apache HTTP Server |
| WAS | was01 | 192.168.111.148 | Ubuntu 24.04 | Spring Boot / Tomcat |
| DB | db01 | 192.168.111.149 | Ubuntu 24.04 | MySQL |

- 가상화 환경: VMware Workstation
- 네트워크 방식: NAT
- 네트워크 대역: 192.168.111.0/24
- 기본 게이트웨이: 192.168.111.2

※ IP는 최초 점검 시 확인한 값이며, 고정 IP 설정 후 최종 주소와 일치하는지 확인한다.

## 3. 네트워크 기본 점검

### 3.1 서버 이름 확인

`hostname`

현재 접속한 서버의 호스트 이름을 확인한다.

### 3.2 네트워크 인터페이스 확인

`ip -br addr`

네트워크 인터페이스의 상태와 할당된 IP 주소를 확인한다.

### 3.3 라우팅 테이블 확인

`ip route`

기본 게이트웨이와 로컬 네트워크의 라우팅 경로를 확인한다.

### 3.4 서버 간 통신 검증

- WEB → WAS
- WEB → DB
- WAS → DB
- 역방향 통신

검증 명령어 예시:

`ping -c 3 192.168.111.148`

ICMP 응답을 통해 서버 간 IP 통신 가능 여부를 확인한다.

### 3.5 인터넷 및 DNS 점검

- `ping -c 3 8.8.8.8`
- `getent hosts google.com`

외부 IP 연결과 DNS 이름 해석이 가능한지 확인한다.

## 4. Ubuntu 기본 보안 설정

### 4.1 패키지 업데이트

- `sudo apt update`
- `sudo apt upgrade -y`

설치된 패키지를 최신 보안 업데이트 상태로 유지한다.

### 4.2 사용자 권한 확인

- `whoami`
- `id`
- `sudo -l`

현재 사용자 및 관리자 권한을 확인한다.

### 4.3 SSH 서비스 확인

- `sudo systemctl status ssh`
- `sudo ss -tlnp`

SSH 서비스의 실행 상태와 리스닝 포트를 확인한다.

### 4.4 UFW 방화벽 기본 정책

- 기본 인바운드: Deny
- 기본 아웃바운드: Allow
- SSH: 실습용 관리 네트워크에서 TCP 22 허용

설정 예시:

- `sudo ufw default deny incoming`
- `sudo ufw default allow outgoing`
- `sudo ufw allow from 192.168.111.0/24 to any port 22 proto tcp`
- `sudo ufw enable`

설정 확인:

`sudo ufw status verbose`

SSH 접근을 허용한 후 방화벽을 활성화하여 원격 접속이 차단되지 않도록 한다.

### 4.5 리스닝 포트 확인

`sudo ss -tulpen`

실행 중인 서비스가 사용하는 TCP/UDP 포트를 확인한다.

## 5. 계층별 포트 설계

| 서버 | 포트 | 접근 대상 |
|---|---|---|
| WEB | 80/TCP | 사용자 |
| WAS | 8080/TCP | WEB |
| DB | 3306/TCP | WAS |
| 관리 | 22/TCP | 관리자 |

현재 단계에서는 SSH 기본 접근만 설정했으며, HTTP/Tomcat/MySQL 포트는 서비스 설치 시 필요한 출발지에 한해 추가 허용한다.

## 6. 학습한 핵심 개념

- NAT: 사설 네트워크에서 외부 네트워크로 통신할 수 있도록 주소를 변환하는 기술
- DHCP: IP 주소와 네트워크 정보를 자동 할당하는 기술
- Routing Table: 목적지별 패킷 전달 경로를 결정하는 정보
- SSH: 서버에 암호화된 원격 접속을 제공하는 프로토콜
- UFW: Ubuntu에서 방화벽 정책을 관리하는 도구
- Least Privilege: 필요한 사용자에게 필요한 권한만 부여하는 보안 원칙

# 02. On-Premises WEB / WAS / DB 서버 구축

## 1. 실습 목표

VMware Workstation 기반 Ubuntu 24.04 서버 3대에 Apache HTTP Server, Spring Boot 내장 Tomcat, MySQL을 구성한다.

각 서비스의 실행 상태와 네트워크 연결을 검증하고, Linux 서비스 관리 및 장애 대응 방법을 학습한다.

## 2. 서버 구성

| 구분 | Hostname | IP | 구성 |
|---|---|---|---|
| WEB | web01 | 192.168.111.147 | Apache HTTP Server |
| WAS | was01 | 192.168.111.148 | Java 21, Spring Boot, 내장 Tomcat |
| DB | db01 | 192.168.111.149 | MySQL Server |

※ IP는 실습 당시 확인한 주소를 기준으로 기록했다.

### 아키텍처

사용자 → Apache WEB01 (80) → Spring Boot WAS01 (8080) → MySQL DB01 (3306)

현재는 개별 서비스와 WAS → DB의 MySQL 클라이언트 접속을 검증했다. Apache Reverse Proxy 및 실제 애플리케이션 DB 연동은 3교시에서 검증할 예정이다.

## 3. WEB01 — Apache 구축

### 3.1 Apache 설치

`sudo apt update`

`sudo apt install apache2 -y`

Apache는 HTTP 요청을 수신하고 정적 콘텐츠를 제공하는 웹 서버다.

본 프로젝트에서는 추후 Reverse Proxy를 구성하여 Spring Boot WAS 서버에 HTTP 요청을 전달하는 역할을 수행한다.

### 3.2 실행 상태 검증

`sudo systemctl status apache2`

`sudo apache2ctl configtest`

`sudo ss -tlnp | grep ':80'`

`curl -I http://localhost`

**실습 결과**
- Apache 서비스: active (running)
- 설정 문법: Syntax OK
- TCP 80 포트: LISTEN
- HTTP 응답: 200 OK

### 3.3 주요 설정 디렉터리

| 경로 | 역할 |
|---|---|
| /etc/apache2/apache2.conf | Apache 기본 설정 |
| /etc/apache2/ports.conf | 수신 포트 설정 |
| /etc/apache2/sites-available/ | VirtualHost 설정 파일 |
| /etc/apache2/sites-enabled/ | 활성화된 VirtualHost |
| /var/www/ | 웹 콘텐츠 디렉터리 |
| /var/log/apache2/ | Apache 로그 |

### 3.4 쇼핑몰 테스트 VirtualHost

파일 경로: `/etc/apache2/sites-available/shopping.conf`

설정 예시:

```apache
<VirtualHost *:80>
    ServerName shopping.local
    DocumentRoot /var/www/shopping
    ErrorLog ${APACHE_LOG_DIR}/shopping_error.log
    CustomLog ${APACHE_LOG_DIR}/shopping_access.log combined
</VirtualHost>
```

**설정 이유**
- VirtualHost: HTTP 요청을 처리할 사이트별 규칙 지정
- ServerName: 가상 호스트 이름 지정
- DocumentRoot: 정적 파일 제공 위치 지정
- ErrorLog: 오류 분석
- CustomLog: HTTP 접근 기록

설정 활성화 및 반영:

`sudo a2ensite shopping.conf`

`sudo apache2ctl configtest`

`sudo systemctl reload apache2`

검증 명령어:

`curl -H 'Host: shopping.local' http://127.0.0.1/`

※ VirtualHost는 설정 실습을 진행했으며, 최종 응답 결과는 별도 확인이 필요하다.

### 3.5 방화벽

실습 네트워크에서 HTTP 80 포트를 허용했다.

`sudo ufw allow from 192.168.111.0/24 to any port 80 proto tcp`

## 4. WAS01 — Spring Boot 내장 Tomcat 구축

### 4.1 내장 Tomcat 선택 이유

별도 Tomcat을 설치하지 않고 Spring Boot에 포함된 Tomcat을 사용하도록 결정했다.

**장점**
- 별도 Tomcat 설치 및 관리 불필요
- JAR 단위 배포 가능
- 애플리케이션과 실행 환경을 함께 관리
- 서비스 구성 단순화

최종 쇼핑몰은 JSP에서 Thymeleaf로 변경 중이며, 해당 소스가 완성되기 전까지 기존 Marble 프로젝트로 WAS 운영 실습을 진행했다.

### 4.2 Java 설치

처음에는 Java 17을 설치했으나, Marble 애플리케이션이 Java 21로 컴파일되어 실행 오류가 발생했다.

Java 21 설치:

`sudo apt install openjdk-21-jdk -y`

버전 확인:

`java -version`

`javac -version`

### 4.3 JAR 배포

배포 디렉터리:

`/opt/marble/`

배포 파일:

`/opt/marble/app.jar`

실행 명령어:

`java -jar /opt/marble/app.jar`

### 4.4 HTTP 서비스 검증

`sudo ss -tlnp | grep ':8080'`

`curl -i http://localhost:8080/`

**실습 결과**
- Java 프로세스가 8080 포트에서 LISTEN
- HTTP 401 응답 확인
- JSESSIONID 쿠키 확인

HTTP 401은 요청에 유효한 인증 정보가 없거나 인증이 필요한 상태를 의미한다. Spring Security 설정에 의한 응답일 가능성이 있다.

HTTP 응답 확인과 실제 애플리케이션 기능 정상 동작 검증은 구분한다.

## 5. systemd 서비스 관리

### 5.1 systemd 도입 이유

터미널에서 JAR를 직접 실행하는 대신 Linux 시스템 서비스로 등록하여 관리한다.

주요 목적:
- 서버 재부팅 후 자동 시작
- 애플리케이션 비정상 종료 시 재시작
- 서비스 시작·중지·상태 확인
- journalctl 로그 확인

### 5.2 서비스 전용 계정

애플리케이션은 root가 아닌 전용 `marble` 계정으로 실행한다.

전용 계정을 사용하면 애플리케이션이 사용할 수 있는 시스템 권한을 제한할 수 있다.

### 5.3 서비스 설정

파일 경로: `/etc/systemd/system/marble.service`

```ini
[Unit]
Description=Marble Spring Boot Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=marble
Group=marble
WorkingDirectory=/opt/marble
ExecStart=/usr/bin/java -jar /opt/marble/app.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

주요 설정:
- User: 서비스 실행 사용자
- WorkingDirectory: 애플리케이션 작업 디렉터리
- ExecStart: 실행 명령어
- Restart: 비정상 종료 시 재시작
- WantedBy: 부팅 시 자동 실행 연결 대상

서비스 관리 명령어:

`sudo systemctl daemon-reload`

`sudo systemctl start marble`

`sudo systemctl enable marble`

`sudo systemctl status marble`

로그 확인:

`sudo journalctl -u marble -n 30 --no-pager`

기존에 준비한 SQL 파일을 사용해 데이터베이스, 테이블 및 전용 계정 구성을 진행했다.

계정의 비밀번호와 실제 인증 정보는 공개 GitHub에 저장하지 않는다.

접근을 허용할 때는 MySQL 수신 주소, UFW 방화벽, DB 계정의 Host 권한을 함께 확인해야 한다.

## 7. 장애 대응 기록

### 장애 1 — Java 버전 불일치

**증상**

`UnsupportedClassVersionError`

`class file version 65.0`

`runtime only recognizes up to 61.0`

**원인**

Marble 프로젝트는 Java 21로 컴파일되었지만 WAS01은 Java 17로 실행하려고 했다.

- Java 21 클래스 버전: 65
- Java 17 클래스 버전: 61

**해결**

WAS01에 Java 21을 설치하고 실행 버전을 일치시켰다.

**배운 점**

Jenkins 빌드 환경과 운영 서버의 Java 버전 호환성을 배포 전에 검증해야 한다.

### 장애 2 — Logback 로그 파일 권한 오류

**증상**

```text
./logs/marble.log (Permission denied)
./logs/marble-error.log (Permission denied)
```

**원인**

기존 `ubuntu` 계정으로 실행하던 애플리케이션을 systemd의 `marble` 계정으로 실행하면서 로그 디렉터리의 쓰기 권한이 부족했다.

**해결**

로그 디렉터리 소유자와 접근 권한을 서비스 계정에 맞춰 조정했다.

```bash
sudo mkdir -p /opt/marble/logs
sudo chown -R marble:marble /opt/marble/logs
sudo chmod 750 /opt/marble/logs
```

서비스를 재시작하여 실행 오류를 해결했다.

**배운 점**

애플리케이션 운영 시 서비스 실행 계정과 로그 파일의 소유권 및 권한을 함께 고려해야 한다.

`chmod 777`로 전체 접근을 허용하기보다 필요한 권한만 부여해야 한다.

### 장애 3 — JDBC 연결 오류

**증상**

`CannotGetJdbcConnectionException: Failed to obtain JDBC Connection`

**상태**

Marble 애플리케이션에서 DB 연결 실패 로그가 발생했다. MySQL 클라이언트를 이용한 WAS01 → DB01 원격 접속은 성공했으나 Marble 애플리케이션의 실제 JDBC 연결은 추가 검증이 필요하다.

**점검할 항목**
- JDBC URL 및 DB 주소
- 데이터베이스 이름
- DB 사용자 및 비밀번호
- Spring Boot 프로파일과 환경변수
- 실제 예외 로그의 `Caused by` 내용
