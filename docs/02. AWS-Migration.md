# 05. AWS VPC 및 네트워크 구축

## 1. 구축 목적

VMware On-Premises 환경에서 운영 중인 Marble 3-Tier 서비스를 AWS로 마이그레이션하기 위해 VPC와 서브넷을 구성한다.

2개 가용 영역(AZ)을 활용하여 향후 WEB/WAS 이중화 및 MySQL Primary/Replica 구성을 지원하도록 설계하였다.

## 2. VPC 구성

| 항목 | 설정 |
|---|---|
| Region | ap-northeast-2 (Seoul) |
| VPC | marble-vpc |
| CIDR | 10.0.0.0/16 |
| AZ | ap-northeast-2a, ap-northeast-2c |
| Internet Gateway | marble-igw |

### VPC 설계 이유

- 독립적인 사설 네트워크 구성
- 서버 역할에 따른 서브넷 분리
- Public/Private 네트워크의 라우팅 경로 분리
- 2개 AZ를 이용한 가용성 확보 기반 마련

## 3. Subnet 구성

| 이름 | AZ | CIDR | 용도 |
|---|---|---|---|
| marble-public-a | 2a | 10.0.1.0/24 | ALB, Bastion |
| marble-public-c | 2c | 10.0.2.0/24 | ALB |
| marble-web-a | 2a | 10.0.11.0/24 | Apache WEB01 |
| marble-web-c | 2c | 10.0.12.0/24 | Apache WEB02 |
| marble-was-a | 2a | 10.0.21.0/24 | Spring Boot WAS01 |
| marble-was-c | 2c | 10.0.22.0/24 | Spring Boot WAS02 |
| marble-db-a | 2a | 10.0.31.0/24 | MySQL Primary |
| marble-db-c | 2c | 10.0.32.0/24 | MySQL Replica |

서브넷은 Public 2개, Private 6개로 구성하였다.

각 서브넷은 서로 겹치지 않는 CIDR을 사용한다.

## 4. Internet Gateway 구성

리소스 이름: `marble-igw`

Internet Gateway를 VPC에 연결하여 인터넷 통신을 위한 경로를 준비하였다.

IGW를 생성하고 연결하는 것만으로 인터넷 연결이 완성되지는 않는다.

서브넷의 라우팅 테이블과 퍼블릭 IP, 보안 설정 등이 함께 충족되어야 한다.

## 5. Route Table 구성

### 5.1 Public Route Table

이름: `marble-rtb-public`

| Destination | Target |
|---|---|
| 10.0.0.0/16 | local |
| 0.0.0.0/0 | marble-igw |

연결 서브넷:
- marble-public-a
- marble-public-c

### 5.2 Private Route Table — AZ-A

이름: `marble-rtb-private-a`

| Destination | Target |
|---|---|
| 10.0.0.0/16 | local |

연결 서브넷:
- marble-web-a
- marble-was-a
- marble-db-a

### 5.3 Private Route Table — AZ-C

이름: `marble-rtb-private-c`

| Destination | Target |
|---|---|
| 10.0.0.0/16 | local |

연결 서브넷:
- marble-web-c
- marble-was-c
- marble-db-c

Private Subnet에는 현재 IGW 또는 NAT Gateway를 통한 기본 경로를 설정하지 않았다.

## 6. NAT Gateway 구성 계획

NAT Gateway는 EC2 구축 및 소프트웨어 설치 시점에 생성할 예정이다.

계획:
1. AZ-A Public Subnet에 NAT Gateway 생성
2. 필요한 Private Subnet에 임시 아웃바운드 경로 설정
3. Apache, Java, MySQL 패키지 설치
4. 애플리케이션과 서비스 환경 구성
5. AMI 생성 및 다른 AZ에 배포
6. NAT Gateway 삭제 또는 유지 필요성 재평가

단일 AZ NAT Gateway는 다른 AZ의 아웃바운드 통신을 지원할 수 있으나, AZ 간 데이터 전송 비용과 가용성 제약이 존재한다.

## 7. 구축 결과

- VPC 1개 생성
- Public Subnet 2개 생성
- Private Subnet 6개 생성
- Internet Gateway 생성 및 VPC 연결
- Public Route Table 1개 구성
- Private Route Table 2개 구성
- 서브넷별 라우팅 테이블 연결

현재 단계에서는 네트워크 리소스 구성을 완료하였다.

EC2 간 통신, 인터넷 접근, Security Group 및 애플리케이션 연결은 후속 교시에서 검증한다.

# 06. AWS Security Group 및 Bastion Host 구축

## 1. 구축 목적

Marble 애플리케이션의 AWS 3-Tier 인프라에 서버 역할별 접근 제어 정책을 적용하고, Private Subnet에 배치할 WEB/WAS/DB 서버를 안전하게 관리하기 위한 Bastion Host를 구성한다.

### 설계 목표

- ALB만 외부 HTTP 요청을 수신하도록 구성
- WEB, WAS, DB 간 필요한 서비스 포트만 허용
- Private EC2에 퍼블릭 IP를 할당하지 않는 구조 준비
- SSH 관리자 접근을 Bastion Host로 제한
- IP 주소보다 Security Group 참조를 활용하여 접근 정책 관리

## 2. Security Group 설계

### 2.1 애플리케이션 통신 구조

```text
Internet User
    |
    | TCP 80
    v
ALB (marble-sg-alb)
    |
    | TCP 80
    v
WEB01 / WEB02 (marble-sg-web)
    |
    | TCP 8080
    v
WAS01 / WAS02 (marble-sg-was)
    |
    | TCP 3306
    v
MySQL DB (marble-sg-db)
```

### 2.2 Security Group 정책

| Security Group | Protocol / Port | Source |
|---|---|---|
| marble-sg-alb | TCP 80 | 0.0.0.0/0 |
| marble-sg-web | TCP 80 | marble-sg-alb |
| marble-sg-web | TCP 22 | marble-sg-bastion |
| marble-sg-was | TCP 8080 | marble-sg-web |
| marble-sg-was | TCP 22 | marble-sg-bastion |
| marble-sg-db | TCP 3306 | marble-sg-was |
| marble-sg-db | TCP 22 | marble-sg-bastion |
| marble-sg-bastion | TCP 22 | 관리자 공인 IP /32 |

Security Group의 아웃바운드는 초기 구축 단계에서 기본 허용 정책을 유지하며, 추후 보안 강화 단계에서 필요한 목적지와 포트로 제한할 예정이다.

DB 간 MySQL 복제 통신(TCP 3306)은 Replica 구축 단계에서 추가한다.

## 3. Security Group과 NACL 비교

| 구분 | Security Group | NACL |
|---|---|---|
| 적용 위치 | 네트워크 인터페이스 | Subnet |
| 동작 방식 | Stateful | Stateless |
| 허용/거부 | 허용 규칙 | 허용 및 거부 규칙 |
| 응답 트래픽 | 연결 상태에 따라 자동 허용 | 별도 규칙 필요 |
| 규칙 처리 | 전체 허용 규칙 평가 | 규칙 번호순 평가 |

이번 프로젝트에서는 Security Group을 중심으로 접근을 제어한다.

NACL은 기본 구성을 유지하여 초기 구축 시 불필요한 네트워크 차단 문제를 방지한다.

## 4. Bastion Host 설계

### 4.1 구축 이유

Private Subnet의 WEB/WAS/DB 서버에 퍼블릭 IP를 부여하지 않고 관리자가 SSH를 통해 접속할 수 있는 구조를 준비하였다.

```text
Windows PC
    |
    | SSH TCP 22
    v
Bastion Host
(Public Subnet)
    |
    | SSH TCP 22
    v
Private EC2
(WEB / WAS / DB)
```

### 4.2 Bastion EC2 구성

| 항목 | 설정 |
|---|---|
| Instance Name | marble-bastion |
| OS | Ubuntu Server 24.04 LTS |
| Instance Type | t3.micro |
| VPC | marble-vpc |
| Subnet | marble-public-a |
| Private IPv4 | 10.0.1.172 |
| Public IPv4 | 할당 |
| Security Group | marble-sg-bastion |
| Storage | 8 GiB gp3 |
| SSH User | ubuntu |
| Key Pair | marble-key |

### 4.3 SSH 접근 통제

Bastion의 SSH 인바운드는 관리자 공인 IP/32만 허용하도록 구성하였다.

Private 서버의 SSH 인바운드는 marble-sg-bastion 보안 그룹에서 시작하는 연결만 허용하도록 준비하였다.

## 5. Bastion 접속 검증

Windows PowerShell에서 SSH 접속을 진행하였다.

```powershell
ssh -i .\marble-key.pem ubuntu@<BASTION_PUBLIC_IP>
```

접속 후 사용자 계정을 확인하였다.

```bash
whoami
```

실제 확인 결과:

```text
ubuntu@ip-10-0-1-172:~$ whoami
ubuntu
```

### 검증 결과

**성공: Windows PC → Bastion EC2 SSH 접속**

이를 통해 다음 구간이 정상적으로 동작함을 확인하였다.

- Public Subnet의 인터넷 접근 경로
- Bastion 퍼블릭 IP를 통한 SSH 접근
- Bastion Security Group의 인바운드 정책
- SSH 키 인증 및 Ubuntu 사용자 로그인

단, Bastion → Private EC2 접속은 Private 서버 구축 후 별도로 검증할 예정이다.

## 6. 기술 선택 이유

### Bastion Host

외부에서 Private EC2로 직접 SSH 접속하지 않도록 관리자 접속 경로를 분리하기 위해 선택하였다.

### Security Group 참조

ALB, WEB, WAS, DB의 IP 변경에 따라 보안 정책을 매번 수정하지 않도록 서버 역할별 Security Group을 참조하는 방식으로 구성하였다.

### Private Subnet

WEB/WAS/DB 서버에 직접적인 인터넷 인바운드 경로를 제공하지 않도록 설계하였다.

### SSH ProxyJump 계획

SSH 개인키를 Bastion 서버에 저장하지 않고 관리자 PC에서 Bastion을 경유하여 Private EC2에 접속할 예정이다.

## 7. 향후 개선 사항

- HTTPS 443 및 TLS 인증서 구성
- Security Group 아웃바운드 최소 권한 정책
- MySQL Primary/Replica 복제 전용 접근 규칙
- SSH 접속 로그 및 관리자 접근 기록 관리
- AWS Systems Manager Session Manager 대안 검토
- Bastion 단일 AZ 장애 대응 방안 검토

# 07. VMware → AWS EC2 마이그레이션 및 3-Tier 구축

## 1. 프로젝트 목적

기존 VMware On-Premises 환경에서 실행하던 Marble 서비스를 AWS EC2 기반 3-Tier 아키텍처로 이전한다.

WEB, WAS, DB를 각각 별도의 Private Subnet에 배치하고 Bastion Host를 통해 관리하도록 구성한다.

### 구축 목표

- AWS EC2 기반 WEB/WAS/DB 서버 구축
- VMware의 Marble Spring Boot JAR 이전
- 기존 SQL 파일을 활용한 MySQL 데이터 구성
- Apache Reverse Proxy 구현
- WEB → WAS → DB 서비스 연결 검증
- NAT Gateway를 통한 임시 인터넷 아웃바운드 및 비용 정리

## 2. AWS 서버 구성

| 구분 | 인스턴스 | Private IP | 역할 |
|---|---|---|---|
| Bastion | marble-bastion | 10.0.1.172 | 관리자 SSH 중계 |
| WEB01 | marble-web01 | 10.0.11.28 | Apache Reverse Proxy |
| WAS01 | marble-was01 | 10.0.21.126 | Java 21 / Spring Boot |
| DB01 | marble-db01 | 10.0.31.x | MySQL |

### 네트워크 구성

- VPC: `marble-vpc` (`10.0.0.0/16`)
- AZ: `ap-northeast-2a`
- Bastion: `marble-public-a`
- WEB01: `marble-web-a`
- WAS01: `marble-was-a`
- DB01: `marble-db-a`

WEB/WAS/DB에는 퍼블릭 IP를 할당하지 않았다.

## 3. Bastion 경유 SSH 접속

Windows 환경의 MobaXterm을 사용하여 Bastion Host를 경유해 Private EC2에 접속하였다.

접속 과정에서 확인한 내용:

- Private EC2에는 퍼블릭 IP가 없음
- Bastion과 Private EC2는 VPC 내부 경로로 통신
- EC2의 SSH 인바운드는 Bastion Security Group에서 오는 연결만 허용

WEB01에서 확인한 결과:

```bash
whoami
# ubuntu

hostname
# ip-10-0-11-28

ip -br addr
# ens5 UP 10.0.11.28/24
```

EC2 내부에서는 DHCP로 전달받은 기본 게이트웨이가 표시되지만, 실제 인터넷 방향의 네트워크 경로는 AWS VPC Route Table에서 제어된다.

## 4. NAT Gateway 임시 구성

Private EC2의 패키지 설치를 위해 AZ-A의 Public Subnet에 NAT Gateway를 생성하였다.

### 구성

- NAT Gateway: `marble-nat-a`
- 유형: Public / Zonal
- Subnet: `marble-public-a`
- Route Table: `marble-rtb-private-a`

실습 중 기본 경로:

```text
10.0.0.0/16 → local
0.0.0.0/0   → NAT Gateway
```

### 활용

- Ubuntu 패키지 저장소 접근
- Apache 설치
- Java 21 설치
- MySQL 설치
- 네트워크 및 패키지 다운로드 검증

기본 설치와 통신 검증을 마친 뒤 NAT 기본 경로를 제거하고 NAT Gateway를 삭제하였다.

NAT용 Elastic IP도 반환하여 불필요한 과금을 방지하였다.

삭제 후에도 VPC 내부의 `local` 라우팅으로 WEB → WAS → DB 통신을 유지하도록 설계하였다.

## 5. WEB01 — Apache 구축

Ubuntu 24.04에서 Apache를 설치하였다.

```bash
sudo apt install -y apache2
sudo systemctl enable --now apache2
```

서비스 검증:

```bash
sudo systemctl status apache2
sudo ss -lntp | grep ':80'
curl -I http://127.0.0.1
```

### Reverse Proxy 설정

설정 파일:

`/etc/apache2/sites-available/marble.conf`

```apache
<VirtualHost *:80>
    ServerName marble.test

    ProxyRequests Off
    ProxyPreserveHost On

    ProxyPass / http://10.0.21.126:8080/
    ProxyPassReverse / http://10.0.21.126:8080/

    ErrorLog ${APACHE_LOG_DIR}/marble_error.log
    CustomLog ${APACHE_LOG_DIR}/marble_access.log combined
</VirtualHost>
```

설정 활성화:

```bash
sudo a2enmod proxy proxy_http
sudo a2ensite marble.conf
sudo a2dissite 000-default.conf
sudo apache2ctl configtest
sudo systemctl reload apache2
```

### 기술 선택 이유

Apache의 Reverse Proxy를 이용해 외부 HTTP 처리 계층과 Spring Boot 애플리케이션 실행 계층을 분리하였다.

향후 WAS02 추가 시 Apache 로드밸런싱 기능을 적용할 예정이다.

## 6. WAS01 — Spring Boot Marble 이전

### Java 21 설치

```bash
sudo apt install -y openjdk-21-jre-headless
java -version
```

기존 Marble 애플리케이션은 Java 21로 빌드되어 동일한 실행 환경을 구성하였다.

### 애플리케이션 파일 이전

VMware WAS01의 `/opt/marble/app.jar`을 MobaXterm을 통해 AWS WAS01로 전송하였다.

AWS 배포 경로:

```text
/opt/marble/
├── app.jar
└── logs/
```

파일 및 디렉터리는 `marble` 전용 계정이 소유하도록 설정하였다.

JAR 파일은 Java 프로세스가 읽어서 실행하므로 별도의 실행 권한 없이 읽기 권한을 부여하였다.

### systemd 등록

파일:

`/etc/systemd/system/marble.service`

```ini
[Unit]
Description=Marble Spring Boot Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=marble
Group=marble
WorkingDirectory=/opt/marble
EnvironmentFile=/etc/marble/marble.env
ExecStart=/usr/bin/java -jar /opt/marble/app.jar
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

### 환경변수 관리

MySQL 연결 정보는 `/etc/marble/marble.env`에 분리하여 저장하였다.

해당 파일에는 DB 접속 주소 및 인증 정보가 포함되므로 GitHub에 업로드하지 않는다.

### 서비스 실행 및 검증

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now marble
sudo systemctl status marble
sudo ss -lntp | grep ':8080'
```

헬스체크:

```bash
curl -i http://127.0.0.1:8080/health/db
```

DB 연결 상태가 정상임을 확인하였다.

## 7. DB01 — MySQL 구축 및 데이터 구성

Ubuntu 24.04에서 MySQL 서버를 설치하였다.

```bash
sudo apt install -y mysql-server
sudo systemctl enable --now mysql
```

MySQL 설정 파일:

`/etc/mysql/mysql.conf.d/mysqld.cnf`

`bind-address`를 DB01의 실제 사설 IP로 설정하여 VPC 내부 서버의 원격 접속을 허용하였다.

### 데이터 구성 방식

기존에 준비한 SQL 파일을 실행하여 AWS DB01에 다음 내용을 구성하였다.

- `marble` 데이터베이스
- 애플리케이션에 필요한 테이블
- SQL 파일에 포함된 실제 데이터
- 애플리케이션용 MySQL 계정

이번 작업은 SQL 파일을 이용한 데이터 적재 방식으로 진행하였다.

### WAS → DB 접속 검증

### Apache Reverse Proxy

### systemd

Spring Boot의 자동 시작, 프로세스 관리, 비정상 종료 시 재시작을 위해 사용하였다.

### 환경변수 파일

# 08. AWS Multi-AZ 이중화 및 ALB 구축

## 1. 프로젝트 개요

### 목표

기존 AWS 단일 가용 영역(AZ-A)의 WEB/WAS 서버를 AMI로 복제하여 AZ-C에도 배치하고, Application Load Balancer(ALB)를 사용해 외부 요청을 분산한다.

또한 로드밸런싱 이후 발생한 회원가입 403 오류를 분석하고, WEB 서버 장애 발생 시 서비스 유지 여부를 검증한다.

### 주요 학습 내용

- Amazon Machine Image(AMI)를 이용한 EC2 복제
- 서로 다른 가용 영역에 WEB/WAS 서버 배치
- 동일 VPC 내부의 AZ 간 통신
- ALB 및 Target Group 구성
- Health Check를 통한 대상 서버 상태 확인
- Sticky Session을 이용한 세션 불일치 완화
- WEB 서버 장애 발생 및 복구 테스트

## 2. 시스템 아키텍처

```text
                 Internet
                    |
                    v
             Application LB
               marble-alb
                    |
              marble-tg-web
                    |
          +---------+---------+
          |                   |
        AZ-A                AZ-C
          |                   |
        WEB01               WEB02
        Apache              Apache
          |                   |
        WAS01               WAS02
      Spring Boot         Spring Boot
          |                   |
          +---------+---------+
                    |
                  DB01
                  MySQL
                  AZ-A
```

### 네트워크 구성

| 구분 | AZ-A | AZ-C |
|---|---|---|
| Availability Zone | ap-northeast-2a | ap-northeast-2c |
| Public Subnet | marble-public-a | marble-public-c |
| WEB Subnet | marble-web-a | marble-web-c |
| WAS Subnet | marble-was-a | marble-was-c |
| WEB EC2 | marble-web01 | marble-web02 |
| WAS EC2 | marble-was01 | marble-was02 |

- VPC: `marble-vpc`
- VPC CIDR: `10.0.0.0/16`
- ALB: 인터넷 연결형, Public Subnet A/C 사용
- WEB/WAS/DB: Private Subnet 배치
- DB01: AZ-A의 단일 MySQL 서버

ALB는 Public Subnet에 배치하지만 WEB 서버는 Private Subnet에 유지하여 외부에서 WEB EC2로 직접 접근하지 않도록 구성했다.

## 3. AMI 기반 EC2 복제

### WEB 서버 복제

기존 `marble-web01`에서 다음 AMI를 생성했다.

- AMI 이름: `marble-web-ami-v1`
- 포함 환경: Ubuntu 24.04, Apache, Reverse Proxy 설정
- 새 인스턴스: `marble-web02`
- 배치 위치: `marble-web-c` (AZ-C)
- 보안 그룹: `marble-sg-web`

### WAS 서버 복제

기존 `marble-was01`에서 다음 AMI를 생성했다.

- AMI 이름: `marble-was-ami-v1`
- 포함 환경: Java 21, Spring Boot JAR, systemd 서비스
- 새 인스턴스: `marble-was02`
- 배치 위치: `marble-was-c` (AZ-C)
- 보안 그룹: `marble-sg-was`

AMI는 운영체제와 디스크에 저장된 애플리케이션 및 설정을 복제하지만, 새 EC2의 서브넷, 사설 IP, 보안 그룹 등은 인스턴스 생성 시 별도로 지정해야 한다.

**보안 주의사항:** 이번 실습에서 생성한 WAS AMI에는 기존 DB 접속 인증 정보가 포함됐을 가능성이 있다. AMI를 비공개로 유지하고, 인증 정보 교체 및 불필요한 AMI/스냅샷 삭제가 필요하다.

## 4. WEB02와 WAS02 연결

AMI로 복제한 WEB02는 처음에 WEB01의 설정을 그대로 사용하여 WAS01로 요청을 전달했다.

WEB02의 Apache 설정을 변경하여 WAS02로 요청을 전달하도록 구성했다.

설정 파일:

`/etc/apache2/sites-available/marble.conf`

핵심 설정:

```apache

ProxyPreserveHost On

ProxyPass / http://<WAS02_PRIVATE_IP>:8080/
ProxyPassReverse / http://<WAS02_PRIVATE_IP>:8080/
```

설정 검사 및 적용:

```bash
sudo apache2ctl configtest
sudo systemctl reload apache2
```

통신 확인:

```bash
curl -i -H 'Host: marble.test' \

```

검증 결과:

- Apache 설정 문법 정상
- WEB02 → WAS02 연결 정상
- WAS02 → DB01 연결 정상

- 응답: `{"status":"UP","db":"UP"}`

## 6. 장애 사례 — 회원가입 403 Forbidden

### 장애 현상

ALB를 통해 회원가입을 시도하는 과정에서 간헐적으로 다음 오류가 발생했다.

```text
Whitelabel Error Page

There was an unexpected error
(type=Forbidden, status=403).
```

한 번 실패한 뒤 다시 성공하거나, 새로운 시크릿 브라우저 창에서 재시도 시 다시 실패하는 등 간헐적인 양상이 나타났다.

### 장애 범위 축소

| 테스트 환경 | 결과 |
|---|---|
| WEB01 → WAS01 단독 | 회원가입 정상 |
| WEB02 → WAS02 단독 | 회원가입 정상 |
| WEB01/02 동시 운영 | 간헐적 HTTP 403 |
| Sticky Session 활성화 | 회원가입 정상 |

### 원인 가설

Spring Security에서 세션 기반 CSRF 보호를 사용하는 경우, 회원가입 화면을 처리한 WAS와 회원가입 POST를 처리한 WAS가 다르면 세션에 저장된 CSRF 토큰이 일치하지 않을 수 있다.

현재 두 WAS가 독립적인 세션을 유지하는 구조이므로, 서버 간 세션 불일치가 가장 유력한 원인으로 판단했다.

단, Spring Security 로그에서 CSRF 예외를 직접 확인한 것은 아니므로 확정 원인이 아닌 **검증 결과에 근거한 가설**로 기록한다.

### 적용한 완화 조치

AWS Target Group의 Sticky Session 기능을 활성화했다.

| 설정 | 값 |
|---|---|
| Target Group | marble-tg-web |
| Stickiness | Enabled |
| Type | Load balancer generated cookie |
| Duration | 1 hour |

Sticky Session은 브라우저별 요청을 같은 WEB 대상에 유지하도록 한다.

현재 WEB01 → WAS01, WEB02 → WAS02로 연결되어 있으므로 사용자 요청이 동일 WAS로 전달되는 효과가 있다.

### 결과 및 한계

- Sticky Session 활성화 후 회원가입 정상 확인
- 서버 간 요청 이동에 따른 세션 불일치 가능성 완화
- Sticky Session만으로 세션 자체가 공유되는 것은 아님
- 장애 전환 시 기존 세션이 유지된다고 보장할 수 없음

향후 개선안으로 Spring Session과 Redis/JDBC 기반의 공용 세션 저장소 구성을 검토할 수 있다.

## 9. 현재 구성의 한계 및 개선 계획

### 1. DB 단일 장애 지점

WEB과 WAS는 두 가용 영역에 배치했지만 DB01은 AZ-A에 단독으로 존재한다.

따라서 DB01 장애 발생 시 전체 애플리케이션이 영향을 받을 수 있다.

향후 MySQL Primary/Replica 복제를 구성하고 수동 장애 전환을 검증할 예정이다.

### 2. WAS 세션 공유 미구현

현재 Sticky Session으로 회원가입 문제를 완화했지만, WAS 장애 후 세션 유지까지 보장하지는 못한다.

세션 공유 또는 애플리케이션의 무상태화가 개선 과제다.

### 3. Apache WAS 로드밸런싱 미구현

현재는 WEB01 → WAS01, WEB02 → WAS02가 각각 고정되어 있다.

향후 Apache `mod_proxy_balancer`를 이용하여 두 WAS에 요청을 분산하도록 개선할 예정이다.

### 4. 인증 정보 관리

WAS AMI에 DB 접속 정보가 포함됐을 가능성이 있으므로 DB 비밀번호 변경, 환경 설정 갱신, 불필요한 AMI 및 관련 EBS 스냅샷 정리가 필요하다.

### 5. HTTPS 미구현

현재 ALB는 HTTP 80을 사용한다.

실제 서비스에서는 TLS 인증서와 HTTPS 리스너를 이용한 암호화 통신이 필요하다.

## 10. 배운 점

1. AMI로 서버 운영체제와 설치 환경을 재사용할 수 있지만, 새 EC2의 네트워크 배치는 별도로 결정한다.
2. 같은 VPC에 있다면 가용 영역이 달라도 사설 IP 통신이 가능하다.
3. ALB를 사용하면 다수 WEB 서버의 상태를 확인하고 정상 대상으로 요청을 전달할 수 있다.
4. 다중 서버 전환 후에는 단일 서버에서 나타나지 않던 세션 및 인증 문제가 발생할 수 있다.
5. 장애 분석은 서버별 단독 테스트처럼 범위를 단계적으로 좁히는 것이 효과적이다.
6. Sticky Session은 세션 불일치 문제를 완화하지만 세션 공유의 완전한 대체재는 아니다.
7. 고가용성은 단순히 서버 수를 늘리는 것으로 완성되지 않으며, DB·세션·보안·장애 복구까지 함께 검토해야 한다.

### 목표

단순히 서비스가 정상 실행되는 것에서 나아가, 실제 운영 환경을 고려하여 **허용된 통신은 정상적으로 이루어지고, 불필요한 접근은 차단되는지** 확인한다.

### 주요 학습 내용

- VMware와 AWS MySQL 데이터 비교
- 3-Tier 네트워크 통신 및 접근 제어 검증
- AWS Security Group의 최소 권한 원칙
- Public/Private Subnet 라우팅 점검
- Spring Boot 환경변수 파일 권한 관리
- MySQL 계정 비밀번호 교체 및 AMI 보안
- systemd 기반 애플리케이션 운영 및 복구 검증

## 2. AWS 시스템 아키텍처

```text
                         Internet
                            |
                            v
                    marble-alb
                Public Subnet A/C
                            |
                    marble-tg-web
                            |
              +-------------+-------------+
              |                           |
            AZ-A                        AZ-C
              |                           |
            WEB01                       WEB02
            Apache                      Apache
              |                           |
            WAS01                       WAS02
          Spring Boot                 Spring Boot
              |                           |
              +-------------+-------------+
                            |
                          DB01
                          MySQL
                          AZ-A
```

### 인프라 구성

| 구분 | 설정 |
|---|---|
| Region | ap-northeast-2 (Seoul) |
| VPC | marble-vpc |
| VPC CIDR | 10.0.0.0/16 |
| Availability Zones | ap-northeast-2a, ap-northeast-2c |
| ALB | marble-alb |
| Target Group | marble-tg-web |
| WEB | Apache 2.4 |
| WAS | Java 21, Spring Boot |
| DB | MySQL |
| 관리 서버 | Bastion Host |

WEB/WAS/DB 인스턴스는 Private Subnet에 배치하고, 외부 요청은 Public Subnet의 ALB를 통해 전달하도록 구성했다.

## 3. VMware ↔ AWS 데이터 정합성 검증

### 검증 목적

AWS로 데이터베이스를 이전한 이후 애플리케이션에서 DB 연결이 성공하더라도 실제 데이터가 누락되었을 가능성은 남아 있다.

따라서 기존 VMware DB와 AWS DB의 데이터를 비교하여 마이그레이션 결과를 점검했다.

### 비교 대상

| 구분 | 기존 환경 | 이전 환경 |
|---|---|---|
| 플랫폼 | VMware | AWS EC2 |
| 서버 | DB01 | marble-db01 |
| DBMS | MySQL | MySQL |
| Database | marble | marble |

### 검증 명령어

각 DB 서버에서 다음 명령어를 사용하여 데이터베이스와 테이블을 확인했다.

```bash
sudo mysql
```

```sql
SHOW DATABASES;

USE marble;

SHOW TABLES;
```

필요한 경우 테이블별 행 개수를 비교할 수 있다.

```sql
SELECT COUNT(*) FROM 테이블명;
```

### 검증 결과

**사용자 확인 결과: VMware와 AWS의 데이터 일치**

기존 데이터가 AWS 환경에 존재하는 것을 확인했다.

다만 정확한 테이블별 건수, 체크섬, 비교 시점의 스냅샷 결과는 별도로 기록되지 않았다. 따라서 데이터 정합성에 대한 엄밀한 증빙을 남기려면 테이블별 행 개수와 주요 데이터의 해시 비교 등을 추가로 수행할 필요가 있다.

또한 AWS에서 회원가입 테스트를 진행하면서 생성된 신규 데이터는 VMware의 이전 시점 데이터와 구분해야 한다.

## 4. 네트워크 접근 제어 검증

### 4.1 검증 목적

3-Tier 환경에서는 각 계층이 필요한 서비스에만 접근하도록 제한해야 한다.

현재 Marble 프로젝트의 통신 정책은 다음과 같다.

| Source | Destination | Port | 정책 |
|---|---|---|---|
| Internet | ALB | TCP 80 | 허용 |
| ALB SG | WEB SG | TCP 80 | 허용 |
| WEB SG | WAS SG | TCP 8080 | 허용 |
| WAS SG | DB SG | TCP 3306 | 허용 |
| Bastion SG | EC2 서버 SG | TCP 22 | 허용 |
| WEB SG | DB SG | TCP 3306 | 차단 |

### 4.2 WEB02 → DB01 직접 접근 테스트

WEB02에서 다음 명령어를 실행했다.

```bash
nc -vz -w 3 <DB01_PRIVATE_IP> 3306
```

테스트 결과:

```text
Connection timed out
```

**검증 결과: WEB02에서 DB01의 TCP 3306 포트로 직접 연결할 수 없음을 확인했다.**

이는 WEB 계층의 불필요한 DB 접근이 차단된다는 의도와 일치한다.

단, `Connection timed out`만으로 특정 보안 그룹 규칙이 유일한 차단 원인이라고 단정할 수는 없다. 따라서 AWS 보안 그룹 설정도 함께 확인했다.

### 4.3 WAS02 → DB01 정상 접근 검증

WAS02에서 Spring Boot의 DB 헬스체크를 실행했다.

```bash
curl -i http://127.0.0.1:8080/health/db
```

검증 결과:

```text
HTTP/1.1 200

{"status":"UP","db":"UP"}
```

**검증 결과: WAS02의 애플리케이션에서 DB01 연결 성공**

WEB의 DB 직접 접근은 차단하면서, WAS의 DB 접근은 허용하는 계층별 접근 정책을 확인했다.

## 5. Security Group 검증

### 5.1 DB 보안 그룹

보안 그룹 이름:

`marble-sg-db`

확인된 인바운드 규칙:

| Type | Protocol | Port | Source |
|---|---|---|---|
| SSH | TCP | 22 | marble-sg-bastion |
| MySQL/Aurora | TCP | 3306 | marble-sg-was |

검증 결과:

- DB 관리용 SSH는 Bastion 보안 그룹에만 허용
- MySQL 연결은 WAS 보안 그룹에만 허용
- WEB 보안 그룹의 직접 DB 접근은 허용하지 않음
- 전체 인터넷 또는 VPC 대역에 대한 광범위한 DB 접근 규칙 없음

### 5.2 Security Group 참조 방식

AWS Security Group은 특정 IP뿐 아니라 다른 Security Group을 통신 허용 대상으로 지정할 수 있다.

예를 들어 DB의 3306 포트에서 `marble-sg-was`를 허용하면 해당 보안 그룹을 사용하는 WAS01과 WAS02에 공통으로 정책을 적용할 수 있다.

이를 통해 인스턴스의 사설 IP가 변경되어도 보안 정책을 일관되게 관리할 수 있다.

### 5.3 보안 설계 원칙

**최소 권한 원칙(Least Privilege)**

서비스 운영에 필요한 접근만 허용하고 불필요한 네트워크 경로는 제한한다.

계층별 네트워크 분리를 적용하면 한 서버가 침해되었을 때 다른 계층으로의 직접적인 접근 가능성을 줄일 수 있다.

## 6. VPC 라우팅 테이블 검증

### 6.1 Public Subnet

Public 라우팅 테이블에서 다음 경로를 확인했다.

| Destination | Target |
|---|---|
| 10.0.0.0/16 | local |
| 0.0.0.0/0 | Internet Gateway |

Public Subnet:

- marble-public-a
- marble-public-c

Internet-facing ALB와 Bastion은 Public Subnet을 사용한다.

### 6.2 Private Subnet

Private 라우팅 테이블에서는 VPC 내부 통신을 위한 Local 경로를 확인했다.

| Destination | Target |
|---|---|
| 10.0.0.0/16 | local |

Private Subnet에 배치된 WEB/WAS/DB 인스턴스는 공인 IP 없이 운영한다.

기존 임시 NAT Gateway는 패키지 설치 이후 삭제했다.

### 6.3 서로 다른 AZ 간 통신

AWS VPC의 Local 라우팅을 통해 AZ-A와 AZ-C의 서버 간 사설 IP 통신이 가능하다.

```text
WEB02 (AZ-C)
      |
      v
WAS02 (AZ-C)
      |
      v
DB01 (AZ-A)
```

검증 결과:

- WEB02 → WAS02 정상
- WAS02 → DB01 정상
- NAT Gateway 없이 VPC 내부 통신 가능

## 7. WAS 환경변수 파일 보안 점검

### 7.1 환경변수 파일

현재 Spring Boot는 DB 접속 정보를 다음 파일에서 읽는다.

```text
/etc/marble/marble.env
```

해당 파일에는 DB 서버 주소와 계정 및 비밀번호가 포함되어 있다.

파일 내용을 GitHub에 업로드하거나 터미널 출력으로 공개하지 않도록 주의한다.

### 7.2 접근 권한 확인

WAS01과 WAS02에서 다음 명령어를 실행했다.

```bash
sudo stat -c '%a %U:%G %n' /etc/marble

sudo stat -c '%a %U:%G %n' /etc/marble/marble.env
```

확인된 결과:

```text
700 root:root /etc/marble

600 root:root /etc/marble/marble.env
```

권한 의미:

| 권한 | 의미 |
|---|---|
| 700 | 디렉터리 소유자만 접근 |
| 600 | 파일 소유자만 읽기·쓰기 |

이를 통해 일반 사용자가 DB 접속 정보에 직접 접근하는 것을 제한한다.

단, 파일 권한이 제한되어 있어도 해당 파일이 저장된 EBS 스냅샷을 복원할 권한이 있다면 내용에 접근할 수 있으므로 이미지 보안은 별도로 관리해야 한다.

## 8. DB 인증 정보 교체 및 AMI 보안

### 8.1 보안 위험

8교시에서는 WAS01을 AMI로 복제하여 WAS02를 생성했다.

사용한 AMI:

`marble-was-ami-v1`

기존 WAS01의 디스크에 DB 접속 비밀번호가 저장되어 있었으므로 AMI와 관련 EBS 스냅샷에 기존 인증 정보가 포함될 수 있었다.

### 8.2 비밀번호 교체 절차

다음 절차로 인증 정보를 교체하도록 구성했다.

1. 새 DB 비밀번호 준비
2. WAS01/WAS02의 `marble.env` 수정
3. WAS01/WAS02 Spring Boot 서비스 중지
4. DB01 MySQL 계정 비밀번호 변경
5. 두 WAS 서비스 재시작
6. `/health/db` 및 ALB Target 상태 검증

MySQL 계정 확인:

```sql
SELECT user, host
FROM mysql.user
WHERE user = 'marble';
```

실제 비밀번호 변경 시에는 조회된 정확한 `user`와 `host` 조합을 사용해야 한다.

DB 계정 비밀번호를 교체한 뒤 WAS01/WAS02 모두 새 비밀번호로 연결되는지 검증해야 한다.

**주의:** 비밀번호 변경 결과와 변경 전후의 인증 성공 증빙은 별도로 보관하지 않았으므로 최종 점검 시 두 WAS의 DB 연결 상태를 재확인한다.

### 8.3 기존 WAS AMI 정리

보안상 필요하지 않은 기존 이미지와 스냅샷은 다음과 같이 정리하도록 계획했다.

| 리소스 | 처리 |
|---|---|
| marble-was-ami-v1 | 등록 해제 |
| 관련 EBS 스냅샷 | 삭제 |
| marble-web-ami-v1 | 유지 |
| WAS01/WAS02 EC2 | 유지 |

AMI 등록 해제와 EBS 스냅샷 삭제는 별개 작업이며, 관련 스냅샷이 남아 있다면 디스크 데이터와 저장 비용이 계속 유지될 수 있다.

정리 작업 진행 후에는 AWS 콘솔에서 대상 AMI와 연결 스냅샷이 실제로 없어졌는지 최종 확인해야 한다.

### 8.4 향후 개선 방안

운영 환경에서는 DB 인증 정보를 서버 이미지에 포함하지 않는 것이 바람직하다.

향후 적용 가능한 방법:

- AWS Systems Manager Parameter Store
- AWS Secrets Manager
- IAM 역할을 이용한 인증 정보 접근 제어
- 애플리케이션 실행 시 인증 정보 주입

이러한 방식은 비밀번호를 AMI에서 분리하고 인증 정보 교체를 용이하게 하는 데 도움이 된다.

## 11. 이번 교시에서 배운 점

### 1. DB 연결 성공과 데이터 정합성은 다르다

Spring Boot가 MySQL에 연결됐다는 사실만으로 모든 데이터가 정상 이전됐다고 판단할 수 없다. 테이블과 실제 데이터의 비교가 필요하다.

### 2. 허용 테스트만큼 차단 테스트도 중요하다

WEB에서 DB에 직접 접근할 수 없어야 한다는 요구사항을 실제 포트 연결 테스트와 Security Group 설정 확인으로 검증했다.

### 3. Security Group과 Route Table은 역할이 다르다

- Security Group: 어떤 네트워크 통신을 허용할지 결정
- Route Table: 목적지 네트워크로 패킷을 전달할 경로 결정

두 설정이 모두 정상이어야 의도한 통신이 이루어진다.

### 4. AMI는 보안 정보도 함께 복제할 수 있다

AMI에 환경변수 파일이나 인증 정보가 포함되어 있으면 이미지 복제 과정에서 민감 정보도 함께 확산될 수 있다.

따라서 이미지 생성 전 민감 정보 분리, 인증 정보 교체 및 불필요한 스냅샷 정리가 필요하다.

### 5. 서비스 재시작 이후의 검증이 중요하다

systemd에서 프로세스가 실행 중인 것과 실제 애플리케이션이 정상 동작하는 것은 다르다.

서비스 상태, HTTP 응답, DB 연결, 로그를 함께 확인해야 한다.

# 10. Apache WAS 로드밸런싱 및 Spring Session JDBC 구축

### 목표

기존 WEB01 → WAS01, WEB02 → WAS02의 고정 연결 구조를 개선하여, 두 WEB 서버가 WAS01과 WAS02에 요청을 분산하도록 구성한다.

- Spring Security CSRF 관련 장애 분석
- ALB Sticky Session과 WAS 세션 관리의 차이
- Spring Session JDBC 기반 HTTP 세션 공유
- MySQL 세션 테이블 구성
- Spring Boot JAR 재빌드 및 WAS01/WAS02 배포
- 애플리케이션 장애 전환 검증 계획

## 3. Apache WAS 로드밸런싱

### 3.1 Apache 모듈 활성화

WEB01과 WEB02에서 로드밸런싱에 필요한 Apache 모듈을 활성화했다.

```bash
sudo a2enmod proxy_balancer
sudo a2enmod lbmethod_byrequests
sudo a2enmod slotmem_shm
```

기존에 사용하던 `proxy`, `proxy_http` 모듈도 함께 사용한다.

활성화 상태 확인:

```bash
sudo apache2ctl -M | grep -E 'proxy|balancer|lbmethod|slotmem'
```

주요 모듈의 역할:

| 모듈 | 역할 |
|---|---|
| proxy | Reverse Proxy 기본 기능 |
| proxy_http | HTTP 요청 전달 |
| proxy_balancer | 여러 백엔드를 하나의 그룹으로 관리 |
| lbmethod_byrequests | 요청 수 기반 부하 분산 |
| slotmem_shm | 공유 메모리 기반 상태 정보 관리 |

### 3.2 기존 설정 백업

WEB01과 WEB02에서 다음 작업을 수행했다.

```bash
cd /etc/apache2/sites-available

sudo cp marble.conf marble.conf.bak
```

설정 변경 후 장애가 발생하면 기존 설정으로 되돌릴 수 있도록 백업했다.

### 3.3 Apache 로드밸런싱 설정

설정 파일:

`/etc/apache2/sites-available/marble.conf`

기존 단일 WAS 설정:

```apache
ProxyPass / http://10.0.21.126:8080/
ProxyPassReverse / http://10.0.21.126:8080/
```

변경 후 WEB01과 WEB02에 적용한 핵심 설정:

```apache
<Proxy "balancer://marblecluster">
    BalancerMember "http://10.0.21.126:8080"
    BalancerMember "http://10.0.22.9:8080"
    ProxySet lbmethod=byrequests
</Proxy>

ProxyPass "/" "balancer://marblecluster/"
ProxyPassReverse "/" "balancer://marblecluster/"
```

위 설정은 기존 `<VirtualHost *:80>` 내부에서 사용하며, 기존 `ServerName`, 로그 설정 등은 유지한다.

### 3.4 주요 설정의 의미

**BalancerMember**

실제 요청을 처리할 WAS 서버를 등록한다.

**balancer://marblecluster**

두 WAS를 논리적인 서버 그룹으로 묶는다.

**lbmethod=byrequests**

요청 수를 기준으로 부하를 분산하는 방식이다. 두 서버의 가중치가 동일하면 요청 수가 대체로 균형 있게 분산된다.

**ProxyPass**

Apache가 받은 요청을 WAS 서버 그룹으로 전달한다.

**ProxyPassReverse**

백엔드가 반환한 리다이렉트 관련 응답 헤더를 프록시 환경에 맞게 조정한다.

### 3.5 설정 검증 및 반영

```bash
sudo apache2ctl configtest
```

정상 결과:

```text
Syntax OK
```

설정 적용:

```bash
sudo systemctl reload apache2
```

서비스 상태 확인:

```bash
sudo systemctl is-active apache2
```

예상 결과:

```text
active
```

## 4. Apache 로드밸런싱 동작 검증

### 4.1 검증 목적

HTTP 200 응답만으로는 어떤 WAS가 요청을 처리했는지 확인할 수 없다.

따라서 Apache 접근 로그에 실제 선택된 WAS 주소를 기록하도록 구성했다.

### 4.2 백엔드 로그 설정

WEB01과 WEB02의 `marble.conf`에 다음 설정을 추가했다.

```apache
LogFormat "%t \"%r\" %>s backend=%{BALANCER_WORKER_NAME}e" marble_backend
CustomLog /var/log/apache2/marble_backend.log marble_backend
```

`BALANCER_WORKER_NAME`을 통해 Apache가 선택한 백엔드 서버를 확인할 수 있다.

### 4.3 요청 테스트

각 WEB에서 다음 명령어를 실행했다.

```bash
for i in $(seq 1 10); do
    curl -s -o /dev/null -w '%{http_code}\n' \
    -H 'Host: marble.test' \
    http://127.0.0.1/health/db
done
```

로드밸런싱 로그 확인:

```bash
sudo tail -n 20 /var/log/apache2/marble_backend.log
```

로그 예시:

```text
"GET /health/db HTTP/1.1" 200 backend=http://10.0.21.126:8080
"GET /health/db HTTP/1.1" 200 backend=http://10.0.22.9:8080
```

### 4.4 검증 결과

- Apache 로드밸런싱 설정 적용
- WEB01과 WEB02에서 WAS01/WAS02 요청 분산 확인
- 백엔드 로그를 통해 요청 전달 대상 확인
- `/health/db` 정상 응답 확인

이 검증으로 두 WEB 서버가 각각 WAS01과 WAS02를 사용할 수 있음을 확인했다.

## 5. 장애 발생 — 회원가입 HTTP 403 Forbidden

### 5.1 장애 현상

Apache WAS 로드밸런싱을 적용한 후 회원가입 과정에서 다음 오류가 발생했다.

```text
Whitelabel Error Page

There was an unexpected error
(type=Forbidden, status=403).
```

이전 8교시에서는 AWS ALB의 Sticky Session을 통해 회원가입 오류를 완화한 상태였다.

하지만 Apache가 WAS01과 WAS02에 요청을 분산하도록 변경하자 유사한 오류가 다시 발생했다.

### 5.2 Apache 로그 분석

실제 확인한 로그:

```text
[19/Oct/2026:23:59:46 +0000] "GET /health/db HTTP/1.1" 200 backend=http://10.0.22.9:8080
[19/Oct/2026:23:59:46 +0000] "POST /signup HTTP/1.1" 403 backend=http://10.0.21.126:8080
[19/Oct/2026:23:59:46 +0000] "GET /favicon.ico HTTP/1.1" 302 backend=http://10.0.22.9:8080
```

로그에서 `POST /signup` 요청이 WAS01까지 전달됐지만 HTTP 403을 반환한 것을 확인했다.

추가 로그를 통해 회원가입 화면 GET 요청과 회원가입 POST 요청이 서로 다른 WAS에 전달된 것도 확인했다.

### 5.3 원인 분석

Spring Security에서 HTTP 세션에 CSRF 토큰을 보관하는 경우, WAS01과 WAS02가 각각 독립적인 메모리 세션을 사용하면 문제가 발생할 수 있다.

예상되는 장애 흐름:

```text
회원가입 화면 GET
       |
       v
     WAS02
       |
       v
세션 및 CSRF 토큰 생성
       |
       v
회원가입 POST
       |
       v
     WAS01
       |
       v
기존 세션의 CSRF 정보 확인 실패 가능
       |
       v
   HTTP 403
```

이번 테스트 결과는 WAS 간 세션 불일치 가설을 강하게 뒷받침한다.

단, Spring Security의 구체적인 CSRF 예외 로그까지 확보한 것은 아니므로 정확한 예외 원인은 가설과 검증 결과를 구분해 기록한다.

### 5.4 ALB Sticky Session만으로 해결되지 않은 이유

ALB Sticky Session은 사용자의 요청을 동일 WEB 서버로 전달하도록 돕는다.

그러나 Apache가 다시 WAS01과 WAS02로 요청을 분산하면 동일 WEB에 접속한 사용자라도 요청마다 서로 다른 WAS를 사용할 수 있다.

따라서 WAS 계층의 세션 관리 문제는 별도로 해결해야 한다.

## 6. 세션 공유 방식 선택

세션 불일치 문제에 대응하기 위해 다음 방식을 검토했다.

| 방법 | 장점 | 한계 |
|---|---|---|
| Apache WAS Sticky Session | 비교적 간단하게 적용 | WAS 장애 시 세션 이동에 한계 |
| Spring Session JDBC | 기존 MySQL 활용, 추가 EC2 불필요 | DB 부하 및 DB 의존성 증가 |
| Spring Session Redis | 빠른 세션 조회, 업무 DB와 분리 | Redis 인프라 구축 및 운영 필요 |

### 최종 선택

**Spring Session JDBC**

### 선택 이유

1. 기존 Marble 프로젝트에서 MySQL DB01을 사용하고 있다.
2. Redis를 위한 추가 EC2를 생성하지 않아도 된다.
3. WAS01과 WAS02가 동일한 세션을 조회할 수 있다.
4. Spring Security의 CSRF 보호 기능을 유지하면서 세션 관련 문제를 개선할 수 있다.
5. 실습 비용과 인프라 복잡도를 줄일 수 있다.

Redis 기반 세션 저장소는 향후 별도 프로젝트에서 학습할 예정이다.

## 7. Spring Session JDBC 적용

### 7.1 애플리케이션 환경

| 항목 | 버전 및 구성 |
|---|---|
| Java | 21 |
| Spring Boot | 3.3.5 |
| Build Tool | Gradle |
| Spring Security | 사용 |
| Database | MySQL |
| 세션 저장 방식 | Spring Session JDBC |

### 7.2 Gradle 의존성 추가

로컬 PC의 `build.gradle`에 다음 의존성을 추가했다.

```gradle
implementation 'org.springframework.session:spring-session-jdbc'
```

Spring Boot의 의존성 관리 기능을 사용하므로 버전은 별도로 지정하지 않았다.

### 7.3 application.yml 설정

기존 `spring:` 블록에 다음 설정을 추가했다.

```yaml
spring:
  session:
    jdbc:
      initialize-schema: never
      table-name: SPRING_SESSION
```

기존 `spring.datasource` 등 다른 설정은 유지했다.

`initialize-schema: never`를 사용해 테이블을 애플리케이션 시작 시 자동 생성하지 않고, MySQL에 직접 구성했다.

### 7.4 DB 인증 정보 개선

기존 설정:

```yaml
password: ${DB_PASSWORD:marble1234}
```

변경 후:

```yaml
password: ${DB_PASSWORD}
```

DB 비밀번호의 하드코딩된 기본값을 제거하고, 서버 환경변수로 전달하도록 변경했다.

WAS01/WAS02에서는 기존 `/etc/marble/marble.env`에 설정된 값을 사용한다.

## 8. MySQL 세션 테이블 구성

### 8.1 세션 테이블

AWS DB01의 `marble` 데이터베이스에 다음 테이블을 생성했다.

- `SPRING_SESSION`
- `SPRING_SESSION_ATTRIBUTES`

### 8.2 테이블 생성

```sql
USE marble;

CREATE TABLE SPRING_SESSION (
    PRIMARY_ID CHAR(36) NOT NULL,
    SESSION_ID CHAR(36) NOT NULL,
    CREATION_TIME BIGINT NOT NULL,
    LAST_ACCESS_TIME BIGINT NOT NULL,
    MAX_INACTIVE_INTERVAL INT NOT NULL,
    EXPIRY_TIME BIGINT NOT NULL,
    PRINCIPAL_NAME VARCHAR(100),
    CONSTRAINT SPRING_SESSION_PK PRIMARY KEY (PRIMARY_ID)
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC;

CREATE UNIQUE INDEX SPRING_SESSION_IX1
ON SPRING_SESSION (SESSION_ID);

CREATE INDEX SPRING_SESSION_IX2
ON SPRING_SESSION (EXPIRY_TIME);

CREATE INDEX SPRING_SESSION_IX3
ON SPRING_SESSION (PRINCIPAL_NAME);

CREATE TABLE SPRING_SESSION_ATTRIBUTES (
    SESSION_PRIMARY_ID CHAR(36) NOT NULL,
    ATTRIBUTE_NAME VARCHAR(200) NOT NULL,
    ATTRIBUTE_BYTES BLOB NOT NULL,
    CONSTRAINT SPRING_SESSION_ATTRIBUTES_PK
        PRIMARY KEY (SESSION_PRIMARY_ID, ATTRIBUTE_NAME),
    CONSTRAINT SPRING_SESSION_ATTRIBUTES_FK
        FOREIGN KEY (SESSION_PRIMARY_ID)
        REFERENCES SPRING_SESSION(PRIMARY_ID)
        ON DELETE CASCADE
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC;
```

생성된 테이블 확인:

```sql
SHOW TABLES LIKE 'SPRING_SESSION%';
```

### 8.3 테이블 역할

**SPRING_SESSION**

- HTTP 세션 식별자 저장
- 세션 생성 시간 저장
- 마지막 접근 시간 저장
- 세션 만료 시간 관리

**SPRING_SESSION_ATTRIBUTES**

- 세션과 연결된 속성 데이터 저장
- 로그인 및 인증 관련 세션 정보 저장 가능
- 세션에 저장된 CSRF 관련 값 보관 가능

### 8.4 DB 계정 권한 확인

WAS01에서 `marble` 계정으로 MySQL에 접속하여 세션 테이블 조회 및 필요한 데이터 변경 권한이 있는지 확인했다.

```sql
SELECT COUNT(*) FROM SPRING_SESSION;

SELECT COUNT(*) FROM SPRING_SESSION_ATTRIBUTES;

SHOW GRANTS;
```

세션 데이터 조회와 저장에 필요한 DB 권한이 있음을 확인했다.

## 10. Spring Session JDBC 실제 동작 검증

### 10.1 검증 목적

Spring Session JDBC 의존성 추가와 JAR 배포만으로는 실제 세션 공유가 동작한다고 확정할 수 없다.

따라서 MySQL 테이블에 세션 정보가 기록되는지 확인하고, 서로 다른 WAS에서 회원가입 요청을 처리하는 테스트를 진행했다.

### 10.2 세션 저장 확인

AWS DB01에서 다음 SQL을 실행했다.

```sql
USE marble;

SELECT COUNT(*) FROM SPRING_SESSION;

SELECT COUNT(*) FROM SPRING_SESSION_ATTRIBUTES;
```

## 12. 운영 관점에서 남은 한계

### 12.1 MySQL 단일 장애 지점

Spring Session JDBC를 적용하면서 WAS 간 세션 공유는 가능해졌지만, 세션 저장소가 DB01에 의존한다.

DB01에 장애가 발생하면 업무 데이터뿐 아니라 HTTP 세션 처리에도 영향을 줄 수 있다.

향후 DB 복제 및 장애 복구 실습을 통해 이 문제를 추가로 검증할 예정이다.

### 12.2 세션 저장소 부하

HTTP 세션을 MySQL에 저장하면 세션 생성·조회·갱신 시 DB 작업이 발생한다.

사용자 수와 요청량이 많아지는 환경에서는 DB 부하를 고려해야 한다.

향후 Redis 기반 세션 공유와 비교할 수 있다.

### 12.3 WAS 장애 감지 및 재시도

Apache는 실패한 백엔드를 일시적으로 제외할 수 있지만, 모든 요청의 무중단 처리와 안전한 자동 재시도를 보장하지는 않는다.

특히 POST 요청은 중복 처리 위험이 있으므로 자동 재시도 정책을 신중하게 설계해야 한다.

### 12.4 세션 공유와 ALB Sticky Session

MySQL 기반 세션 공유를 적용한 이후에도 기존 ALB Sticky Session 설정은 유지되어 있다.

따라서 향후 ALB Sticky Session을 비활성화한 상태에서도 정상 동작하는지 추가 검증하면 WEB 계층과 WAS 계층의 세션 의존성을 더욱 명확히 확인할 수 있다.

## 13. 이번 교시에서 배운 점

### 1. 다중 계층 로드밸런싱

ALB는 WEB 계층의 요청을 분산하고, Apache는 WAS 계층의 요청을 분산한다.

각 로드밸런서가 관리하는 대상과 장애 범위를 구분해야 한다.

### 2. 서버 이중화만으로 고가용성이 완성되지 않는다

WAS 서버를 두 대로 늘려도 세션을 각각 보관하면 인증 및 상태 유지 기능에서 문제가 발생할 수 있다.

### 3. 장애 분석은 실제 로그를 근거로 진행해야 한다

Apache 백엔드 로그를 통해 403 응답이 발생한 요청의 전달 대상과 HTTP 상태 코드를 확인했다.

또한 회원가입 GET과 POST 요청이 서로 다른 WAS로 전달된다는 사실을 확인해 원인 범위를 좁혔다.

### 4. Sticky Session과 세션 공유는 다르다

Sticky Session은 요청을 가능한 한 같은 대상으로 보내는 방식이다.

세션 공유는 서로 다른 WAS가 동일한 세션 데이터를 조회하도록 하는 방식이다.

### 5. 기능 정상 여부와 내부 동작 검증은 다르다

회원가입 성공만 확인한 것이 아니라 MySQL의 세션 테이블에서 실제 데이터 증가를 확인했다.

### 6. 보안 기능을 비활성화하기보다 원인을 해결해야 한다

Spring Security의 CSRF 보호를 무작정 해제하지 않고, 공통 세션 저장소를 구성해 장애를 개선했다.

## 3. 기술 선택 이유

### 3.1 MySQL Primary/Replica를 선택한 이유

데이터베이스 장애 발생 시 복구할 수 있는 별도의 데이터 사본을 확보하기 위해서다.

기존 구조에서는 DB01에 모든 데이터가 집중되어 있었다.

Replica를 추가하면 DB01의 변경 사항을 DB02에도 반영할 수 있어 수동 Failover를 위한 기반을 확보할 수 있다.

다만 **복제는 백업을 대체하지 않는다.** DB01에서 잘못 삭제한 데이터도 DB02로 복제될 수 있으므로 별도의 백업 및 복구 전략이 필요하다.

### 3.2 GTID 기반 복제를 선택한 이유

GTID(Global Transaction Identifier)는 MySQL 트랜잭션에 부여되는 고유 식별자다.

기존 Binary Log 파일명과 위치를 직접 관리하는 방식과 달리, GTID 기반 복제는 Replica가 자신에게 없는 트랜잭션을 식별하고 이어받을 수 있게 한다.

이번 프로젝트에서는 다음 옵션을 사용했다.

```sql
SOURCE_AUTO_POSITION = 1
```

이를 통해 DB02가 이미 반영한 GTID를 기준으로 필요한 변경 이벤트를 자동으로 요청한다.

### 3.3 비동기 복제의 한계

이번 실습은 비동기 복제다.

Primary의 트랜잭션이 커밋되었더라도 Replica에 적용되기 전 장애가 발생할 수 있다.

따라서 복제 지연에 따라 일부 최신 데이터가 유실될 가능성이 있다.

이번 구성은 자동 무중단·무손실 데이터베이스 이중화가 아니라 **복제 기반 수동 장애 복구 구조**다.

## 6. 초기 데이터 백업 및 복원

### 6.1 초기 데이터 복사가 필요한 이유

Binary Log 복제만 설정한다고 기존 데이터가 자동으로 모두 복사되는 것은 아니다.

따라서 DB01의 기존 데이터를 DB02에 먼저 복원하고, 해당 백업 시점 이후의 변경 사항을 GTID로 이어받도록 구성했다.

### 6.2 DB01 데이터 백업

실습 중 데이터 변경을 최소화하기 위해 WAS01/WAS02 서비스를 잠시 중지했다.

각 WAS 서버에서:

```bash
sudo systemctl stop marble
```

DB01에서 백업 디렉터리 생성:

```bash
sudo install -d -o root -g root -m 700 /var/backups/marble
```

데이터베이스 백업:

```bash
sudo sh -c '
umask 077
mysqldump \
  --single-transaction \
  --quick \
  --routines \
  --triggers \
  --events \
  --no-tablespaces \
  --set-gtid-purged=ON \
  --databases marble \
  > /var/backups/marble/marble-primary.sql
'
```

주요 옵션:

| 옵션 | 설명 |
|---|---|
| `--single-transaction` | InnoDB의 일관된 시점 백업 |
| `--quick` | 결과를 순차적으로 읽어 메모리 사용 완화 |
| `--routines` | 저장 프로시저 및 함수 포함 |
| `--triggers` | 트리거 포함 |
| `--events` | 이벤트 포함 |
| `--set-gtid-purged=ON` | GTID 기반 초기 복제 위치 정보 포함 |
| `--databases marble` | Marble 데이터베이스 백업 |

**주의:** `--set-gtid-purged=ON`으로 기록되는 GTID 집합은 덤프에 포함된 `marble` 스키마의 트랜잭션만을 의미하지 않을 수 있다. 다른 업무 데이터베이스가 존재하는 환경이라면 전체 GTID 이력과 백업 범위를 별도로 검토해야 한다.

백업 파일 확인:

```bash
sudo ls -lh /var/backups/marble/
sudo grep 'Dump completed' /var/backups/marble/marble-primary.sql
```

백업 완료 후 WAS01/WAS02를 다시 시작했다.

```bash
sudo systemctl start marble
sudo systemctl is-active marble
```

### 6.3 DB02로 백업 파일 전송

DB01에서 SFTP 전송용 사본을 생성했다.


```sql
CREATE USER 'marble_repl'@'10.0.32.160'
```

## 8. GTID 기반 복제 연결

DB02에서 복제 연결을 설정했다.

```sql
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '10.0.31.42',
    SOURCE_PORT = 3306,
    SOURCE_USER = 'marble_repl',
    SOURCE_PASSWORD = '실제_복제_계정_비밀번호',
    SOURCE_AUTO_POSITION = 1,
    SOURCE_SSL = 1;
```

위 비밀번호는 예시 문자열이며 실제 비밀번호가 아니다.

실제 적용한 뒤 복제를 시작했다.

```sql
START REPLICA;
```

복제 상태 확인:

```sql
SHOW REPLICA STATUS\G
```

### 주요 설정 의미

| 옵션 | 의미 |
|---|---|
| `SOURCE_HOST` | Primary 주소 |
| `SOURCE_PORT` | MySQL 접속 포트 |
| `SOURCE_USER` | 복제 계정 |
| `SOURCE_PASSWORD` | 복제 계정 인증 정보 |
| `SOURCE_AUTO_POSITION=1` | GTID 기반 자동 위치 지정 |
| `SOURCE_SSL=1` | 복제 연결에 TLS 요청 |

### 복제 상태 검증

실제 확인 결과:

```text
Source_Host: 10.0.31.42

Replica_IO_Running: Yes
Replica_SQL_Running: Yes

Seconds_Behind_Source: 0

Last_IO_Error:
Last_SQL_Error:

Auto_Position: 1
```

추가로 GTID를 확인했다.

```text
Retrieved_Gtid_Set:
ed995cb1-cba4-11f1-95ee-02ffe396cfed:2-9

Executed_Gtid_Set:
ed995cb1-cba4-11f1-95ee-02ffe396cfed:1-9
```

초기 백업에 포함된 GTID `1` 이후, Primary에서 발생한 GTID `2-9`를 Replica가 받아서 적용한 것을 확인했다.

복제 연결 직후에는 `Executed_Gtid_Set`이 `1-4`였으며, 이후 `1-9`로 증가했다.

**결과: GTID 기반 데이터 복제 정상 동작 확인**

참고로 `Source_SSL_Allowed=Yes`였지만 `Source_SSL_Verify_Server_Cert=No`이므로 서버 인증서 검증은 추후 보완할 보안 항목이다.

## 9. Replica 읽기 전용 설정

Replica에서 직접 데이터를 수정하면 Primary와 데이터 불일치가 발생할 수 있다.

이를 방지하기 위해 다음 설정을 사용한다.

DB02에서:

```sql
SET PERSIST super_read_only = ON;
```

확인:

```sql
SELECT
    @@GLOBAL.read_only,
    @@GLOBAL.super_read_only;
```

기대 결과:

```text
read_only       = 1
super_read_only = 1
```

`SET PERSIST`를 이용하면 현재 설정을 적용하고 MySQL 재시작 이후에도 유지할 수 있다.

복제 SQL 스레드는 이 상태에서도 Primary의 변경 이벤트를 적용할 수 있다.

**검증 기록:** 설정 명령은 실습 과정에 포함했으며, 최종 두 변수의 실제 조회 결과는 별도 확인이 필요하다.

## 11. 장애 대응 및 점검 방법

### 11.1 IO 스레드 장애

증상:

```text
Replica_IO_Running: No
```

가능한 원인:

- DB01 MySQL 서비스 중지
- 보안 그룹 TCP 3306 차단
- DB01과 DB02 사이 네트워크 장애
- 복제 계정 인증 오류
- 필요한 Binary Log가 이미 삭제됨

점검:

```sql
SHOW REPLICA STATUS\G
```

특히 다음 항목을 확인한다.

```text
Last_IO_Errno
Last_IO_Error
```

DB02에서 네트워크 확인:

```bash
nc -zv 10.0.31.42 3306
```

복제 계정 인증 확인:

```bash
mysql -h 10.0.31.42 -P 3306 -u marble_repl -p
```

### 11.2 SQL 스레드 장애

증상:

```text
Replica_SQL_Running: No
```

가능한 원인:

- Primary/Replica 데이터 불일치
- 중복된 Primary Key
- 테이블 구조 불일치
- 권한 또는 복제 이벤트 적용 오류

점검:

```sql
SHOW REPLICA STATUS\G
```

특히 다음 항목을 확인한다.

```text
Last_SQL_Errno
Last_SQL_Error
```

**주의:** 오류가 발생했다고 임의로 트랜잭션을 건너뛰면 데이터 불일치가 생길 수 있다. 원인을 확인하고 데이터 정합성에 맞는 복구 방법을 선택해야 한다.

### 11.3 복제 지연

확인:

```sql
SHOW REPLICA STATUS\G
```

주요 항목:

```text
Seconds_Behind_Source
```

복제 지연의 원인으로는 대량 트랜잭션, 디스크 I/O 병목, Replica 자원 부족, 네트워크 문제 등이 있다.

다만 해당 값 하나만으로 모든 데이터 정합성을 보장할 수는 없다. GTID 상태와 실제 데이터도 함께 확인해야 한다.

## 14. 이번 실습에서 배운 내용

### 14.1 복제는 백업이 아니다

Replica는 Primary의 변경 사항을 복사한다.

따라서 Primary에서 잘못 삭제한 데이터나 잘못 실행한 UPDATE도 Replica로 전파될 수 있다.

별도의 데이터 백업, 보존 정책, 복구 절차가 필요하다.

### 14.2 복제 연결과 장애 전환은 다르다

현재 DB02에 데이터가 복제되고 있어도 WAS 서버는 DB01을 사용하고 있다.

DB01에 장애가 발생하면 DB02로 자동 전환되지 않는다.

장애 전환을 위해서는 복제 지연 및 GTID 상태 확인, Primary 승격, WAS 접속 정보 변경, 애플리케이션 검증이 필요하다.

### 14.3 MySQL 복제에서는 세 가지 상태를 함께 봐야 한다

1. IO 스레드가 변경 이벤트를 정상 수신하는가?
2. SQL 스레드가 이벤트를 정상 적용하는가?
3. 실제 GTID 및 데이터가 기대한 상태로 일치하는가?

`Replica_IO_Running=Yes`만으로 복제 정상 여부를 판단해서는 안 된다.

### 14.4 복제 계정은 별도로 관리해야 한다

애플리케이션 계정과 복제 계정의 목적이 다르므로 권한을 분리한다.

복제 계정에 필요한 권한만 부여하고, 접속 가능한 호스트를 제한하며, 비밀번호를 안전하게 관리해야 한다.
