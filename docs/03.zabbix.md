# 13. Zabbix 기반 인프라 모니터링 및 Discord 장애 알림 구축

## 1. 프로젝트 개요

AWS에 구축한 Marble 서비스의 WEB, WAS, DB 서버를 대상으로 Zabbix 기반 통합 모니터링 환경을 구성하였다.

단순히 서버의 CPU와 메모리 사용률을 확인하는 수준을 넘어, 서비스 포트와 HTTP 헬스체크를 통해 장애를 탐지하고 Discord로 장애 발생 및 복구 알림을 자동 전송하는 기능을 구현하였다.

**프로젝트 목표**

- Zabbix Server를 이용한 중앙 집중식 인프라 모니터링
- WEB/WAS/DB 총 6대 서버의 리소스 상태 수집
- WEB, WAS, DB 서비스 포트 상태 감시
- Spring Boot HTTP 헬스체크
- Trigger를 이용한 장애 자동 탐지
- Discord Webhook을 이용한 장애 발생 및 복구 알림
- 실제 서비스 장애 상황을 통한 모니터링 기능 검증

---

## 2. 시스템 아키텍처

### 2.1 전체 구조

AWS VPC 내부에 Zabbix Server와 모니터링 대상 서버를 구성하였다.

**Public Subnet**

- Zabbix Server
  - Ubuntu 24.04
  - Zabbix 7.0 LTS
  - Zabbix Server / Agent 2
  - MySQL
  - Nginx / PHP-FPM

**Private Subnet**

- WEB01 / WEB02 — Apache
- WAS01 / WAS02 — Spring Boot
- DB01 / DB02 — MySQL

**모니터링 및 알림 흐름**

1. 각 서버의 Zabbix Agent 2가 시스템 상태를 수집한다.
2. Zabbix Server가 Agent를 통해 CPU, 메모리, 디스크, 서비스 포트 데이터를 가져온다.
3. Zabbix Web scenario가 WAS의 HTTP 헬스체크를 수행한다.
4. Trigger가 수집된 데이터를 분석해 장애 여부를 판단한다.
5. Trigger Action이 장애 이벤트 발생 시 Discord Webhook을 호출한다.
6. Discord 채널에 장애 발생 및 복구 알림이 표시된다.

### 2.2 주요 통신 포트

| 출발지 | 목적지 | 포트 | 용도 |
|---|---|---|---|
| 관리자 PC | Zabbix EC2 | TCP 22 | SSH 접속 및 포트 포워딩 |
| Zabbix Server | WEB/WAS/DB | TCP 10050 | Zabbix Agent 수동 검사 |
| Zabbix Server | WAS01 | TCP 8080 | HTTP 헬스체크 |
| Zabbix Server | Discord | TCP 443 | Webhook 알림 전송 |

Zabbix 웹 관리 화면은 SSH 로컬 포트 포워딩을 이용하여 접속하였다.

관리 화면의 HTTP 8080 포트를 인터넷에 직접 공개하지 않고, SSH 터널을 통해 접근하도록 구성하였다.

### 2.3 네트워크 및 보안 설계

- Zabbix Server는 AWS Public Subnet에 배치
- WEB/WAS/DB는 Private Subnet에서 운영
- 같은 VPC의 Private IP를 사용하여 모니터링 통신
- 각 대상 서버의 보안 그룹에서 TCP 10050을 Zabbix 보안 그룹에 한정하여 허용
- HTTP 헬스체크에 필요한 WAS 포트만 별도로 접근 허용
- Discord Webhook URL은 GitHub에 노출하지 않음

Private Subnet 서버에 Zabbix Agent를 설치할 때는 기존에 준비한 패키지 파일을 전달하여 NAT Gateway를 추가하지 않고 설치하였다.

**설계 의도**

- 모니터링 서버와 실제 서비스 서버의 역할 분리
- Private Subnet의 서비스 서버를 외부에 직접 노출하지 않음
- 불필요한 NAT Gateway 비용 방지
- 서비스 포트와 모니터링 포트의 접근 권한 분리

## 3. Zabbix Server 구축

### 3.1 사용 기술

| 항목 | 사용 기술 |
|---|---|
| 클라우드 | AWS EC2 / VPC |
| 운영체제 | Ubuntu 24.04 LTS |
| 모니터링 | Zabbix 7.0 LTS |
| Agent | Zabbix Agent 2 |
| Zabbix 데이터베이스 | MySQL |
| 웹 서버 | Nginx |
| 알림 | Discord Webhook |

### 3.2 Zabbix 구성 요소

**Zabbix Server**

모니터링 대상 서버로부터 데이터를 수집하고, Trigger를 평가하며, 장애 이벤트와 알림을 관리한다.

**Zabbix Agent 2**

모니터링 대상 서버에 설치하여 CPU, 메모리, 디스크, 네트워크 및 서비스 포트 상태 등을 수집한다.

**Zabbix Frontend**

웹 기반 관리 화면으로 호스트 등록, Item, Trigger, Dashboard, Action 등을 설정한다.

**MySQL**

Zabbix의 설정 정보, 수집 데이터 및 이벤트 기록 등을 저장한다.

### 3.3 주요 서비스 상태 점검

## 5. 서비스 상태 모니터링

### 5.1 서비스 포트 감시

Zabbix의 `net.tcp.listen[]` Item을 사용하여 서비스 포트의 LISTEN 상태를 수집하였다.

| 서버 | 서비스 | 포트 | Item Key |
|---|---|---|---|
| WEB01 | Apache | 80 | `net.tcp.listen[80]` |
| WEB02 | Apache | 80 | `net.tcp.listen[80]` |
| WAS01 | Spring Boot | 8080 | `net.tcp.listen[8080]` |
| WAS02 | Spring Boot | 8080 | `net.tcp.listen[8080]` |
| DB01 | MySQL | 3306 | `net.tcp.listen[3306]` |
| DB02 | MySQL | 3306 | `net.tcp.listen[3306]` |

Item 설정:

- Type: Zabbix agent
- Type of information: Numeric (unsigned)
- Update interval: 30s

**수집 값의 의미**

- `1`: 지정한 TCP 포트가 LISTEN 상태
- `0`: 지정한 TCP 포트가 LISTEN 상태가 아님

**검증 결과:** 총 6대 서버에서 각 서비스 포트 Item의 값이 `1`로 수집되는 것을 확인하였다.

단, TCP 포트가 LISTEN 상태라고 해서 실제 애플리케이션 요청이 정상 처리되는 것은 아니므로 HTTP 헬스체크도 별도로 구성하였다.

### 5.2 WAS HTTP 헬스체크

Zabbix Web scenario를 사용하여 WAS01의 Spring Boot `/health` 엔드포인트를 모니터링하였다.

**Web scenario 설정**

| 항목 | 값 |
|---|---|
| Name | Marble WAS01 Health Check |
| 대상 | WAS01 |
| URL | `http://WAS01_PRIVATE_IP:8080/health` |
| Required status codes | 200 |
| Update interval | 1m |

**검증 결과**

WAS01 `/health` 엔드포인트에서 HTTP 200 응답이 반환되는 것을 확인하였다.

**포트 감시와 HTTP 헬스체크의 차이**

| 구분 | 확인 내용 |
|---|---|
| TCP 포트 감시 | 서비스 프로세스가 포트를 열고 있는가? |
| HTTP 헬스체크 | 애플리케이션이 HTTP 요청에 정상 응답하는가? |

## 6. 장애 탐지 Trigger 구성

### 6.1 Trigger의 역할

Zabbix에서 Item이 수집한 데이터를 특정 조건으로 평가하여 장애 여부를 판단한다.

예를 들어 WEB01의 Apache 포트가 계속 닫혀 있으면 PROBLEM 이벤트가 발생하도록 구성하였다.

**WEB01 Trigger Expression**

`max(/marble-web01/net.tcp.listen[80],2m)=0`

의미:

- `net.tcp.listen[80]`: Apache 포트 상태
- `2m`: 최근 2분 동안의 수집 데이터
- `max(...)=0`: 해당 구간에서 수집된 값이 모두 0이면 장애로 판단

순간적인 값 변화보다는 일정 시간 지속되는 상태를 기준으로 장애를 탐지하도록 하였다.

### 6.2 서비스 장애 Trigger

| 서버 | 장애 조건 |
|---|---|
| WEB01 | `max(/marble-web01/net.tcp.listen[80],2m)=0` |
| WEB02 | `max(/marble-web02/net.tcp.listen[80],2m)=0` |
| WAS01 | `max(/marble-was01/net.tcp.listen[8080],2m)=0` |
| WAS02 | `max(/marble-was02/net.tcp.listen[8080],2m)=0` |
| DB01 | `max(/marble-db01/net.tcp.listen[3306],2m)=0` |
| DB02 | `max(/marble-db02/net.tcp.listen[3306],2m)=0` |

서비스 장애 Trigger는 High 심각도로 구성하였다.

### 6.3 HTTP 헬스체크 Trigger

WAS01의 Web scenario 실패 여부도 Trigger로 감시하였다.

`last(/marble-was01/web.test.fail[Marble WAS01 Health Check])<>0`

Web scenario의 실패 단계 값이 0이 아니면 장애로 판단한다.

**이번 실습 범위:** 서버 리소스, 서비스 포트, HTTP 헬스체크 및 장애 알림

MySQL Primary–Replica의 복제 스레드와 지연 시간 모니터링은 이번 Zabbix 실습 범위에서 제외하였다.

## 8. Discord 장애 알림 연동

### 8.1 연동 목적

Zabbix Dashboard를 지속적으로 확인하지 않아도 서비스 장애 발생 사실을 전달받을 수 있도록 Discord Webhook 알림을 구성하였다.

### 8.2 장애 알림 구조

1. Zabbix Item이 비정상 값을 수집한다.
2. Trigger 조건에 따라 PROBLEM 이벤트가 발생한다.
3. Trigger Action이 이벤트 조건을 확인한다.
4. Discord Media type을 사용하여 알림을 전송한다.
5. Discord 채널에서 장애 정보를 확인한다.
6. 서비스 복구 시 OK 이벤트를 기반으로 복구 알림을 전송한다.

### 8.3 Discord Webhook

Discord의 `marble-alerts` 채널에 Webhook을 생성하고 Zabbix Media type과 연동하였다.

Discord Webhook URL은 인증 정보이므로 GitHub 및 공개 문서에 포함하지 않는다.

### 8.4 Trigger Action 설정

Action 이름:

`Marble Discord Alerts`

**Conditions**

- Trigger severity: High 이상
- Host group: Marble 모니터링 대상 그룹

**Operations**

- Operation: Send message
- Recipient: Admin
- Media type: Discord

**Recovery operations**

- Operation: Send message
- Recipient: Admin
- Media type: Discord

- 장애가 발생한 서버
- 장애 이름
- 장애 심각도
- 발생 시간
- 이벤트 ID

## 9. 실제 장애 테스트 및 검증

### 9.1 테스트 목적

설정된 Trigger와 Action이 실제 서비스 장애 상황에서도 정상적으로 동작하는지 확인하였다.

단순 Webhook 테스트 성공이 아니라, 실제 WEB 서버 중단을 통해 전체 알림 흐름을 검증하였다.

### 9.2 장애 시나리오

**시나리오: WEB01 Apache 서비스 중단**

1. WEB01의 Apache 서비스를 중단한다.
2. Zabbix Agent가 TCP 80 포트 상태를 수집한다.
3. Item 값이 `1`에서 `0`으로 변경된다.
4. Trigger 조건이 충족되면 PROBLEM 이벤트가 발생한다.
5. Trigger Action이 Discord 장애 알림을 전송한다.
6. Apache 서비스를 다시 시작한다.
7. Item 값이 `0`에서 `1`로 복구된다.
8. Zabbix가 장애 복구를 감지한다.
9. Discord에 복구 알림이 전송된다.

### 9.3 테스트 명령어

WEB01의 Apache 중단:

`sudo systemctl stop apache2`

WEB01의 Apache 복구:

`sudo systemctl start apache2`

서비스 상태 확인:

`sudo systemctl is-active apache2`

HTTP 응답 확인:

`curl -I http://127.0.0.1`

### 9.4 테스트 결과

| 테스트 항목 | 실제 확인 결과 |
|---|---|
| Apache 중단 | 수행 |
| WEB01 포트 Item | `0` 수집 확인 |
| Zabbix Problems | PROBLEM 발생 확인 |
| Discord 장애 알림 | 수신 성공 |
| Apache 복구 | 수행 |
| Discord 복구 알림 | 수신 성공 |

**최종 결과: 장애 탐지 → 알림 전송 → 서비스 복구 → 복구 알림 흐름을 실제로 검증하였다.**

## 10. 트러블슈팅

### 10.1 Discord Media type 테스트 오류

**문제**

`Incorrect "event_source" parameter given: {EVENT.SOURCE}. Must be 0-4.`

**원인**

Media type의 수동 테스트에서는 실제 이벤트 정보가 없기 때문에 일부 이벤트 매크로가 숫자로 치환되지 않았다.

**해결**

테스트 화면의 이벤트 관련 매크로를 테스트용 값으로 지정하였다.

예시:

- `event_source=0`
- `event_value=1`
- `event_severity=4`

이후 테스트를 다시 진행하였다.

### 10.2 Discord URL 매크로 오류

**문제**

`URL value "{$ZABBIX.URL}" must contain a schema.`

**원인**

Discord Webhook에서 사용하는 Zabbix URL 매크로가 실제 주소로 치환되지 않았다.

**해결**

Discord Media type의 `zabbix_url` 설정을 확인하고 유효한 HTTP URL로 변경하였다.

실습 환경에서는 SSH 로컬 포트 포워딩 주소를 사용하였다.

`http://127.0.0.1:8080`

해당 링크는 SSH 터널이 연결된 관리자 PC에서만 접근 가능하다.

### 10.3 Trigger는 동작하지만 Discord 알림이 오지 않는 문제

**증상**

- WEB01의 `net.tcp.listen[80]` 값이 `0`으로 변경됨
- Monitoring → Problems에서 장애 확인
- Discord 알림 미수신

**원인 분석**

Item 및 Trigger는 정상 동작하므로 모니터링 대상이나 장애 탐지 자체의 문제는 아니라고 판단하였다.

Zabbix `Reports → Action log`에서 전송 실패 메시지를 확인하였다.

**확인된 오류**

`Sending failed: Webhook processing failed: URL value "{$ZABBIX.URL}" must contain a schema.`

**해결**

Discord Media type의 `zabbix_url` 설정을 수정한 후 다시 알림을 검증하였다.

수정 이후 Discord 장애 알림과 복구 알림이 정상적으로 수신되었다.

### 10.4 트러블슈팅을 통해 학습한 점

Zabbix에서 장애 알림이 오지 않을 때는 다음 순서로 확인하는 것이 효율적이었다.

1. Item이 정상 데이터를 수집하는지 확인
2. Trigger가 PROBLEM을 발생시키는지 확인
3. Trigger Action이 활성화되고 조건이 일치하는지 확인
4. 관리자 Media가 설정되어 있는지 확인
5. Action log의 전송 실패 원인 확인

이를 통해 **데이터 수집 문제, 장애 판단 문제, 알림 전달 문제를 분리해 진단하는 방법**을 학습하였다.

## 11. 기술 선택 이유

### 11.1 Zabbix를 선택한 이유

Zabbix는 Agent 기반 서버 모니터링, Trigger, Dashboard, 알림 기능을 통합 제공한다.

이번 프로젝트에서는 비교적 적은 수의 WEB/WAS/DB 서버를 통합 관리하면서 시스템 상태뿐 아니라 서비스 포트와 장애 발생 여부까지 확인해야 했다.

이 요구에 따라 Zabbix를 선택하였다.

**장점**

- Agent 기반 시스템 리소스 수집
- 템플릿을 통한 모니터링 항목 재사용
- Trigger 기반 장애 감지
- 웹 기반 운영 Dashboard
- Webhook을 이용한 외부 알림 연동

**고려할 점**

- 수집 항목과 Trigger 조건을 적절히 설계해야 함
- 서버 수와 데이터 보존량 증가 시 Zabbix Server 및 DB 자원 관리 필요
- 잘못된 Trigger 조건으로 오탐 또는 알림 과다 발생 가능

### 11.2 Discord를 선택한 이유

개인 포트폴리오 환경에서 별도 유료 장애 알림 솔루션 없이 Webhook 연동과 장애 메시지 수신을 검증하기 위해 Discord를 사용하였다.

실제 기업 환경에서는 조직의 운영 체계에 따라 이메일, Slack, Microsoft Teams 또는 전문 Incident Management 솔루션을 사용할 수 있다.

## 12. 프로젝트 성과 및 한계

### 12.1 구현 성과

- AWS WEB/WAS/DB 총 6대의 리소스 모니터링 환경 구축
- Zabbix Agent 2 기반 중앙 집중식 서버 모니터링 구현
- TCP 포트 감시를 통한 서비스 상태 수집
- Spring Boot HTTP 헬스체크 구성
- 서비스 장애 Trigger 구성
- Discord Webhook 및 Trigger Action 연동
- 실제 Apache 중단 테스트를 통한 장애 및 복구 알림 검증
- AWS Private Subnet 구조를 유지한 상태에서 모니터링 구현

### 12.2 현재 구현 범위의 한계

- TCP 포트 감시만으로 애플리케이션의 모든 기능을 확인할 수 없음
- WAS01 이외의 HTTP 헬스체크 확대는 추가 개선 가능
- MySQL 포트 상태는 감시하지만 데이터베이스 쿼리 성공 여부까지 검증한 것은 아님
- MySQL 복제 상태 및 지연 시간 감시는 이번 범위에서 제외
- 장애 감지 및 알림은 구현했지만 자동 복구 기능은 구현하지 않음

### 12.3 추후 개선 방향

- WEB01/02 및 WAS02 HTTP 헬스체크 확대
- CPU·메모리·디스크 임계치 Trigger 고도화
- 알림 중복 방지 및 심각도별 알림 정책 개선
- 장애 이벤트와 애플리케이션 로그를 함께 분석하는 운영 절차 정리
- 장애 감지부터 조치 및 복구까지의 운영 Runbook 작성

## 13. 최종 결과

이번 프로젝트에서는 Zabbix를 단순히 설치하는 데서 끝나지 않고, **AWS 인프라의 상태를 수집하고 실제 서비스 장애를 탐지하여 외부 알림까지 전달하는 운영 모니터링 환경**을 구현하였다.

특히 WEB01 Apache 중단 테스트에서 Zabbix Item과 Trigger가 장애를 정상적으로 감지하였으며, Discord Action의 설정 오류를 Action log를 통해 분석하고 수정하였다.

이후 장애 발생 알림과 복구 알림이 정상적으로 도착하는 것을 확인하였다.

이를 통해 **모니터링 데이터 수집 → 장애 판단 → 알림 실행 → 오류 분석 → 복구 확인**까지 인프라 엔지니어의 기본적인 장애 대응 흐름을 실습하였다.
