
# A과정 4장 2교시 — Spring Boot systemd 서비스 운영

## 1. systemd란?

systemd는 Linux에서 서비스를 시작·중지·재시작하고 실행 상태를 관리하는 시스템 관리자이다.

### systemd를 사용하는 이유

- 서버 부팅 시 Spring Boot 자동 시작
- 애플리케이션 비정상 종료 시 재시작
- 서비스 실행 계정 및 환경변수 관리
- 서비스 상태와 로그 확인

### 실행 방식 차이

```text
수동 실행
ubuntu → java -jar app.jar

systemd 실행
systemd → marble.service → java -jar app.jar
```

핵심: java -jar는 애플리케이션을 실행하고, systemd는 애플리케이션의 운영을 관리한다.

## 3. 실제 systemd 설정

서비스 파일: marble.service

```ini
[Unit]
Description=Marble Spring Boot Application
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=marble
Group=marble
WorkingDirectory=/opt/marble
ExecStart=/usr/bin/java -jar /opt/marble/app.jar

Restart=on-failure
RestartSec=5

Environment="DB_HOST=192.168.111.149"

[Install]
WantedBy=multi-user.target
```

### 주요 설정 해설

| 설정 | 의미 |
|---|---|
| After | 지정한 대상 이후 실행 순서 배치 |
| Wants | 필요한 대상을 함께 활성화하도록 요청 |
| Type=simple | 실행한 프로세스를 서비스로 관리 |
| User=marble | marble 계정으로 실행 |
| Group=marble | marble 그룹 사용 |
| WorkingDirectory | 작업 기준 디렉터리 |
| ExecStart | JAR 실행 명령어 |
| Restart=on-failure | 비정상 종료 시 재시작 시도 |
| RestartSec=5 | 재시작 전 5초 대기 |
| Environment | 프로세스에 환경변수 전달 |
| WantedBy | 부팅 시 자동 시작 등록에 사용 |

주의: network-online.target은 DB 연결이 정상이라는 것을 보장하지 않는다.

---

## 4. 실행 계정을 분리하는 이유

```text
ubuntu
 └─ SSH 접속 및 서버 관리

marble
 └─ Spring Boot 애플리케이션 실행
```

애플리케이션을 root로 실행하지 않고 별도 계정으로 실행하면 필요한 권한만 부여하기 쉽다.

### 파일 권한 확인

```bash
ls -ld /opt/marble
ls -l /opt/marble/app.jar

sudo -u marble test -r /opt/marble/app.jar \
  && echo "JAR readable"
```

- JAR를 읽을 수 있어야 한다.
- 작업 디렉터리에 필요한 접근 권한이 있어야 한다.
- 파일 로그 등을 생성한다면 해당 위치에 쓰기 권한도 필요하다.
- 무조건 chmod 777을 사용하지 않는다.

## 5. 환경변수 관리

실제 프로젝트 설정:

```ini
Environment="DB_HOST=192.168.111.149"
```

Spring Boot 실행 프로세스에 DB_HOST라는 환경변수를 전달한다.

애플리케이션에서 다음처럼 참조할 수 있다.

```properties
spring.datasource.url=jdbc:mysql://${DB_HOST}:3306/DB이름
```

위 application.properties는 환경변수 사용법을 보여주는 예시이며, 실제 프로젝트의 DB 설정과 다를 수 있다.

핵심: DB 주소와 같은 환경별 설정을 JAR 외부에서 전달할 수 있다.

## 6. systemctl 주요 명령어

```bash
# 서비스 상태 확인
sudo systemctl status marble

# 서비스 시작
sudo systemctl start marble

# 서비스 중지
sudo systemctl stop marble

# 서비스 재시작
sudo systemctl restart marble

# 부팅 시 자동 시작 등록
sudo systemctl enable marble

# 자동 시작 여부 확인
systemctl is-enabled marble

# 실행 상태 확인
systemctl is-active marble

# 서비스 파일 변경 후 다시 읽기
sudo systemctl daemon-reload

# 현재 적용된 서비스 설정 확인
systemctl cat marble
```

### 중요 차이

- start: 지금 실행
- enable: 부팅 시 자동 시작 등록
- restart: 실행 중인 서비스 재시작
- daemon-reload: systemd 서비스 정의 다시 읽기

서비스 파일을 수정했다면 일반적으로 다음 순서로 적용한다.

```bash
sudo systemctl daemon-reload
sudo systemctl restart marble
```

운영 중에는 서비스 재시작에 따른 중단 영향을 먼저 확인한다.

## 7. Spring Boot 로그 확인

### 최근 로그

```bash
sudo journalctl -u marble -n 50 --no-pager
```

### 실시간 로그

```bash
sudo journalctl -u marble -f
```

### 현재 부팅 이후 로그

```bash
sudo journalctl -u marble -b --no-pager
```

로그에서 확인할 내용:

- Spring Boot 시작 및 종료
- Java 예외 발생
- TCP 8080 포트 충돌
- DB 연결 실패
- 애플리케이션 비정상 종료

기존 애플리케이션이 별도 파일 로그를 사용한다면 해당 로그도 함께 확인해야 한다.

## 8. 정상 동작 검증

### WAS01에서 실행

```bash
# 서비스 실행 확인
systemctl is-active marble

# 자동 시작 확인
systemctl is-enabled marble

# 프로세스 확인
ps -ef | grep '[j]ava'

# TCP 8080 수신 확인
sudo ss -lntp '( sport = :8080 )'

# HTTP 응답 확인
curl -i http://127.0.0.1:8080/health
```

/health가 기존 app.jar에 구현되어 있다면 정상 응답을 확인한다.

### WEB01에서 실행

```bash
# WEB → WAS TCP 연결
nc -vz -w 3 192.168.111.148 8080

# WAS 직접 HTTP 응답
curl -i http://192.168.111.148:8080/health
```

핵심 검증 순서:

```text
systemd active
      ↓
Java 프로세스 실행
      ↓
TCP 8080 LISTEN
      ↓
HTTP 정상 응답
      ↓
WEB01 → WAS01 정상 연결
```

systemd가 active라고 해서 HTTP 서비스까지 정상이라는 뜻은 아니다.

## 9. 장애 대응

### ① Spring Boot 서비스 실행 실패

```bash
sudo systemctl status marble
sudo journalctl -u marble -n 50 --no-pager
```

확인할 내용:
- Java 실행 경로
- JAR 파일 위치
- marble 계정의 파일 접근 권한
- 애플리케이션 실행 오류

### ② TCP 8080 포트 충돌

```bash
sudo ss -lntp '( sport = :8080 )'
ps -ef | grep '[j]ava'
```

기존에 수동 실행한 app.jar가 남아 있는지 확인한다.

### ③ 서비스가 반복 재시작되는 경우

```bash
sudo systemctl status marble
sudo journalctl -u marble -n 100 --no-pager
```

Restart=on-failure는 비정상 종료 후 재시작을 시도하지만 근본적인 설정 오류까지 해결하지는 못한다.

## 10. 최종 핵심 정리

1. systemd는 Spring Boot의 실행과 운영을 관리한다.
2. User=marble을 사용해 SSH 로그인 계정과 애플리케이션 실행 계정을 분리한다.
3. WorkingDirectory는 애플리케이션 작업 기준 경로다.
4. ExecStart는 실제 JAR 실행 명령어다.
5. Restart=on-failure는 비정상 종료 시 재시작을 시도한다.
6. Environment를 사용해 DB_HOST 등의 설정을 외부에서 전달할 수 있다.
7. journalctl로 애플리케이션 실행·오류 로그를 확인한다.
8. systemctl active, TCP LISTEN, HTTP 응답을 각각 확인해야 한다.

### 반드시 기억할 한 문장

**systemd는 애플리케이션의 실행을 관리하고, 서비스가 정상인지 여부는 프로세스·포트·HTTP 응답을 통해 검증한다.**
