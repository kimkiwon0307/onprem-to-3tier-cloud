## 2. MySQL 보안 관리

MySQL 보안은 다음 세 가지를 구분해야 한다.

| 항목 | 역할 |
|---|---|
| bind-address | MySQL이 어떤 로컬 IP에서 연결을 받을지 결정 |
| UFW | 어떤 출발지에서 DB 포트에 접근할 수 있는지 제어 |
| MySQL 계정·GRANT | 인증 및 데이터베이스 작업 권한 관리 |

### 설정 확인 — DB01

```bash
sudo systemctl status mysql --no-pager

sudo ss -lntp '( sport = :3306 )'

sudo ufw status verbose
```

MySQL 접속:

```bash
sudo mysql
```

SQL 실행:

```sql
SHOW VARIABLES LIKE 'bind_address';

SELECT user, host FROM mysql.user;

SHOW GRANTS;
```

### 보안 원칙

- DB 포트 3306은 필요한 WAS에서만 접근하도록 제한한다.
- 애플리케이션 DB 계정에는 최소 권한을 부여한다.
- DB 비밀번호를 GitHub나 로그에 공개하지 않는다.
- 불필요한 `ALL PRIVILEGES` 권한 부여를 피한다.

## 3. MySQL 연결 수 관리

### max_connections란?

MySQL이 허용하는 일반 클라이언트의 동시 연결 수를 제한하는 설정이다.

### 연결 상태 확인

```sql
-- 설정된 연결 한도
SHOW VARIABLES LIKE 'max_connections';

-- 현재 열린 연결 수
SHOW GLOBAL STATUS LIKE 'Threads_connected';

-- 서버 시작 이후 최대 동시 연결 수
SHOW GLOBAL STATUS LIKE 'Max_used_connections';

-- 연결 한도 초과로 거부된 횟수
SHOW GLOBAL STATUS LIKE 'Connection_errors_max_connections';
```

| 항목 | 의미 |
|---|---|
| max_connections | 설정된 연결 한도 |
| Threads_connected | 현재 연결 수 |
| Max_used_connections | 관측된 최대 연결 수 |
| Connection_errors_max_connections | 연결 한도 초과 오류 횟수 |

### 주의사항

Too many connections 오류가 발생했다고 무조건 max_connections를 증가시키면 안 된다.

먼저 확인할 내용:
- 실제 DB 연결 수
- Spring Boot 커넥션 풀 설정
- 연결 누수 여부
- 동시 요청량
- MySQL 메모리 사용량

## 4. 실행 중인 SQL 확인

### SHOW FULL PROCESSLIST

```sql
SHOW FULL PROCESSLIST;
```

현재 MySQL에 연결된 세션과 실행 중인 작업을 확인한다.

| 항목 | 의미 |
|---|---|
| User | MySQL 사용자 |
| Host | 접속한 클라이언트 |
| Command | 현재 작업 유형 |
| Time | 현재 상태 지속 시간 |
| State | 작업 상태 |
| Info | 실행 중인 SQL 등 |

### 중요 개념

- Sleep: 연결되어 있지만 현재 쿼리를 실행하지 않는 상태
- Query: 쿼리를 실행하는 상태

Sleep이 있다고 무조건 장애는 아니다.

Spring Boot의 Connection Pool은 연결을 재사용하기 위해 유휴 연결을 유지할 수 있다.

## 5. Slow Query Log

### Slow Query Log란?

오래 걸리는 SQL을 찾아 성능 문제를 분석하기 위한 로그다.

### 설정 확인

```sql
SHOW VARIABLES LIKE 'slow_query_log';

SHOW VARIABLES LIKE 'long_query_time';

SHOW VARIABLES LIKE 'slow_query_log_file';

SHOW VARIABLES LIKE 'log_output';
```

| 항목 | 의미 |
|---|---|
| slow_query_log | 느린 쿼리 로깅 활성화 여부 |
| long_query_time | 느린 쿼리 판단 기준 시간 |
| slow_query_log_file | 로그 파일 경로 |
| log_output | 로그 출력 대상 |

예를 들어 long_query_time이 2초라면 설정 조건을 충족하는 2초 초과 쿼리가 기록될 수 있다.

운영 환경에서는 로그량과 성능 영향을 고려하여 설정한다.

## 6. EXPLAIN — SQL 실행 계획 확인

### EXPLAIN이란?

MySQL이 SQL을 어떤 방법으로 실행할 예정인지 확인하는 명령어다.

```sql
EXPLAIN
SELECT *
FROM a_course05_lab.lesson_items
WHERE id = 1;
```

위 SQL은 해당 실습 DB와 테이블이 존재할 때만 실행한다.

### 주요 항목

| 항목 | 의미 |
|---|---|
| type | 테이블 접근 방식 |
| possible_keys | 사용 가능한 인덱스 후보 |
| key | 실제 선택된 인덱스 |
| rows | 검사할 것으로 예상되는 행 수 |
| Extra | 추가 실행 정보 |

### 핵심

- 인덱스는 조건에 맞는 데이터를 효율적으로 찾는 데 도움을 준다.
- EXPLAIN을 이용하면 SQL 실행 계획을 분석할 수 있다.
- 인덱스가 있다고 무조건 쿼리가 빠른 것은 아니다.

## 7. CPU·메모리·디스크 점검

### DB01에서 실행

```bash
# CPU 처리 단위 확인
nproc

# 메모리 사용량
free -h

# MySQL 프로세스 자원 사용량
ps -C mysqld -o pid,%cpu,rss,cmd

# 파일시스템 공간 확인
df -h

# inode 사용량 확인
df -i
```

### MySQL 데이터 경로 확인

```sql
SHOW VARIABLES LIKE 'datadir';
```

예를 들어 데이터 경로가 `/var/lib/mysql`이라면:

```bash
df -h /var/lib/mysql
```

### 주의사항

- 디스크 부족 시 MySQL 데이터 파일을 임의로 삭제하지 않는다.
- Binary Log를 무작정 삭제하지 않는다.
- 복제 환경에서는 Binary Log 삭제가 Replica에 영향을 줄 수 있다.

## 8. 주요 장애 대응

### ① DB 연결 실패

WAS01에서 실행:

```bash
nc -vz -w 3 192.168.111.149 3306
```

DB01에서 실행:

```bash
sudo systemctl status mysql --no-pager

sudo ss -lntp '( sport = :3306 )'

sudo ufw status verbose

sudo journalctl -u mysql -n 50 --no-pager
```

Spring Boot 로그 확인 — WAS01:

```bash
sudo journalctl -u marble -n 50 --no-pager
```

### ② Access denied (1045)

확인할 내용:

- DB 사용자 이름
- 비밀번호
- 'user'@'host' 계정 매칭
- 인증 방식

권한 확인 예시:

```sql
SHOW GRANTS FOR '실제사용자'@'실제호스트';
```

인증 실패와 로그인 후 SQL 권한 부족은 구분해야 한다.

### ③ Too many connections

```sql
SHOW VARIABLES LIKE 'max_connections';

SHOW GLOBAL STATUS LIKE 'Threads_connected';

SHOW FULL PROCESSLIST;
```

연결 수, 커넥션 풀, 연결 누수 여부를 확인한다.

### ④ SQL 응답 지연

```sql
SHOW FULL PROCESSLIST;

SHOW VARIABLES LIKE 'slow_query_log';

SHOW VARIABLES LIKE 'long_query_time';

EXPLAIN SELECT * FROM a_course05_lab.lesson_items WHERE id = 1;
```

쿼리 실행 계획과 CPU·메모리·디스크 상태를 함께 분석한다.

### ⑤ mysqldump 백업 실패

확인 대상:
- 백업 계정 권한
- DB 존재 여부
- 디스크 공간
- 실제 백업 오류 로그
- 백업 옵션 및 MySQL 복제 설정

```bash
df -h
```

```sql
SHOW GRANTS;
```

백업 후에는 별도 DB에서 실제 복원 검증을 진행한다.

## 9. 장애 분석 핵심 순서

### DB 연결 장애

```text
Spring Boot DB 연결 실패
        ↓
DB01 MySQL 서비스 확인
        ↓
TCP 3306 LISTEN 확인
        ↓
WAS01 → DB01 TCP 연결 확인
        ↓
계정 인증 및 GRANT 확인
        ↓
SQL 실행 검증
        ↓
애플리케이션 DB 기능 재검증
```

### DB 성능 장애

```text
DB 응답 지연
       ↓
현재 연결 수 확인
       ↓
PROCESSLIST 확인
       ↓
Slow Query Log 확인
       ↓
EXPLAIN 실행 계획 분석
       ↓
CPU·메모리·디스크 확인
       ↓
병목 원인 해결 및 재검증
```

## 10. 반드시 기억할 핵심

1. bind-address, UFW, MySQL 계정·권한은 서로 다른 보안 단계다.
2. max_connections는 MySQL의 연결 한도를 관리한다.
3. SHOW FULL PROCESSLIST로 현재 연결과 SQL 작업을 확인한다.
4. Slow Query Log는 오래 걸리는 SQL을 분석하는 데 사용한다.
5. EXPLAIN은 SQL의 실행 계획을 확인한다.
6. CPU·메모리·디스크 부족도 DB 성능 장애의 원인이 될 수 있다.
7. MySQL 설정값을 무조건 증가시키거나 서비스를 재시작하지 않는다.
8. 장애 원인을 확인하고 수정한 뒤 실제 DB 기능을 다시 검증한다.

### 반드시 기억할 두 문장

**연결 장애는 서비스 → 포트 → 네트워크 → 인증 → SQL 순서로 확인한다.**

**성능 장애는 연결 수 → 실행 중인 쿼리 → 실행 계획 → 서버 자원을 함께 분석한다.**
