
# A과정 6장 2교시 — AWS Subnet 및 AZ 구성

## 1. Subnet이란?

Subnet은 VPC의 IP 주소 공간을 작은 네트워크로 나눈 것이다.

### Subnet을 나누는 이유

1. WEB·WAS·DB 역할별 네트워크 분리
2. 계층별 라우팅 및 보안 정책 관리
3. 여러 AZ에 서버를 분산 배치
4. 장애 영향 범위 축소 및 확장성 확보

### 핵심 개념

- VPC: 전체 네트워크 주소 공간
- Subnet: VPC 안의 작은 네트워크
- AZ: AWS 리전 내의 가용 영역

**VPC는 리전 단위, Subnet은 하나의 AZ에 속한다.**

---

## 2. Public Subnet과 Private Subnet

### Public Subnet

Internet Gateway(IGW)로 향하는 직접 라우팅 경로를 가진 Subnet이다.

라우팅 예시:

Destination: 0.0.0.0/0
Target: Internet Gateway

### Private Subnet

IGW로 향하는 직접 라우팅 경로가 없는 Subnet이다.

인터넷에 나가는 통신이 필요하면 NAT Gateway 등의 구성을 사용할 수 있다.

### 주의할 점

- Public/Private 여부는 Subnet 이름으로 결정되지 않는다.
- Route Table의 인터넷 연결 경로가 중요하다.
- Public Subnet의 EC2도 공인 IP와 적절한 보안 설정이 필요하다.
- Private Subnet에 있어도 VPC 내부에서 허용된 통신은 가능하다.
- Subnet을 나누는 것만으로 서버 간 접근이 자동 차단되지는 않는다.

## 3. 실제 Marble 프로젝트 네트워크 구성

### VPC

10.0.0.0/16

### 총 8개 Subnet

| 구분 | AZ-a | AZ-c |
|---|---|---|
| Public | 10.0.1.0/24 | 10.0.2.0/24 |
| Private WEB | 10.0.11.0/24 | 10.0.12.0/24 |
| Private WAS | 10.0.21.0/24 | 10.0.22.0/24 |
| Private DB | 10.0.31.0/24 | 10.0.32.0/24 |

### 전체 아키텍처

```text
VPC 10.0.0.0/16
│
├── AZ-a
│   ├── Public         10.0.1.0/24
│   ├── Private WEB    10.0.11.0/24
│   ├── Private WAS    10.0.21.0/24
│   └── Private DB     10.0.31.0/24
│
└── AZ-c
    ├── Public         10.0.2.0/24
    ├── Private WEB    10.0.12.0/24
    ├── Private WAS    10.0.22.0/24
    └── Private DB     10.0.32.0/24
```

### 실제 서버 배치

```text
인터넷 사용자
      ↓
Public Subnet
ALB
      ↓
Private WEB Subnet
WEB01 / WEB02 (Apache)
      ↓
Private WAS Subnet
WAS01 / WAS02 (Spring Boot)
      ↓
Private DB Subnet
MySQL Primary / Replica
```

Public 영역에는 ALB, Bastion, Zabbix 등의 구성도 배치했다.

### WEB을 Private Subnet에 배치한 이유

- WEB EC2에 직접 인터넷 접근 경로를 제공할 필요를 줄이기 위해
- 외부 HTTP 요청을 ALB를 통해 전달하도록 하기 위해
- ALB와 WEB 간 접근을 Security Group으로 제한하기 위해
- WAS·DB를 포함한 계층별 네트워크 구조를 유지하기 위해

**Public ALB → Private WEB으로 HTTP 요청을 전달할 수 있다.**

단, ALB의 Target Group, 라우팅 및 Security Group 설정이 올바르게 구성되어야 한다.

## 4. AZ를 두 개 사용하는 이유

AZ(Availability Zone)는 하나의 AWS 리전 내에서 서로 분리된 인프라 운영 영역이다.

### 두 AZ를 사용하는 이유

1. 단일 AZ 장애에 대비
2. WEB01/WEB02 분산 배치
3. WAS01/WAS02 분산 배치
4. MySQL Primary/Replica 분산 배치

주의:

두 AZ에 서버를 배치하는 것만으로 자동 장애 전환이 완성되지는 않는다.

ALB 분산, 애플리케이션 상태 및 DB 복제·장애 전환 설정이 추가로 필요하다.

---

## 5. AWS Subnet IP 주소

예시: 10.0.11.0/24

- 전체 IPv4 주소: 256개
- AWS 예약 IPv4 주소: 5개
- 리소스에 할당 가능한 주소: 251개

AWS는 각 Subnet에서 첫 4개와 마지막 1개의 IPv4 주소를 예약한다.

### Subnet 설계 원칙

1. Subnet CIDR은 VPC CIDR 안에 포함되어야 한다.
2. 동일 VPC의 Subnet CIDR은 서로 겹치면 안 된다.
3. Subnet 하나는 한 AZ에 속한다.
4. 향후 서버 증설을 고려해 주소 범위를 정한다.

## 6. AWS 콘솔에서 확인할 항목

AWS 콘솔 → VPC → Subnets

기존 프로젝트의 8개 Subnet을 선택하여 확인한다.

| 확인 항목 | 검증 목적 |
|---|---|
| VPC ID | 모두 올바른 VPC에 속하는가? |
| Availability Zone | 설계한 AZ에 배치되었는가? |
| IPv4 CIDR | 주소 범위가 올바른가? |
| State | Available 상태인가? |
| Available IPv4 addresses | 사용 가능한 IP가 충분한가? |
| Route Table | 올바른 라우팅 테이블을 사용하는가? |

### Route Table 관련 주의사항

새 Subnet은 별도 Route Table 연결이 없다면 VPC의 Main Route Table을 사용한다.

Public/Private 경로는 7장에서 본격적으로 구성·검증한다.

## 7. 주요 장애 및 설정 오류

### ① Subnet CIDR 중복

기존 Subnet과 IP 주소 범위가 겹치면 생성할 수 없다.

### ② VPC 범위를 벗어남

VPC가 10.0.0.0/16인데 192.168.111.0/24 Subnet을 생성하려 하면 오류가 발생한다.

### ③ 잘못된 AZ 선택

이름이 private-web-c여도 실제 AZ가 a일 수 있다.

이름이 아닌 Availability Zone 값을 확인해야 한다.

### ④ Public Subnet 인터넷 연결 실패

확인할 내용:
- IGW 연결
- Route Table 기본 경로
- EC2 공인 IP 필요 여부
- Security Group 및 NACL

### ⑤ Private WEB에 접속할 수 없음

확인할 내용:
- ALB Target Group 설정
- WEB 대상 포트
- ALB → WEB Security Group
- 라우팅 및 WEB 서비스 상태

Private Subnet이라는 이유만으로 ALB에서 접속할 수 없는 것은 아니다.

---

## 8. 반드시 기억할 핵심

1. VPC는 전체 네트워크, Subnet은 나누어진 네트워크이다.
2. VPC는 리전 단위, Subnet은 AZ 단위이다.
3. Public/Private는 Route Table의 IGW 직접 경로로 구분한다.
4. WEB 서버도 Private Subnet에 배치할 수 있다.
5. Marble 프로젝트는 Public 2개 + Private 6개 = 총 8개 Subnet이다.
6. 두 AZ 배치는 가용성 확보를 위한 기반이다.
7. Subnet 분리만으로 보안이 완성되지는 않는다.
8. CIDR·AZ·Route Table·Security Group을 함께 검증해야 한다.

### 핵심 문장

**Subnet은 IP 주소 공간과 AZ 배치를 구분하고, Route Table은 통신 경로를, Security Group은 허용할 네트워크 접근을 제어한다.**
