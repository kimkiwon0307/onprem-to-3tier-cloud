
# A과정 6장 3교시 — AWS VPC·Subnet 검증 및 장애 대응

## 1. 실제 Marble 프로젝트 네트워크

- Region: 서울 (ap-northeast-2)
- VPC CIDR: 10.0.0.0/16
- AZ: 2개
- Subnet: 총 8개 (Public 2개 + Private 6개)

### Subnet 구성

| 구분 | AZ-a | AZ-c |
|---|---|---|
| Public | 10.0.1.0/24 | 10.0.2.0/24 |
| Private WEB | 10.0.11.0/24 | 10.0.12.0/24 |
| Private WAS | 10.0.21.0/24 | 10.0.22.0/24 |
| Private DB | 10.0.31.0/24 | 10.0.32.0/24 |

### 요청 흐름

```text
인터넷 사용자
     ↓
Public Subnet — ALB
     ↓
Private WEB — Apache WEB01/02
     ↓
Private WAS — Spring Boot WAS01/02
     ↓
Private DB — MySQL Primary/Replica
```

**WEB·WAS·DB 모두 Private Subnet에 배치한 것이 실제 프로젝트의 핵심이다.**

---

## 2. VPC·Subnet 정상 구성 검증

AWS 콘솔 → VPC → Your VPCs / Subnets

### 확인 항목

| 항목 | 검증 내용 |
|---|---|
| VPC ID | 모든 Subnet이 동일한 VPC에 속하는가? |
| CIDR | 10.0.0.0/16 범위 안에 있는가? |
| AZ | 의도한 AZ-a, AZ-c에 배치되었는가? |
| State | Available 상태인가? |
| IP 여유 | 사용 가능한 IPv4 주소가 충분한가? |
| Route Table | 올바른 라우팅 테이블이 적용되는가? |

### CIDR 주의사항

- Subnet CIDR은 VPC CIDR 범위 안에 있어야 한다.
- 같은 VPC의 Subnet끼리는 주소 범위가 겹칠 수 없다.
- Subnet 하나는 하나의 AZ에만 속한다.
- AWS /24 Subnet은 IPv4 256개 중 5개를 예약한다.

따라서 /24 Subnet의 최대 할당 가능 IPv4 주소는 251개이다.

## 3. Route Table과 Subnet의 관계

Route Table은 패킷이 목적지로 이동할 경로를 결정한다.

### Public Subnet 라우팅 예시

```text
Destination       Target
10.0.0.0/16       local
0.0.0.0/0         Internet Gateway
```

- local: VPC 내부 통신
- IGW: 인터넷 목적지로 향하는 직접 경로

### Private Subnet 라우팅 예시

```text
Destination       Target
10.0.0.0/16       local
0.0.0.0/0         NAT Gateway
```

- local: VPC 내부 통신
- NAT Gateway: 내부 서버에서 외부로 나가는 통신 지원

Private DB처럼 외부 인터넷 연결이 불필요한 경우에는 local 경로만 사용하는 설계도 가능하다.

**위 라우팅은 원리를 설명하는 예시다. 실제 프로젝트 설정은 AWS 콘솔에서 확인한다.**

### 핵심

1. Subnet에 별도 Route Table을 연결하지 않으면 Main Route Table을 사용한다.
2. 여러 Subnet이 동일한 Route Table을 공유할 수 있다.
3. Public/Private 여부는 Subnet 이름이 아니라 IGW 직접 경로로 구분한다.
4. Private Subnet은 IGW로 향하는 직접 경로를 두지 않는다.

## 4. Private WEB에 ALB가 접근할 수 있는 이유

```text
인터넷
   ↓
Public ALB
   ↓ VPC 내부 통신
Private WEB01/02
```

ALB와 WEB이 같은 VPC 내부 주소를 통해 통신할 수 있기 때문이다.

단, 정상 통신을 위해 다음 조건이 필요하다.

- ALB Target Group에 WEB 서버 등록
- 올바른 포트 및 Health Check
- ALB → WEB Security Group 허용
- WEB 서버의 Apache 정상 실행
- 라우팅 및 NACL 설정 정상

### WEB을 Private에 배치한 이유

- WEB EC2의 직접 인터넷 노출 최소화
- 사용자 요청을 ALB를 통해 수신
- Security Group으로 접근 출발지 제한
- WEB·WAS·DB 계층별 보안 구조 유지

**Private Subnet에 있다는 사실만으로 모든 내부 접근이 차단되는 것은 아니다.**

## 5. 주요 네트워크 장애 대응

### ① Subnet이 잘못된 AZ에 있음

AWS 콘솔 → EC2 → Instances → Networking

확인:
- Subnet ID
- Availability Zone
- Private IPv4 주소

Subnet 이름이 아니라 실제 AZ 값을 확인한다.

### ② Public ALB 생성 또는 인터넷 연결 문제

확인:
- 서로 다른 AZ의 Public Subnet 2개 사용
- 각 Public Subnet의 IGW 경로
- 인터넷 연결형 ALB 설정
- 사용 가능한 IP 주소

### ③ ALB Target이 Unhealthy

AWS 콘솔 → EC2 → Target Groups → Targets

확인:
1. WEB EC2의 Subnet 및 IP
2. Target Group 포트
3. Health Check 경로와 응답 코드
4. Security Group 및 NACL
5. Apache 실행 상태 및 HTTP 응답

Unhealthy가 발생했다고 무조건 Subnet 문제는 아니다.

### ④ Private WAS에서 인터넷 접속 실패

확인:
- Private WAS의 Route Table
- NAT Gateway 연결 경로
- NAT Gateway 상태
- 외부 통신 관련 Security Group·NACL

Private Subnet에서 인터넷 연결이 필요하다면 NAT 등의 경로가 있어야 한다.

### ⑤ VPC 내부 서버 간 통신 실패

확인:
- 출발지·목적지 IP
- 두 서버가 속한 VPC
- Route Table
- Security Group
- NACL
- 대상 서버의 서비스·포트 상태

동일 VPC에 local 경로가 정상이라면 Security Group·NACL·대상 서비스 상태도 우선 점검한다.

## 6. 장애 대응 시 핵심 구분

| 구성 요소 | 역할 |
|---|---|
| VPC | 전체 네트워크 주소 공간 |
| Subnet | IP 범위 및 AZ 배치 |
| Route Table | 패킷 이동 경로 결정 |
| Security Group | EC2·ALB 등의 네트워크 접근 제어 |
| NACL | Subnet 경계의 네트워크 트래픽 제어 |
| Internet Gateway | VPC와 인터넷 연결 |
| NAT Gateway | Private 서버의 외부 방향 통신 지원 |
| ALB | HTTP/HTTPS 요청을 WEB 대상 서버에 분산 |

---

## 7. 반드시 기억할 핵심

1. Marble 프로젝트는 VPC 1개, Subnet 8개, AZ 2개로 구성했다.
2. WEB·WAS·DB 모두 Private Subnet에 배치했다.
3. Public ALB가 Private WEB으로 요청을 전달한다.
4. Subnet은 IP 주소 범위와 AZ 배치를 결정한다.
5. Route Table은 목적지까지의 통신 경로를 결정한다.
6. Security Group은 허용할 네트워크 트래픽을 제어한다.
7. Public/Private는 IGW 직접 경로 유무로 구분한다.
8. 네트워크 장애 시 Subnet·Route Table·SG·NACL·서비스 상태를 구분해 확인한다.

### 반드시 기억할 문장

**Subnet = 서버가 어느 네트워크·AZ에 있는가?**

**Route Table = 패킷이 어디로 이동하는가?**

**Security Group = 해당 통신을 허용하는가?**

### 장애 분석 핵심 순서

**대상 IP·Subnet 확인 → Route Table 확인 → SG·NACL 확인 → 대상 포트·서비스 확인 → 통신 재검증**
