
# A과정 8장 2교시 — Security Group·Bastion 핵심 정리

## 1. Security Group(SG)이란?

Security Group은 EC2, ALB 등의 네트워크 접근을 제어하는 AWS의 가상 방화벽이다.

### 주요 특징

- Inbound: 들어오는 통신 제어
- Outbound: 나가는 통신 제어
- Allow 규칙만 설정 가능 (명시적 Deny 불가)
- Stateful 방식으로 동작
- 하나의 EC2에 여러 SG 적용 가능

### Stateful이란?

허용된 연결의 응답 트래픽을 자동으로 허용하는 방식이다.

예시:

ALB → WEB01:80 (HTTP 요청)
WEB01 → ALB (HTTP 응답)

WEB01이 요청을 허용했다면 해당 연결의 응답은 자동으로 허용된다.

단, WEB01 → WAS01:8080은 별도의 새로운 연결이므로 관련 Inbound/Outbound 규칙을 확인해야 한다.

## 2. Route Table·SG·NACL 차이

| 구분 | 역할 | 특징 |
|---|---|---|
| Route Table | 패킷 이동 경로 결정 | 목적지 기반 |
| Security Group | 리소스의 접근 제어 | Stateful, Allow |
| NACL | Subnet 경계 접근 제어 | Stateless, Allow/Deny |

### 핵심

- Route Table: 어디로 이동하는가?
- Security Group: 이 통신을 허용하는가?
- NACL: Subnet 경계를 통과할 수 있는가?

NACL은 Stateless이므로 요청과 응답 양방향의 규칙을 고려해야 한다.

## 3. Marble 프로젝트 Security Group 구조

### 서비스 요청 흐름

```text
인터넷 사용자
      ↓ HTTP/HTTPS
ALB-SG
      ↓ TCP 80
WEB-SG (Apache)
      ↓ TCP 8080
WAS-SG (Spring Boot)
      ↓ TCP 3306
DB-SG (MySQL)
```

### 대표 Inbound 규칙

| SG | 포트 | Source | 목적 |
|---|---|---|---|
| ALB-SG | 80/443 | 허용된 사용자 대역 | 사용자 요청 |
| WEB-SG | 80 | ALB-SG | HTTP 요청 |
| WAS-SG | 8080 | WEB-SG | 애플리케이션 요청 |
| DB-SG | 3306 | WAS-SG | DB 연결 |
| Bastion-SG | 22 | 관리자 IP/32 | SSH 접속 |
| WEB/WAS/DB-SG | 22 | Bastion-SG | 서버 관리 |

※ 실제 사용 포트와 SG 규칙은 AWS 콘솔에서 확인한다.

※ MySQL Primary → Replica 복제에 필요한 TCP 3306 접근도 실제 복제 방향에 맞게 별도로 확인한다.

### 계층별 SG 분리 이유

1. 서버 역할별 접근 권한 관리
2. 불필요한 포트 개방 방지
3. 서버 간 통신 출발지 제한
4. 장애 발생 시 접근 정책 확인 용이

## 4. SG를 IP 대신 참조하는 이유

예시: WAS-SG Inbound

```text
Protocol: TCP
Port: 8080
Source: WEB-SG
```

WEB01, WEB02의 IP를 각각 등록하지 않고 WEB-SG를 참조할 수 있다.

### 장점

- WEB 서버 추가·교체 시 IP 변경에 유연함
- 여러 서버의 접근 정책 관리가 쉬움
- 서버 역할을 기준으로 접근 제한 가능

주의:

SG 참조는 네트워크 경로를 생성하지 않는다.
Route Table과 서비스 상태도 정상이어야 한다.

## 5. Bastion 서버란?

Bastion은 관리자가 Private 서버에 SSH로 접근할 때 사용하는 경유 서버이다.

### Marble 프로젝트 관리 경로

```text
관리자 PC
    ↓ SSH 22
Public Bastion
    ↓ SSH 22
Private WEB / WAS / DB
```

### Bastion을 사용하는 이유

- Private 서버에 공인 IP를 직접 부여하지 않기 위해
- 서버마다 SSH를 인터넷에 공개하지 않기 위해
- 관리자 접속 경로를 집중 관리하기 위해
- 관리자의 접근 IP와 인증을 제한하기 위해

### Bastion 접속에 필요한 조건

1. Bastion에 접근 가능한 공인 IP 및 인터넷 경로
2. Bastion-SG에서 관리자 IP의 TCP 22 허용
3. Private 서버 SG에서 Bastion-SG의 TCP 22 허용
4. Bastion의 Outbound 통신 허용
5. Private 서버의 SSH 서비스 정상
6. 올바른 SSH 계정 및 개인키

---

## 6. SSH 접속 명령어

### 관리자 PC → Bastion

```bash
ssh -i marble-key.pem ubuntu@BASTION_PUBLIC_IP
```

- ssh: 원격 서버 접속
- -i: SSH 개인키 지정
- ubuntu: Ubuntu EC2 로그인 계정
- BASTION_PUBLIC_IP: Bastion의 실제 공인 IP

### Bastion을 경유한 Private WEB 접속

```bash
ssh -i marble-key.pem \
  -J ubuntu@BASTION_PUBLIC_IP \
  ubuntu@WEB_PRIVATE_IP
```

- -J: SSH 경유 서버(ProxyJump) 지정
- WEB_PRIVATE_IP: Private WEB 서버의 실제 IP

위 명령어는 두 서버가 동일한 개인키로 인증 가능한 경우의 예시다.

서버별 SSH 키가 다르다면 SSH config에서 IdentityFile을 각각 설정할 수 있다.

**개인키는 가능하면 관리자 PC에 보관하고 Bastion에 불필요하게 복사하지 않는다.**

## 7. AWS 콘솔 검증

AWS 콘솔 → EC2 → Security Groups

### ALB-SG
- 실제 Listener 포트가 허용되는가?

### WEB-SG
- ALB-SG → TCP 80 허용
- Bastion-SG → TCP 22 허용

### WAS-SG
- WEB-SG → TCP 8080 허용
- Bastion-SG → TCP 22 허용

### DB-SG
- WAS-SG → TCP 3306 허용
- 필요한 복제 연결 허용
- Bastion 경유 관리 접속 허용 여부

실제 SG ID, 연결된 리소스, Inbound/Outbound 규칙을 함께 확인한다.

## 8. Linux SSH 점검 명령어

### SSH 서비스 상태 확인

```bash
sudo systemctl status ssh
```

- systemctl: systemd 서비스 관리
- status: 서비스 상태 조회
- ssh: Ubuntu SSH 서버 서비스

### SSH 포트 확인

```bash
sudo ss -lntp | grep ':22'
```

- -l: LISTEN 상태 표시
- -n: 주소·포트를 숫자로 표시
- -t: TCP 표시
- -p: 프로세스 표시

TCP 22를 실제로 수신 대기하는지 확인한다.

## 9. 주요 장애 대응

### ① 관리자 PC → Bastion SSH 실패

| 오류 | 우선 확인 |
|---|---|
| Connection timed out | IP, SG, 라우팅, NACL |
| Connection refused | SSH 서비스, 포트, OS 방화벽 |
| Permission denied (publickey) | SSH 계정, 개인키, 인증 설정 |

### ② Bastion → Private WEB SSH 실패

확인 순서:

1. WEB EC2 Running 상태
2. WEB Private IP
3. WEB-SG의 TCP 22 Inbound
4. Bastion Outbound 규칙
5. NACL 및 내부 라우팅
6. WEB SSH 서비스 및 인증 설정

### ③ WEB → WAS 연결 실패

확인 순서:

1. WEB이 사용하는 WAS IP 및 포트
2. WAS-SG의 TCP 8080 Inbound
3. WEB-SG의 Outbound
4. NACL 및 VPC 내부 경로
5. Spring Boot 서비스 실행 상태

검증 예시:

```bash
curl -i --max-time 5 http://WAS_PRIVATE_IP:8080/health
```

- -i: 응답 헤더 출력
- --max-time 5: 최대 실행 시간 5초

실제 WAS 포트와 Health Check 경로에 맞게 사용한다.

## 10. 반드시 기억할 핵심

1. SG는 EC2·ALB 등의 네트워크 접근을 제어한다.
2. Inbound는 들어오는 통신, Outbound는 나가는 통신이다.
3. SG는 Stateful이며 응답 트래픽을 자동 허용한다.
4. 새로운 서버 간 연결은 양쪽 SG 규칙을 확인해야 한다.
5. NACL은 Stateless 방식이다.
6. IP 대신 SG를 참조하면 서버 교체·확장에 유리하다.
7. Bastion은 Private 서버로 SSH 접속하기 위한 경유 서버다.
8. 관리자의 Bastion 접속과 Bastion의 Private 서버 접속은 서로 다른 연결이다.
9. SSH 장애는 네트워크 문제와 인증 문제를 구분해야 한다.
10. Marble 프로젝트는 ALB→WEB→WAS→DB 순서로 필요한 포트만 허용하도록 설계했다.

### 최종 암기 문장

**Route Table = 패킷의 이동 경로**

**Security Group = 서버의 통신 허용 여부**

**Stateful = 허용된 연결의 응답 자동 허용**

**SG 참조 = 서버 IP 대신 보안 그룹으로 접근 제어**

**Bastion = Private 서버에 SSH로 접근하는 경유 서버**

**장애 대응 = 접속 경로 → SG/NACL → 포트·서비스 → 인증 확인**
