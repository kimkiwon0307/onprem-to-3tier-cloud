
# A과정 8장 3교시 — EC2 통신 검증 및 장애 대응

## 1. Marble 프로젝트 통신 구조

### 서비스 요청 경로

```text
인터넷 사용자
      ↓
Public ALB
      ↓ HTTP 80
Private WEB01 / WEB02 (Apache)
      ↓ HTTP 8080
Private WAS01 / WAS02 (Spring Boot)
      ↓ TCP 3306
Private MySQL
```

### 관리자 SSH 접속 경로

```text
관리자 PC
    ↓ SSH 22
Public Bastion
    ↓ SSH 22
Private WEB / WAS / DB
```

**서비스 통신 경로와 관리자 SSH 접속 경로는 서로 다르다.**

---

## 2. EC2 상태 확인

AWS 콘솔 → EC2 → Instances → Status and alarms

| 확인 항목 | 의미 |
|---|---|
| Instance State | EC2 실행 상태 |
| System Status Check | AWS 기반 인프라 상태 |
| Instance Status Check | 인스턴스 내부 상태 |
| EBS Status Check | 연결된 EBS I/O 상태 |

### 핵심

- EC2 Running: 인스턴스가 실행 중
- Status Checks 정상: 기본 시스템 상태 점검 통과
- 애플리케이션 정상: 별도의 서비스·HTTP·DB 검증 필요

**EC2 Running은 Apache·Spring Boot·MySQL의 정상 작동을 보장하지 않는다.**

---

## 3. SSH 접속 검증

### 관리자 PC → Bastion

```bash
ssh -i marble-key.pem -o ConnectTimeout=5 ubuntu@BASTION_PUBLIC_IP
```

- `-i`: SSH 개인키 지정
- `-o`: SSH 옵션 설정
- `ConnectTimeout=5`: 연결 시간 제한

### Bastion 경유 → Private WEB

```bash
ssh -i marble-key.pem \
  -J ubuntu@BASTION_PUBLIC_IP \
  ubuntu@WEB01_PRIVATE_IP
```

- `-J`: SSH 경유 서버(ProxyJump) 지정

※ 같은 키로 양쪽 서버에 인증 가능한 경우의 예시이다. 실제 IP와 키는 기존 프로젝트 값으로 변경한다.

### SSH 오류별 점검

| 오류 | 우선 확인 |
|---|---|
| Connection timed out | IP·Route Table·SG·NACL |
| Connection refused | SSH 서비스·대상 포트·OS 방화벽 |
| Permission denied (publickey) | 로그인 계정·SSH 키·인증 설정 |
| Host key verification failed | 서버 호스트 키 변경 여부 |

**SSH 네트워크 연결 문제와 인증 문제를 구분해야 한다.**

## 4. WEB → WAS 통신 검증

### ① TCP 포트 연결 확인

WEB 서버에서 실행:

```bash
nc -zv -w 3 WAS_PRIVATE_IP 8080
```

| 옵션 | 의미 |
|---|---|
| `-z` | 실제 데이터 전송 없이 포트 연결 확인 |
| `-v` | 상세 정보 출력 |
| `-w 3` | 연결 대기 시간 3초 |

연결 성공은 TCP 8080 접근이 가능하다는 의미이다.

### ② HTTP 응답 확인

```bash
curl -i --max-time 5 http://WAS_PRIVATE_IP:8080/health
```

- `-i`: HTTP 응답 헤더 포함
- `--max-time 5`: 최대 실행 시간 5초
- `/health`: 애플리케이션 상태 확인 경로 예시

### 결과 해석

| 결과 | 의미 및 확인 방향 |
|---|---|
| TCP 연결 실패 | SG·NACL·IP·포트·서비스 확인 |
| TCP 성공 + HTTP 200 | 해당 HTTP 경로 정상 응답 |
| TCP 성공 + HTTP 404 | URL 또는 라우팅 확인 |
| TCP 성공 + HTTP 500 | 애플리케이션 내부 오류 확인 |

**TCP 연결 성공과 애플리케이션 정상 작동은 다르다.**

## 5. Spring Boot 서비스 점검

WAS 서버에서 실행:

```bash
# 서비스 상태
sudo systemctl status marble.service

# 최근 서비스 로그 50줄
sudo journalctl -u marble.service -n 50 --no-pager

# TCP 8080 수신 상태
sudo ss -lntp | grep ':8080'
```

### 핵심

- `systemctl`: 서비스 실행 상태 확인
- `journalctl`: 서비스 로그 확인
- `ss`: 실제 포트 수신 상태 확인

※ `marble.service`는 기존 Marble 환경의 서비스 이름이다. AWS 서버에서 다른 이름을 사용한다면 실제 서비스 이름으로 확인한다.

## 6. WAS → MySQL 연결 검증

### ① TCP 3306 확인

WAS 서버에서 실행:

```bash
nc -zv -w 3 DB_PRIVATE_IP 3306
```

### ② 실제 MySQL 접속 확인

```bash
mysql -h DB_PRIVATE_IP -P 3306 -u APP_USER -p -e "SELECT 1;"
```

| 옵션 | 의미 |
|---|---|
| `-h` | MySQL 서버 주소 |
| `-P` | 포트 번호 |
| `-u` | 접속 계정 |
| `-p` | 비밀번호 입력 |
| `-e` | SQL 명령 실행 |

### 결과에 따른 판단

- TCP 3306 실패 → 네트워크·SG·MySQL 수신 상태 확인
- TCP 성공 + ERROR 1045 → MySQL 인증·계정 권한 확인
- SELECT 1 성공 → 해당 계정으로 DB 연결 및 간단한 SQL 실행 성공

**DB 포트 연결 성공과 MySQL 인증 성공은 서로 다른 검증이다.**

## 7. HTTP 오류별 장애 분석

| 오류 | 우선 확인할 내용 |
|---|---|
| Connection timed out | 네트워크·SG·NACL·응답 지연 |
| Connection refused | 대상 포트·서비스 실행 |
| HTTP 403 | 접근 권한·보안 정책 |
| HTTP 404 | URL·Reverse Proxy 경로 |
| HTTP 500 | 애플리케이션 내부 오류 |
| HTTP 502 | 프록시와 업스트림 통신·응답 |
| HTTP 503 | 서비스 가용성·정상 대상 여부 |
| HTTP 504 | 업스트림 응답 시간 초과 |

오류 코드만으로 원인을 확정하지 않는다.

**ALB·Apache·Spring Boot 중 어느 구성 요소가 오류를 반환했는지 확인해야 한다.**

## 8. ALB Target Group 검증

AWS 콘솔 → EC2 → Target Groups → Targets

| 상태 | 의미 |
|---|---|
| Healthy | Health Check 통과 |
| Unhealthy | Health Check 실패 |
| Initial | 초기 검사 진행 중 |
| Unused | 대상 사용 조건 및 연결 상태 확인 필요 |

### WEB Target Unhealthy 점검

1. WEB EC2 실행 상태
2. Target Group 포트
3. Health Check 경로 및 응답 코드
4. ALB-SG → WEB-SG 접근 허용
5. Apache 서비스 상태
6. Apache 로그

**Target Unhealthy는 반드시 네트워크 장애를 의미하지 않는다.**

## 9. 장애 대응 핵심 절차

```text
① 어느 구간에서 장애가 발생했는가?
              ↓
② 대상 서버 IP·포트 확인
              ↓
③ Route Table·SG·NACL 확인
              ↓
④ TCP 연결 가능 여부 확인 (nc)
              ↓
⑤ 서비스 실행 상태 확인 (systemctl, ss)
              ↓
⑥ HTTP·DB 응답 확인 (curl, mysql)
              ↓
⑦ 로그 확인 (journalctl, 서비스 로그)
              ↓
⑧ 원인 해결 후 동일 경로 재검증
```

증상에 따라 점검 순서는 조정할 수 있다.

### 장애 대응 원칙

- 무작정 서버를 재시작하지 않는다.
- 원인 확인 없이 SG를 0.0.0.0/0으로 개방하지 않는다.
- 정상 구간과 실패 구간을 구분한다.
- 네트워크 연결과 애플리케이션 정상 여부를 따로 확인한다.
- 변경 후에는 동일한 방법으로 정상 복구를 검증한다.

## 10. 주요 명령어 요약

| 명령어 | 확인 대상 |
|---|---|
| `ssh` | 원격 서버 접속 및 인증 |
| `nc -zv` | TCP 포트 연결 |
| `curl -i` | HTTP 응답 |
| `systemctl status` | 서비스 실행 상태 |
| `ss -lntp` | TCP 수신 포트 |
| `journalctl -u` | systemd 서비스 로그 |
| `mysql -h` | MySQL 접속 및 인증 |

---

## 11. 반드시 기억할 핵심

1. EC2 Running과 서비스 정상 상태는 다르다.
2. TCP 연결 성공과 HTTP 정상 응답은 다르다.
3. TCP 3306 연결 성공과 MySQL 인증 성공은 다르다.
4. SSH 오류는 네트워크 문제와 인증 문제로 구분한다.
5. Bastion 접속 성공이 모든 Private 서버 접속 성공을 의미하지 않는다.
6. ALB Target Unhealthy는 SG·포트·Health Check·Apache 등을 확인한다.
7. 서버 장애는 WEB→WAS→DB 구간별로 분석한다.
8. 변경 후 동일한 테스트로 복구 여부를 검증한다.

### 최종 암기 문장

**EC2 Running ≠ 서비스 정상**

**TCP 연결 성공 ≠ 애플리케이션 정상**

**포트 연결 성공 ≠ DB 인증 성공**

**장애 대응 = 실패 구간 파악 → 네트워크 확인 → 서비스 확인 → 로그 분석 → 복구 검증**
