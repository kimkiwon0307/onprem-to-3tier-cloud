
# A과정 9장 2교시 — ALB·WEB 이중화 핵심 정리

## 1. WEB 이중화란?

WEB 서버를 두 대 이상 운영하여 사용자 요청을 분산하고, 한 서버에 장애가 발생해도 다른 서버가 요청을 처리하도록 구성하는 것이다.

### 이중화하는 이유

1. WEB 서버 한 대에 트래픽이 집중되는 것을 방지
2. 단일 WEB 서버 장애로 인한 서비스 중단 위험 감소
3. 서버 확장 및 유지보수에 유리
4. 서로 다른 AZ에 배치하여 가용성 향상

**WEB 서버 두 대를 생성하는 것만으로 이중화가 완성되지는 않는다. ALB 연결과 정상 동작 검증이 필요하다.**

---

## 2. Marble 프로젝트 WEB 이중화 구성

### 네트워크

- VPC: 10.0.0.0/16
- Public ALB: AZ-a / AZ-c
- WEB01: Private Subnet 10.0.11.0/24
- WEB02: Private Subnet 10.0.12.0/24

### 요청 흐름

```text
인터넷 사용자
      ↓
Public ALB
      ↓
Listener
      ↓
WEB Target Group
      ├── WEB01 (Apache, AZ-a)
      └── WEB02 (Apache, AZ-c)
                ↓
       Private WAS 서버
                ↓
           MySQL DB
```

### 설계 이유

- ALB는 외부 HTTP/HTTPS 요청 수신
- WEB01/WEB02는 Private Subnet에서 운영
- 두 WEB 서버는 서로 다른 AZ에 배치
- ALB Health Check로 정상 대상 판단
- Security Group으로 ALB → WEB 접근 제한

---

## 3. ALB 트래픽 분산 알고리즘

### Round Robin

정상 대상 서버에 요청을 순차적으로 분산하는 알고리즘이다.

예시:

```text
요청 1 → WEB01
요청 2 → WEB02
요청 3 → WEB01
요청 4 → WEB02
```

실제 요청이 반드시 위 순서로 관찰되는 것은 아니다.

### 다른 알고리즘

| 알고리즘 | 원리 |
|---|---|
| Round Robin | 순차적으로 요청 분산 |
| Least Outstanding Requests | 처리 중인 요청 수가 적은 대상으로 분산 |
| Weighted Random | 가중치를 고려하여 무작위 분산 |

Target Group의 실제 알고리즘은 AWS 콘솔에서 확인한다.

---

## 4. Cross-zone Load Balancing

ALB 노드가 자신과 다른 AZ에 있는 WEB 서버에도 요청을 전달할 수 있도록 하는 기능이다.

예시:

```text
ALB 노드 (AZ-a)
       ↓
WEB02 (AZ-c)
```

### 장점

- AZ 간 정상 대상 활용
- 요청 분산 유연성 향상
- 특정 AZ에 대상 서버가 적은 상황 대응

단, 실제 동작은 ALB 및 Target Group의 Cross-zone 설정에 따라 달라진다.

---

## 5. WEB 이중화 정상 검증

### ① AWS Target Group 확인

AWS 콘솔 → EC2 → Target Groups → Targets

확인:
- WEB01 등록 여부
- WEB02 등록 여부
- 두 서버의 AZ
- Target Port
- Health Status: Healthy

### ② Apache Access Log 확인

WEB01과 WEB02에서 각각 실행:

```bash
sudo tail -n 30 /var/log/apache2/access.log
```

- tail: 파일 마지막 부분 출력
- -n 30: 마지막 30줄 확인

실제 Apache VirtualHost에서 별도 로그를 사용한다면 해당 경로를 확인한다.

### ③ 외부에서 ALB 요청

```bash
curl -i --max-time 5 http://ALB_DNS_NAME/
```

- -i: HTTP 응답 헤더 표시
- --max-time 5: 최대 실행 시간 5초

여러 요청을 보낸 후 WEB01과 WEB02의 Access Log를 비교한다.

### 주의사항

- HTTP 200 한 번으로 두 서버의 분산 처리를 증명할 수 없다.
- Health Check 요청과 실제 사용자 요청을 구분해야 한다.
- 두 서버의 로그에 테스트 요청이 기록되는지 확인한다.
- 요청 비율이 정확히 50:50일 필요는 없다.
- Stickiness 및 알고리즘 설정이 분산 결과에 영향을 줄 수 있다.

**Healthy 상태 확인과 실제 트래픽 분산 검증은 서로 다른 작업이다.**

## 6. WEB 서버 장애 시 ALB 동작

### 상황 ① 두 서버 모두 정상

```text
ALB
 ├── WEB01: Healthy → 요청 전달
 └── WEB02: Healthy → 요청 전달
```

설정된 로드밸런싱 알고리즘에 따라 요청을 분산한다.

### 상황 ② WEB02 장애

```text
ALB
 ├── WEB01: Healthy   → 요청 전달
 └── WEB02: Unhealthy → 일반적으로 제외
```

ALB는 Health Check 결과에 따라 일반적으로 정상 대상에 요청을 전달한다.

주의:
- 장애 감지에는 시간이 필요하다.
- 기존 요청이 실패할 수 있다.
- 남은 WEB 서버에 충분한 처리 용량이 필요하다.

### 상황 ③ 두 서버 모두 장애

```text
ALB
 ├── WEB01: Unhealthy
 └── WEB02: Unhealthy
```

ALB는 모든 대상이 Unhealthy일 때 Fail-open으로 비정상 대상에도 요청을 전달할 수 있다.

**Fail-open은 서비스 정상 동작을 보장하지 않는다.**

---

## 7. ALB와 Auto Scaling 차이

| 기능 | 역할 |
|---|---|
| ALB | 정상 대상으로 요청 분산 |
| Health Check | 대상 서버 상태 판단 |
| Auto Scaling | 정책에 따라 EC2 수량 관리 및 교체 |
| AMI | 새로운 EC2 생성에 활용 |

**ALB는 장애 WEB 서버를 자동으로 재생성하지 않는다.**

Auto Scaling을 별도로 구현하지 않았다면 자동 서버 복구를 구현했다고 설명하면 안 된다.

## 8. 트래픽이 WEB01에만 전달되는 경우

확인 순서:

1. WEB02가 Target Group에 등록되어 있는가?
2. WEB02가 Healthy인가?
3. WEB02의 AZ가 활성화되어 있는가?
4. Target Group 알고리즘은 무엇인가?
5. Stickiness가 활성화되어 있는가?
6. WEB02의 Apache Access Log 경로가 올바른가?
7. 충분한 테스트 요청을 보냈는가?

WEB02의 로그에 요청이 없다고 해서 무조건 ALB 장애는 아니다.

## 9. Health Check 설계 시 주의사항

Marble 프로젝트에는 다음과 같은 상태 확인 경로가 있다.

- /health: 애플리케이션 응답 확인
- /health/db: 애플리케이션에서 DB 연결 및 검사 확인

단, 실제 검사 범위는 구현된 코드에 따라 달라진다.

### ALB Health Check 주의

ALB → WEB 구조에서는 Health Check URL이 Apache WEB 서버를 통해 실제로 응답할 수 있어야 한다.

ALB의 Health Check를 /health/db로 설정한다면 Apache → WAS → DB까지 의존하게 될 수 있다.

이 경우 DB 장애가 WEB01/WEB02 모두의 Health Check 실패로 이어질 수 있다.

따라서 목적에 따라 다음을 구분한다.

- ALB Health Check: 트래픽 수신 가능 여부 판단
- /health/db: WAS와 DB 연결 상태를 확인하는 심층 점검

실제 Target Group에 설정한 Health Check 경로는 AWS 콘솔에서 확인한다.

## 10. AWS 콘솔 점검 항목

### ALB

EC2 → Load Balancers

- State: Active
- Scheme: Internet-facing
- Public Subnet 2개
- AZ 구성
- Listener 및 Security Group

### Target Group

EC2 → Target Groups

- WEB01/WEB02 등록 여부
- Healthy/Unhealthy 상태
- Protocol 및 Port
- Health Check 경로
- Load Balancing Algorithm
- Stickiness
- Cross-zone 설정

---

## 11. 반드시 기억할 핵심

1. WEB 이중화는 여러 서버를 이용한 요청 분산 및 장애 대응 구조이다.
2. Marble 프로젝트는 서로 다른 AZ의 Private WEB01/WEB02를 사용한다.
3. ALB는 Target Group의 설정에 따라 요청을 분산한다.
4. Round Robin은 순차적 요청 분산 방식이다.
5. Cross-zone은 다른 AZ의 대상에도 요청을 전달할 수 있도록 한다.
6. Healthy는 Health Check 조건을 통과했다는 의미이다.
7. 두 서버 모두 Healthy여도 실제 트래픽 분산은 별도로 검증해야 한다.
8. WEB 장애 시 ALB는 일반적으로 정상 대상으로 요청을 전달한다.
9. 모든 대상이 Unhealthy이면 Fail-open할 수 있다.
10. ALB는 장애 EC2를 자동으로 재생성하지 않는다.

### 최종 암기 문장

**WEB 이중화 = 여러 WEB 서버를 이용한 요청 분산과 장애 대응**

**ALB = 정상 대상에 HTTP/HTTPS 요청 분산**

**Round Robin = 순차적 요청 분산**

**Cross-zone = AZ를 넘어 다른 대상에도 요청 전달**

**Healthy ≠ 실제 트래픽 분산 검증 완료**

**Fail-open = 모든 대상이 비정상일 때도 요청이 전달될 수 있음**

**이중화 검증 = Target Healthy 확인 + 양쪽 WEB Access Log 확인 + 실제 HTTP 요청 검증**
