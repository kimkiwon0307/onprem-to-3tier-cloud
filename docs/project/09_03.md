# 9장 3교시 — ALB 장애 대응 (Unhealthy / 502 / 503 / 504)

## 1. ALB 장애 대응의 핵심

ALB(Application Load Balancer)는 Target Group에 등록된 WEB 서버의 상태를 Health Check로 확인하고 요청을 분산한다.

Marble 프로젝트의 요청 흐름:

```text
Client
   |
   v
Public ALB
   |
   v
Target Group
   |
   +---- WEB01 (Apache :80)
   |
   +---- WEB02 (Apache :80)
```

- WEB01, WEB02 모두 Healthy → 정상적인 요청 분산
- WEB01 Healthy, WEB02 Unhealthy → 일반적으로 WEB01로 요청 전달
- WEB01, WEB02 모두 Unhealthy → ALB가 Fail-open 방식으로 Unhealthy 대상에도 요청을 전달할 수 있음
- 등록된 대상이 없거나 모든 대상이 Unused → ALB 503 발생 가능

**핵심:** Unhealthy와 HTTP 503은 같은 의미가 아니다.

## 2. Health Check 동작 원리

ALB는 설정된 경로와 포트로 주기적으로 요청을 보내고 응답 코드 및 응답 시간을 검사한다.

예시 설정:

| 설정 | 예시 |
|---|---|
| Protocol | HTTP |
| Port | 80 |
| Path | `/` |
| Success Code | 200 |
| Timeout | 5초 |
| Healthy Threshold | 연속 5회 성공 |
| Unhealthy Threshold | 연속 2회 실패 |

※ 위 값은 학습 예시이며, 실제 AWS Target Group의 설정값은 콘솔에서 확인한다.

동작 과정:

1. ALB가 WEB 서버로 HTTP 요청 전송
2. WEB 서버가 HTTP 응답 반환
3. 성공 코드와 응답 시간 확인
4. 연속 성공·실패 횟수에 따라 Healthy/Unhealthy 판정

예를 들어 성공 코드가 200인데 WEB 서버가 404를 반환하면 Health Check에 실패한다.

## 3. 주요 Reason Code

| Reason Code | 의미 | 확인 항목 |
|---|---|---|
| `Target.ResponseCodeMismatch` | 예상 HTTP 응답 코드와 다름 | Health Check Path, Apache 응답 코드 |
| `Target.Timeout` | Health Check 시간 초과 | 네트워크, SG, 서버 응답 지연 |
| `Target.FailedHealthChecks` | 연결 오류 또는 잘못된 응답 | Apache 서비스, 포트, 로그 |
| `Target.NotInUse` | Target Group 또는 AZ 설정 문제 | Listener 규칙, 활성화된 AZ |
| `Target.InvalidState` | 대상 인스턴스 상태가 유효하지 않음 | EC2 실행 상태 |

**Reason Code를 먼저 확인하면 무작정 서버를 재시작하지 않고 장애 원인을 좁힐 수 있다.**

## 4. HTTP 502 / 503 / 504 차이

| 상태 코드 | 의미 | ALB가 직접 반환하는 대표 상황 |
|---|---|---|
| 502 Bad Gateway | 유효한 백엔드 응답을 받지 못함 | 연결 재설정, 잘못된 HTTP 응답 |
| 503 Service Unavailable | 요청을 처리할 대상이 없음 | Target 미등록, 모든 Target이 Unused |
| 504 Gateway Timeout | 제한 시간 내 응답을 받지 못함 | 백엔드 연결 또는 응답 시간 초과 |

### HTTP 502

ALB가 WEB 서버로 요청을 전달하는 과정에서 연결이 비정상 종료되거나 잘못된 응답을 받는 상황.

확인 항목:
- Apache 프로세스 및 서비스 상태
- Apache Error Log
- ALB와 WEB 간 연결 문제
- 비정상적인 HTTP 응답 여부

### HTTP 503

ALB가 요청을 처리할 사용 가능한 대상을 찾지 못하는 상황.

확인 항목:
- Target Group에 서버가 등록되어 있는지
- 대상의 상태가 Unused인지
- Listener가 올바른 Target Group을 참조하는지
- ALB에 필요한 AZ가 활성화되어 있는지

### HTTP 504

ALB가 WEB 서버에 연결하지 못하거나, 연결 후 제한 시간 내 응답을 받지 못하는 상황.

확인 항목:
- Security Group 및 NACL
- 서버 CPU·메모리 사용량
- Apache 응답 지연
- WAS 또는 DB 처리 지연
- ALB Idle Timeout 설정

※ 502·503·504는 ALB뿐 아니라 백엔드에서도 반환할 수 있으므로 오류 발생 주체를 구분해야 한다.

## 5. AWS 콘솔 장애 확인

경로:

`EC2 → Target Groups → 대상 그룹 선택 → Targets`

확인할 내용:

1. WEB01/WEB02 등록 상태
2. Health Status
3. Status Details 및 Reason Code
4. Health Check Path와 Success Codes
5. Listener 및 Target Group 연결 상태

## 6. Linux 장애 확인 명령어

### Apache 서비스 확인

```bash
sudo systemctl status apache2
```

### HTTP 응답 확인

```bash
curl -i http://127.0.0.1/
```

실제 Health Check 경로가 `/health`라면 해당 경로로 검사해야 한다.

### Apache 오류 로그

```bash
sudo tail -n 50 /var/log/apache2/error.log
```

### Apache 접근 로그

```bash
sudo tail -n 50 /var/log/apache2/access.log
```

### 80번 포트 LISTEN 확인

```bash
sudo ss -lntp | grep ':80 '
```

### 서버 자원 확인

```bash
uptime
free -h
df -h
```

## 7. 장애 대응 순서

```text
사용자 HTTP 오류 발생
        |
        v
1. ALB Listener 확인
        |
        v
2. Target Group 상태 확인
        |
        v
3. Reason Code 분석
        |
        v
4. EC2 / Apache 상태 확인
        |
        v
5. Security Group / NACL 확인
        |
        v
6. Apache 로그 및 응답 확인
        |
        v
7. 필요 시 WAS / DB까지 추적
        |
        v
8. 원인 해결 후 Health Check 재검증
```

장애 대응에서는 서비스 재시작보다 **오류가 발생한 구간을 먼저 특정하는 것이 중요하다.**

## 8. 핵심 요약

- **ALB:** 요청 분산 및 Target 상태 확인
- **Health Check:** 서버가 설정된 조건에 맞게 응답하는지 검사
- **Unhealthy:** Health Check 실패 상태
- **502:** 백엔드 연결 또는 응답 이상
- **503:** 서비스 요청을 받을 대상이 없는 경우
- **504:** 백엔드 연결 또는 응답 시간 초과
- **Reason Code:** Target 상태 이상 원인을 분류하는 단서
- **장애 대응:** ALB → Target Group → EC2 → Apache → WAS/DB 순서로 점검

### 운영 관점에서 기억할 점

**Healthy는 전체 애플리케이션의 정상 동작을 보장하지 않는다.**

예를 들어 Apache의 `/` 경로가 정상 응답하더라도 실제 WAS나 DB에 장애가 발생할 수 있다.

따라서 Health Check 상태와 실제 서비스 요청 결과를 함께 확인해야 한다.

또한 장애가 발생하면 무조건 서비스를 재시작하지 않고, AWS 콘솔의 Reason Code와 Linux 로그를 바탕으로 원인을 확인한 뒤 조치한다.
