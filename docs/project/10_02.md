# 10장 2교시 — WAS 부하 분산 검증 및 장애 대응

## 1. WAS 이중화 구조

Marble 프로젝트에서는 Apache Reverse Proxy를 이용해 WAS01/WAS02에 요청을 분산한다.

```text
Client
   |
   v
Public ALB
   |
   +── WEB01 (Apache :80)
   |
   +── WEB02 (Apache :80)
          |
          v
   Apache Balancer
   (marblecluster)
          |
     +----+----+
     |         |
     v         v
   WAS01     WAS02
 10.0.21.126 10.0.22.9
   :8080      :8080
```

- **ALB:** WEB01/WEB02 사이에서 요청 분산
- **Apache Balancer:** WAS01/WAS02 사이에서 요청 분산
- **Spring Boot:** 애플리케이션 요청 처리

## 2. WAS 부하 분산 설정

실제 `marble.conf` 설정:

```apache
<Proxy "balancer://marblecluster">
    BalancerMember "http://10.0.21.126:8080"
    BalancerMember "http://10.0.22.9:8080"

    ProxySet lbmethod=byrequests
</Proxy>

ProxyPass "/" "balancer://marblecluster/"
ProxyPassReverse "/" "balancer://marblecluster/"
```

### byrequests 동작 원리

- 가중 요청 수를 기준으로 WAS에 요청을 분산한다.
- WAS01/WAS02의 기본 가중치가 같으므로 요청을 비슷한 비율로 분산한다.
- 반드시 WAS01 → WAS02 순서로 번갈아 요청을 보내는 것은 아니다.
- 각 WEB 서버의 Apache는 독립적으로 WAS를 선택한다.

## 3. WAS 부하 분산 검증

Marble 프로젝트에서는 `marble_backend.log`를 이용해 요청을 처리하도록 선택된 WAS를 확인할 수 있다.

실제 로그 설정:

```apache
LogFormat "%t \"%r\" %>s backend=%{BALANCER_WORKER_NAME}e" marble_backend
CustomLog /var/log/apache2/marble_backend.log marble_backend
```

### 로그 확인

```bash
sudo tail -n 20 /var/log/apache2/marble_backend.log
```

로그 출력 예시:

```text
"GET / HTTP/1.1" 200 backend=http://10.0.21.126:8080
"GET / HTTP/1.1" 200 backend=http://10.0.22.9:8080
```

- `backend=10.0.21.126:8080` → WAS01 선택
- `backend=10.0.22.9:8080` → WAS02 선택

※ 위 로그는 실제 실행 결과가 아닌 예시이다.

### 요청 분산 테스트

WEB 서버에서 실행:

```bash
for i in {1..6}; do
    curl -s -o /dev/null \
      --max-time 5 \
      -H "Host: marble.test" \
      -w "요청 $i: HTTP %{http_code}\n" \
      http://127.0.0.1/
done
```

테스트 후 `marble_backend.log`에서 WAS01/WAS02가 선택되었는지 확인한다.

## 4. WAS 장애 발생 시 동작

### WAS01 연결 장애

```text
Apache
   |
   +── WAS01 (연결 실패)
   |
   +── WAS02 (정상)
```

1. Apache가 WAS01로 요청 전달을 시도한다.
2. WAS01 연결이 실패하면 해당 Worker가 오류 상태로 표시될 수 있다.
3. Apache가 정상 Worker인 WAS02로 요청을 전달할 수 있다.
4. 일정 시간이 지나면 WAS01에 대한 재사용을 시도할 수 있다.

단, 모든 요청이 자동으로 재시도되거나 성공하는 것은 아니다.

### WAS01에서 HTTP 500 발생

- WAS01 프로세스는 실행 중이지만 애플리케이션 내부 오류가 발생한 상황이다.
- 현재 설정에서는 HTTP 500만으로 WAS01이 자동 제외되지 않는다.
- Apache의 연결 장애 감지와 애플리케이션 오류 감지는 구분해야 한다.

**핵심: WAS 이중화가 모든 애플리케이션 장애의 자동 복구를 보장하지는 않는다.**

## 5. Apache Health Check

- ALB는 Target Group에 설정된 Health Check를 수행한다.
- Apache도 `mod_proxy_hcheck` 등을 통해 능동적인 Health Check를 구성할 수 있다.
- 현재 공유된 `marble.conf`에는 별도의 능동 Health Check 설정이 없다.
- 다른 설정 파일에도 관련 설정이 없다면 주로 실제 요청 처리 과정에서 발생한 연결 오류 등을 기반으로 장애를 감지한다.

## 6. 장애 대응 및 검증 명령어

### Apache 실행 상태 확인

```bash
sudo systemctl status apache2
```

### WEB → WAS01 직접 통신 확인

```bash
curl -i --max-time 5 http://10.0.21.126:8080/health
```

### WEB → WAS02 직접 통신 확인

```bash
curl -i --max-time 5 http://10.0.22.9:8080/health
```

※ `/health`는 실제 애플리케이션에 구현되어 있어야 한다.

### Apache Error Log 확인

```bash
sudo tail -n 50 /var/log/apache2/marble_error.log
```

### WAS 분산 로그 확인

```bash
sudo tail -n 50 /var/log/apache2/marble_backend.log
```

### 장애 원인별 확인 항목

| 장애 현상 | 우선 확인 |
|---|---|
| WAS01만 연결 실패 | Spring Boot 프로세스, 포트, 네트워크 |
| 두 WAS 모두 연결 실패 | 보안 그룹, Apache 설정, 공통 장애 |
| HTTP 500 발생 | WAS 애플리케이션 로그, DB 연결 |
| 한 WAS로만 분산 | Worker 상태, 가중치, Balancer 설정 |
| Apache를 거칠 때만 실패 | ProxyPass, Apache Error Log |
| WAS 변경 시 인증 오류 | 세션 공유 및 Spring Security |

## 7. WAS 이중화와 세션 공유의 차이

| 구분 | 역할 |
|---|---|
| Apache Balancer | 어느 WAS로 요청을 전달할지 결정 |
| Spring Session JDBC | 여러 WAS가 동일한 세션 데이터를 공유 |

Marble 프로젝트에서는 Spring Session JDBC와 MySQL을 이용해 WAS 간 세션을 공유하도록 구성했다.

따라서 요청이 WAS01에서 WAS02로 변경되더라도 동일한 세션 데이터를 사용할 수 있다.

세션 공유의 실제 설정과 HTTP 403 장애 원인은 13장에서 학습한다.

## 8. 핵심 요약

1. **byrequests:** 가중 요청 수 기준으로 WAS01/WAS02에 요청 분산
2. **marble_backend.log:** 어떤 WAS가 선택되었는지 확인
3. **연결 장애:** 다른 정상 WAS로 요청이 전달될 수 있음
4. **HTTP 500:** 현재 설정에서 WAS 자동 제외 조건이 아님
5. **Health Check:** Apache의 능동 Health Check는 별도 설정 필요
6. **장애 대응:** Apache 상태 → WAS 연결 → 프록시 로그 → 애플리케이션 로그 순서로 점검
7. **세션 공유:** WAS 이중화와 별개의 기능으로 Spring Session JDBC 사용

**최종 핵심:** Apache Balancer는 WAS01/WAS02의 요청 분산과 일부 연결 장애에 대한 우회 처리를 담당한다. 하지만 모든 장애를 자동 복구하지는 않으므로 로그와 WAS 상태를 함께 확인해야 한다.
