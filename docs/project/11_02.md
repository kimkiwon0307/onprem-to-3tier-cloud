# 11장 2교시 — MySQL Primary/Replica 구축 및 운영 이해

## 1. 프로젝트 구성 및 목적

### Marble 실제 DB 아키텍처

```text
WAS01 / WAS02
      |
      v
DB01 - Primary
10.0.31.42:3306
      |
      | GTID 기반 비동기 복제
      v
DB02 - Replica
10.0.32.160:3306
```

- **Primary:** 데이터 읽기·쓰기와 변경 이벤트 기록
- **Replica:** Primary의 변경 이벤트를 전달받아 데이터 복제
- **GTID:** 복제 트랜잭션 고유 식별 및 위치 추적
- **비동기 복제:** Primary가 Replica의 적용 완료를 기다리지 않고 Commit 가능

### 복제 원리

```text
Primary에서 INSERT/UPDATE/DELETE
              |
              v
          Binary Log
              |
              v
      Replica I/O Receiver
              |
              v
           Relay Log
              |
              v
          SQL Applier
              |
              v
       Replica 데이터 반영
```

**목표:** MySQL 서버 두 대로 Primary/Replica 복제를 구성하고, 변경 데이터가 실제로 동기화되는지 확인한다.

## 2. 구축 순서

※ 아래 설치 및 변경 명령어는 신규 Ubuntu 24.04 실습 서버를 대상으로 한다. 기존 Marble DB01/DB02에는 그대로 재실행하지 않는다.

실습용 IP 예시:

- Primary: `192.168.111.151`
- Replica: `192.168.111.152`

### 1단계. 서버 및 네트워크 준비

DB01과 DB02에서 각각 IP를 확인한다.

```bash
ip -4 addr
```

MySQL은 기본적으로 TCP 3306 포트를 사용한다.

- Replica → Primary TCP 3306 접근 허용
- AWS 환경에서는 Security Group으로 접근 범위 제한
- Ubuntu UFW가 활성화된 경우 방화벽 규칙 확인

**이유:** Replica가 Primary에 접속하여 Binary Log 이벤트를 가져와야 하기 때문이다.

### 2단계. MySQL 설치

두 서버에서 실행한다.

```bash
sudo apt update
sudo apt install -y mysql-server
```

MySQL 서비스 상태 확인:

```bash
sudo systemctl status mysql
```

포트 확인:

```bash
sudo ss -lntp | grep ':3306 '
```

MySQL 접속 및 버전 확인:

```bash
sudo mysql
```

```sql
SELECT VERSION();
```

- `apt update`: 패키지 목록 갱신
- `apt install`: MySQL 설치
- `systemctl status`: 서비스 상태 확인
- `ss -lntp`: TCP 리스닝 포트 확인
- `sudo mysql`: 로컬 관리자 인증 방식이 허용하는 경우 MySQL 접속

### 3단계. DB01 Primary 설정

설정 파일을 생성한다.

```bash
sudo nano /etc/mysql/mysql.conf.d/99-replication.cnf
```

설정 예시:

```ini
[mysqld]

server-id = 101
bind-address = 192.168.111.151

log_bin = mysql-bin
binlog_format = ROW

gtid_mode = ON
enforce_gtid_consistency = ON
```

| 설정 | 역할 |
|---|---|
| `server-id` | 복제 서버를 구분하는 고유 ID |
| `bind-address` | MySQL이 TCP 연결을 수신할 IP |
| `log_bin` | Binary Log 활성화 및 파일 이름 |
| `binlog_format=ROW` | 변경된 행 기반으로 이벤트 기록 |
| `gtid_mode=ON` | GTID 기반 트랜잭션 식별 활성화 |
| `enforce_gtid_consistency=ON` | GTID와 호환되는 트랜잭션 사용 강제 |

설정 적용:

```bash
sudo systemctl restart mysql
```

적용 결과 확인:

```sql
SHOW VARIABLES LIKE 'server_id';
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'gtid_mode';
SHOW VARIABLES LIKE 'binlog_format';
```

**핵심:** Primary는 변경 데이터를 Binary Log에 기록할 수 있어야 한다.

### 4단계. DB02 Replica 설정

DB02에서 설정 파일을 생성한다.

```bash
sudo nano /etc/mysql/mysql.conf.d/99-replication.cnf
```

```ini
[mysqld]

server-id = 102
bind-address = 192.168.111.152

log_bin = mysql-bin
relay_log = mysql-relay-bin
log_replica_updates = ON

binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON
```

추가로 알아야 할 설정:

| 설정 | 역할 |
|---|---|
| `relay_log` | Primary에서 수신한 이벤트 저장 |
| `log_replica_updates` | 복제된 변경 사항을 Replica의 Binary Log에도 기록 |
| `server-id=102` | Primary와 서로 다른 서버 ID 사용 |

설정 적용:

```bash
sudo systemctl restart mysql
```

**핵심:** Replica는 수신한 이벤트를 Relay Log에 기록하고 SQL Applier를 통해 실제 데이터에 반영한다.

### 5단계. Primary 복제 계정 생성

DB01의 MySQL에서 실행한다.

```sql
CREATE USER 'repl'@'192.168.111.152'
IDENTIFIED BY '강력한_실습용_비밀번호'
REQUIRE SSL;
```

복제 권한 부여:

```sql
GRANT REPLICATION SLAVE ON *.*
TO 'repl'@'192.168.111.152';
```

권한 확인:

```sql
SHOW GRANTS FOR 'repl'@'192.168.111.152';
```

- `repl`: 복제 전용 계정
- `@'192.168.111.152'`: 접속 가능한 Replica 주소
- `REPLICATION SLAVE`: 복제 이벤트를 읽을 수 있는 권한
- `REQUIRE SSL`: TLS 암호화 연결 필수

**이유:** root 계정 대신 필요한 권한만 가진 전용 계정을 사용하여 보안을 강화한다.

### 6단계. Primary 초기 데이터 생성 및 백업

DB01에서 실습 DB 생성:

```sql
CREATE DATABASE marble_lab;

USE marble_lab;

CREATE TABLE products (
    id INT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
) ENGINE=InnoDB;

INSERT INTO products (name)
VALUES ('keyboard'), ('mouse');
```

MySQL을 종료한 후 Linux에서 백업:

```bash
umask 077

sudo mysqldump \
  --single-transaction \
  --quick \
  --set-gtid-purged=ON \
  --databases marble_lab \
  > ~/marble_lab.sql
```

| 옵션 | 의미 |
|---|---|
| `--single-transaction` | InnoDB 데이터의 일관된 스냅샷 백업 |
| `--quick` | 행을 순차적으로 읽어 메모리 사용량 절약 |
| `--set-gtid-purged=ON` | 복원 대상에 실행 완료 GTID 정보 전달 |
| `--databases` | 백업할 데이터베이스 지정 |

**주의:** 이 백업 예시는 전용 실습 Primary와 비어 있는 신규 Replica를 전제로 한다. 일부 DB만 백업하더라도 `gtid_purged`에는 Primary에서 실행된 다른 DB의 GTID가 포함될 수 있다.

실제 운영에서는 전체 복제 범위와 GTID 정합성을 확인하고 일관된 백업 방법을 선택해야 한다.

### 7단계. Replica 초기 데이터 복원

DB01에서 백업 파일을 DB02로 전달한다.

```bash
scp ~/marble_lab.sql \
  ubuntu@192.168.111.152:~/
```

DB02에서 복원:

```bash
sudo mysql < ~/marble_lab.sql
```

데이터 확인:

```sql
USE marble_lab;
SELECT * FROM products;
```

초기 복원이 끝난 후 Replica 설정에 추가:

```ini
read_only = ON
super_read_only = ON
```

MySQL 재시작:

```bash
sudo systemctl restart mysql
```

- `read_only`: 일반적인 쓰기 작업 제한
- `super_read_only`: 관리자 수준의 일반적인 쓰기 작업까지 제한
- 복제 SQL Applier는 해당 설정 아래에서도 복제 이벤트 적용 가능

**핵심:** 복제 연결 전에 초기 데이터와 GTID 이력을 맞추어야 한다.

### 8단계. Primary 연결 설정

DB02의 MySQL에서 실행한다.

```sql
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.111.151',
    SOURCE_PORT = 3306,
    SOURCE_USER = 'repl',
    SOURCE_PASSWORD = '실제_복제계정_비밀번호',
    SOURCE_AUTO_POSITION = 1,
    SOURCE_SSL = 1;
```

| 옵션 | 역할 |
|---|---|
| `SOURCE_HOST` | Primary IP |
| `SOURCE_PORT` | Primary MySQL 포트 |
| `SOURCE_USER` | 복제 계정 |
| `SOURCE_PASSWORD` | 복제 계정 비밀번호 |
| `SOURCE_AUTO_POSITION=1` | GTID 기반 복제 위치 자동 추적 |
| `SOURCE_SSL=1` | TLS 암호화 연결 사용 |

**핵심:** GTID 기반 자동 위치 추적을 사용하면 Binary Log 파일명과 Position을 직접 관리할 필요가 줄어든다.

### 9단계. 복제 시작 및 상태 확인

DB02에서 실행한다.

```sql
START REPLICA;
```

복제 상태 확인:

```sql
SHOW REPLICA STATUS\G
```

| 항목 | 정상 상태 예시 |
|---|---|
| `Replica_IO_Running` | Yes |
| `Replica_SQL_Running` | Yes |
| `Seconds_Behind_Source` | 일반적으로 0 또는 낮은 값 |
| `Last_IO_Error` | 오류 없음 |
| `Last_SQL_Error` | 오류 없음 |
| `Auto_Position` | 1 |

- IO Receiver: Primary에서 이벤트 수신
- SQL Applier: Relay Log 이벤트 적용
- `Seconds_Behind_Source`: 복제 지연 추정 지표

※ IO/SQL이 모두 Yes이더라도 데이터의 완전한 일치를 보장하지는 않는다.

### 10단계. 실제 데이터 복제 검증

DB01에서 실행:

```sql
USE marble_lab;

INSERT INTO products (name)
VALUES ('monitor');
```

DB02에서 확인:

```sql
SELECT * FROM marble_lab.products;
```

정상 복제 결과:

```text
1 | keyboard
2 | mouse
3 | monitor
```

GTID 확인:

```sql
SELECT @@GLOBAL.gtid_executed;
```

**검증 성공:** Primary에서 입력한 데이터가 Replica에도 반영된다.

# 3. 추가 질문 정리

## Q1. SSL 인증서를 직접 만들지 않았는데 복제가 되는 이유는?

MySQL은 TLS를 지원하며, 서버 초기화 또는 시작 과정에서 자체 서명 인증서를 자동 생성할 수 있다.

대표적인 파일:

```text
ca.pem
server-cert.pem
server-key.pem
```

따라서 인증서를 직접 생성하지 않았더라도 TLS 통신이 가능할 수 있다.

### 복제에서 SSL 관련 설정

| 설정 | 의미 |
|---|---|
| `SOURCE_SSL=0` | 복제 연결에 TLS를 사용하지 않음 |
| `SOURCE_SSL=1` | 복제 연결에 TLS 사용 |
| `REQUIRE SSL` | 해당 계정에 암호화 연결 필수 |
| `SOURCE_SSL_CA` | 신뢰할 CA 인증서 지정 |
| `SOURCE_SSL_VERIFY_SERVER_CERT=1` | 서버 인증서의 호스트 신원 검증 활성화 |

- TLS 없이도 계정과 서버 설정이 허용하면 복제 가능
- TLS 사용과 서버 인증서 신원 검증은 별개
- 운영 환경에서는 CA 신뢰 및 서버 신원 검증까지 구성하는 것이 바람직함

MySQL TLS 지원 여부 확인:

```sql
SHOW VARIABLES LIKE 'have_ssl';
```

Replica의 TLS 복제 설정 확인:

```sql
SHOW REPLICA STATUS\G
```

여기서 `Source_SSL_Allowed`는 TLS 허용 설정을 나타내며, 이것만으로 실제 연결의 암호화 여부를 완전히 검증했다고 판단해서는 안 된다.

**핵심:** SSL은 복제 동작 자체가 아니라 복제 통신을 암호화하기 위한 기술이다.

## Q2. 이번 구축 과정은 실무에서도 일반적인가?

**기본 구축 순서는 실제 실무에서 사용되는 직접 구성 방식과 같다.**

```text
서버 준비
   ↓
MySQL 설치
   ↓
Primary Binary Log 설정
   ↓
Replica 설정
   ↓
복제 계정 생성
   ↓
초기 데이터 일치
   ↓
복제 연결 설정
   ↓
복제 시작
   ↓
상태 및 데이터 검증
```

하지만 실제 운영 환경에서는 다음 요소가 추가된다.

| 운영 항목 | 필요한 이유 |
|---|---|
| TLS 인증서 검증 | 안전한 DB 간 통신 |
| 초기 데이터 정합성 | 잘못된 복제 시작 방지 |
| Binary Log 보관 정책 | 디스크 공간 및 복제 재연결 관리 |
| 복제 지연 모니터링 | Replica 데이터 반영 지연 탐지 |
| 정기 백업 및 복구 테스트 | 데이터 손상·삭제에 대비 |
| Failover 절차 | Primary 장애 시 복구 |
| 알림 시스템 | 복제 중단 및 장애 조기 발견 |

**핵심:** 현재 배운 것은 실무의 기본 구축 절차이며, 운영 환경에서는 안정성·보안·복구 기능이 추가된다.

## Q3. 현재 Marble 프로젝트에서 수동 Failover가 가능한가?

**수동 Failover를 수행하기 위한 기본 인프라는 구성되어 있다.**

| 항목 | 상태 |
|---|---|
| Primary DB01 | 구축 |
| Replica DB02 | 구축 |
| GTID 기반 비동기 복제 | 구성 |
| Binary Log / Relay Log | 구성 |
| 복제 데이터 검증 | 구축 당시 진행 |
| Replica Primary 승격 | 미검증 |
| WAS DB 연결 대상 전환 | 미검증 |
| 전체 수동 Failover | 미검증 |

### 수동 Failover 절차

```text
DB01 Primary 장애 발생
          |
          v
1. 기존 Primary 격리
          |
          v
2. Replica 복제 상태 및
   미적용 데이터 확인
          |
          v
3. DB02를 새로운 Primary로 승격
          |
          v
4. WAS01/02의 DB 연결 변경
          |
          v
5. 애플리케이션 읽기·쓰기 검증
          |
          v
6. 기존 DB01 복구 및 재편입
```

주의 사항:

- DB01과 DB02가 동시에 쓰기 가능한 Primary로 동작하면 데이터 충돌 위험이 있다.
- 비동기 복제에서는 마지막 트랜잭션이 Replica에 반영되지 않았을 수 있다.
- 실제 Failover를 수행하기 전에 데이터와 서비스 영향 범위를 확인해야 한다.

**핵심:** 수동 Failover가 가능한 기본 구조와 실제 검증 완료된 수동 Failover는 구분해야 한다.

## Q4. 자동 Failover는 어려운가?

자동 Failover는 단순한 복제보다 추가적인 기술이 필요하다.

자동 Failover는 다음을 수행해야 한다.

1. Primary 장애 감지
2. 장애 서버 격리
3. 새로운 Primary 선출
4. Replica 승격
5. 애플리케이션 연결 대상 전환
6. 기존 Primary 복구 시 데이터 충돌 방지

### 구현 방법

| 방식 | 난이도 |
|---|---|
| 수동 Failover | 중간 |
| 직접 작성한 자동 전환 스크립트 | 높음 |
| MySQL InnoDB Cluster + Router | 높음 |

MySQL InnoDB Cluster는 Group Replication과 Router를 이용한 고가용성 구성을 지원한다. 일반적으로 한 노드 장애를 견디기 위해 3개의 MySQL 인스턴스를 구성한다.

**현재 권장 학습 방향:** 수동 Failover와 복제 장애 대응을 먼저 학습하고, 자동 Failover는 별도 고가용성 실습에서 진행한다.

# 4. 다음 AWS 프로젝트에 적용하면?

EC2에 MySQL을 직접 구축한 경험은 AWS 관리형 서비스를 이해하는 데 도움이 된다.

| 항목 | 현재 직접 구축 | AWS 관리형 서비스 |
|---|---|---|
| DB 설치 | EC2에 MySQL 설치 | Amazon RDS |
| 데이터 복제 | GTID/Binary Log 직접 관리 | RDS Read Replica |
| 자동 장애 전환 | 별도 구축 필요 | RDS Multi-AZ |
| 자동 백업 | 직접 구축 필요 | RDS 자동 백업 |
| 모니터링 | 직접 수집 및 분석 | CloudWatch 활용 |

### RDS Read Replica와 Multi-AZ 차이

**RDS Read Replica**
- 읽기 부하 분산에 활용
- 일반적으로 비동기 복제
- 일반적인 Read Replica는 자동 Primary 승격 기능이 아님

**RDS Multi-AZ DB 인스턴스**
- 고가용성 목적
- 동기식 Standby 유지
- 장애 발생 시 AWS가 자동 Failover 수행
- 일반적인 Standby는 읽기 분산에 사용하지 않음

※ RDS Multi-AZ DB 클러스터는 별도의 형태로, 읽기 가능한 인스턴스와 자동 Failover를 함께 제공할 수 있다.

### 다음 프로젝트에서 중요한 설계 질문

- 직접 EC2에 MySQL을 구축할 것인가, RDS를 사용할 것인가?
- 읽기 확장이 목적인가, 고가용성이 목적인가?
- Primary 장애 시 허용 가능한 서비스 중단 시간은?
- 관리형 서비스의 운영 편의성과 추가 비용 중 어느 것을 우선할 것인가?

**핵심:** 직접 구축 경험이 있으면 AWS가 대신 수행하는 작업과 관리형 서비스를 선택하는 이유를 더 구체적으로 이해할 수 있다.

# 5. 최종 핵심 요약

### MySQL 복제 구축 순서

1. 두 서버 준비 및 네트워크 확인
2. MySQL 설치
3. Primary Binary Log 및 GTID 설정
4. Replica Relay Log 및 GTID 설정
5. 복제 전용 계정 생성
6. 초기 데이터 백업 및 복원
7. Primary 연결 정보 설정
8. `START REPLICA` 실행
9. `SHOW REPLICA STATUS\G` 확인
10. INSERT / SELECT로 데이터 복제 검증

### 운영에서 기억할 사항

- **Replication:** 데이터 변경 사항을 복제하는 기능
- **GTID:** 트랜잭션 식별 및 복제 위치 관리
- **TLS:** 복제 통신 암호화
- **수동 Failover:** 운영자가 Replica를 승격하고 서비스 연결을 변경
- **자동 Failover:** 장애 감지·승격·연결 전환을 시스템이 수행
- **RDS Read Replica:** 읽기 확장 중심
- **RDS Multi-AZ:** 고가용성 및 자동 장애 전환 중심

**최종 결론:** Marble 프로젝트에서는 MySQL Primary/Replica를 직접 구성하여 데이터 복제 원리를 학습했다. 이 경험을 바탕으로 복제 장애 대응, 수동 Failover, AWS RDS의 관리형 고가용성 기능을 이해하고 비교할 수 있다.
