# 11장 3교시 — MySQL 복제 장애 대응 및 수동 Failover

## 1. Marble 프로젝트 DB 구성

```text
WAS01 / WAS02
      |
      v
DB01 (Primary)
10.0.31.42:3306
      |
      | GTID 기반 비동기 복제
      v
DB02 (Replica)
10.0.32.160:3306
```

- **Primary:** 데이터 읽기·쓰기 처리
- **Replica:** Primary의 변경 데이터를 복제
- **Replication:** 데이터 복제 기능
- **Failover:** Primary 장애 시 다른 서버로 서비스를 전환하는 과정

현재 Marble 프로젝트는 Primary/Replica 복제가 구축되어 있지만 자동 Failover는 구성되지 않았다.

---

## 2. 복제 장애 발생 시 가장 먼저 확인할 명령어

DB02(Replica)의 MySQL에서 실행한다.

```sql
SHOW REPLICA STATUS\G
```

### 주요 확인 항목

| 항목 | 의미 |
|---|---|
| `Replica_IO_Running` | Primary에서 변경 이벤트를 수신하는 상태 |
| `Replica_SQL_Running` | Relay Log의 이벤트를 적용하는 상태 |
| `Seconds_Behind_Source` | 복제 지연 추정값 |
| `Last_IO_Error` | 이벤트 수신 오류 |
| `Last_SQL_Error` | 이벤트 적용 오류 |
| `Retrieved_Gtid_Set` | Replica가 수신한 GTID 집합 |
| `Executed_Gtid_Set` | Replica가 실행한 GTID 집합 |

### 상태별 장애 판단

| IO | SQL | 점검 방향 |
|---|---|---|
| Yes | Yes | 복제 실행 중, 지연·데이터 정합성 확인 |
| Connecting | Yes | Primary 연결 문제 |
| No | Yes | I/O 스레드 중지 또는 오류 |
| Yes | No | SQL 이벤트 적용 실패 |
| No | No | 복제 전체 중지 또는 복합 장애 |

**핵심:** IO는 변경 이벤트 수신, SQL은 변경 이벤트 적용을 담당한다.

## 3. 장애 유형 ① — I/O 연결 장애

### 증상

```text
Replica_IO_Running: Connecting
Last_IO_Error: Can't connect to MySQL server
```

### 확인 순서

**① DB02 → DB01 네트워크 확인**

DB02 Linux 터미널:

```bash
nc -vz -w 3 10.0.31.42 3306
```

**② DB01 MySQL 실행 상태 확인**

DB01 Linux 터미널:

```bash
sudo systemctl status mysql
```

**③ MySQL 포트 확인**

```bash
sudo ss -lntp | grep ':3306 '
```

**④ MySQL 복제 계정 및 보안 설정 확인**

- Security Group / NACL
- `bind-address`
- 복제 계정 Host 및 비밀번호
- `REPLICATION SLAVE` 권한
- TLS 설정

**핵심:** I/O 연결 장애는 네트워크 → MySQL 서비스 → 인증 및 권한 순서로 확인한다.

---

## 4. 장애 유형 ② — SQL 적용 장애

### 증상

```text
Replica_IO_Running: Yes
Replica_SQL_Running: No

Last_SQL_Error: Duplicate entry ...
```

Primary의 변경 이벤트는 받았지만 Replica에서 데이터에 적용하지 못한 상태이다.

### 대표 원인

- Primary/Replica 데이터 불일치
- 중복 Primary Key
- Replica에서 직접 수행한 데이터 변경
- 스키마 또는 제약 조건 불일치

### 오류 확인

```sql
SHOW REPLICA STATUS\G
```

멀티스레드 복제의 Worker별 오류 확인:

```sql
SELECT
    WORKER_ID,
    LAST_ERROR_NUMBER,
    LAST_ERROR_MESSAGE,
    APPLYING_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker;
```

**주의:** 오류가 발생했다고 GTID를 임의로 건너뛰거나 `RESET REPLICA ALL`을 실행하지 않는다.

먼저 실패한 트랜잭션과 데이터 불일치 원인을 확인하고, 필요한 경우 일관된 백업으로 Replica를 다시 구축한다.

---

## 5. 장애 유형 ③ — 복제 지연(Replication Lag)

Primary에서 데이터 변경이 완료되었지만 Replica에는 아직 반영되지 않은 상태이다.

### 주요 원인

| 원인 | 설명 |
|---|---|
| 네트워크 지연 | Binary Log 이벤트 수신 지연 |
| CPU 부족 | Replica 처리 성능 저하 |
| 디스크 I/O 병목 | 데이터 기록 속도 저하 |
| 대량 트랜잭션 | 많은 데이터 변경으로 적용 지연 |
| 잠금 경합 | 복제 SQL Applier가 작업 대기 |

### 복제 지연 확인

```sql
SHOW REPLICA STATUS\G
```

```text
Seconds_Behind_Source: 30
```

복제 지연이 약 30초로 추정되는 예시이다. 이 값만으로 완전한 데이터 일치 여부를 판단해서는 안 된다.

### GTID 확인

DB01과 DB02에서 각각 실행:

```sql
SELECT @@GLOBAL.gtid_executed;
```

GTID 집합 차이 계산:

```sql
SELECT GTID_SUBTRACT(
    'PRIMARY_GTID_SET',
    'REPLICA_GTID_SET'
);
```

실제 실행 시 문자열을 조회한 GTID 값으로 변경한다.

**핵심:** 비동기 복제에서는 Primary 장애 시 아직 복제되지 않은 데이터가 손실될 수 있다.

# 6. 수동 Failover 구축 및 복구 순서

## 상황: DB01 Primary 장애

```text
[장애 전]

WAS01 / WAS02
       |
       v
DB01 (Primary)
       |
       v
DB02 (Replica)


[장애 후 목표]

WAS01 / WAS02
       |
       v
DB02 (New Primary)

DB01 (장애 / 격리)
```

수동 Failover는 단순히 DB02를 실행하는 작업이 아니다.

**기존 Primary 격리 → 데이터 확인 → Replica 승격 → WAS 연결 변경 → 서비스 검증**까지 포함한다.

아래 상태 변경 명령어는 신규 격리 실습 환경에서만 실행한다. 기존 Marble AWS 서버에 바로 실행하지 않는다.

### 1단계. 기존 Primary 격리

목적: DB01과 DB02에서 동시에 쓰기가 발생하는 Split-Brain 방지.

계획된 전환에서 DB01에 정상 접근이 가능하다면:

```sql
SET GLOBAL super_read_only = ON;
```

다만 이것만으로 완전한 격리가 보장되지는 않는다.

실제 장애 시에는 기존 Primary에 대한 애플리케이션 접근 차단, 서버 격리 등 추가적인 조치가 필요하다.

### 2단계. 마지막 트랜잭션 및 복제 상태 확인

DB01에 접근할 수 있다면:

```sql
SELECT @@GLOBAL.gtid_executed;
```

DB02에서 해당 GTID가 적용될 때까지 대기:

```sql
SELECT WAIT_FOR_EXECUTED_GTID_SET(
    '실제_PRIMARY_GTID_SET',
    30
);
```

결과:

- `0`: 지정한 GTID가 모두 적용됨
- `1`: 제한 시간 안에 모두 적용되지 않음

갑작스러운 Primary 장애로 마지막 GTID 확인이 불가능한 경우에는 DB02의 수신·적용된 GTID와 Relay Log 상태를 확인한다.

DB02:

```sql
SHOW REPLICA STATUS\G
```

필요 시 I/O 수신만 중지하고 이미 받아온 이벤트가 적용되도록 할 수 있다.

```sql
STOP REPLICA IO_THREAD;
```

SQL Applier가 기존에 수신한 이벤트를 모두 처리했는지 확인한 후 다음 단계로 진행한다.

**주의:** 이미 수신한 이벤트를 모두 적용했다고 해서 Primary의 마지막 Commit까지 확보했다는 의미는 아니다.

### 3단계. DB02를 새로운 Primary로 승격

DB02에서 실행:

```sql
STOP REPLICA;
```

읽기 전용 해제:

```sql
SET GLOBAL super_read_only = OFF;
SET GLOBAL read_only = OFF;
```

상태 확인:

```sql
SELECT
    @@GLOBAL.read_only,
    @@GLOBAL.super_read_only;
```

쓰기 가능 상태의 예:

```text
read_only        0
super_read_only  0
```

`SET GLOBAL`은 실행 중인 서버의 설정을 변경한다. 재시작 후에도 설정을 유지하려면 설정 파일 등 영구 설정을 확인해야 한다.

**핵심:** Replica를 승격하기 전에 기존 Primary 격리 및 데이터 정합성 확인이 선행되어야 한다.

### 4단계. WAS01/WAS02 DB 연결 변경

기존 연결:

```properties
spring.datasource.url=jdbc:mysql://10.0.31.42:3306/DB_NAME
```

새로운 연결:

```properties
spring.datasource.url=jdbc:mysql://10.0.32.160:3306/DB_NAME
```

`DB_NAME`은 실제 데이터베이스 이름으로 변경한다.

확인 항목:

- WAS01/WAS02 모두 DB 연결 변경
- 새 Primary의 Security Group과 MySQL 접근 권한
- Spring Boot 설정 적용 및 연결 풀 갱신
- DB 읽기·쓰기 성공 여부
- Spring Session JDBC 세션 정상 동작 여부

### 5단계. 서비스 복구 검증

검증 순서:

```text
DB02 읽기/쓰기 확인
        |
        v
WAS01/02 DB 연결 확인
        |
        v
Apache Reverse Proxy 확인
        |
        v
ALB 전체 서비스 접근 확인
        |
        v
로그인 / 세션 / DB 저장 검증
```

Marble 프로젝트에서 `/health/db`가 구성되어 있다면 WAS에서 다음과 같이 확인할 수 있다.

```bash
curl -i http://127.0.0.1:8080/health/db
```

정상 응답 외에도 실제 애플리케이션의 데이터 저장 기능을 확인해야 한다.

### 6단계. 기존 DB01 복구 및 재편입

DB01이 복구되었다고 해서 바로 Primary로 재사용해서는 안 된다.

1. 기존 DB01의 쓰기 접근 차단 유지
2. 새 Primary(DB02)와 DB01의 GTID 및 데이터 정합성 비교
3. 필요 시 DB02의 백업으로 DB01 재구축
4. DB01이 DB02를 Source로 사용하도록 복제 구성
5. 복제 및 데이터 정합성 검증
6. 새로운 Primary/Replica 구조로 운영

**핵심:** 기존 Primary를 다시 시작하는 것과 정상적인 복제 구조로 재편입하는 것은 다르다.

## 7. RTO와 RPO

| 개념 | 의미 |
|---|---|
| RTO (Recovery Time Objective) | 목표 서비스 복구 시간 |
| RPO (Recovery Point Objective) | 장애 시 허용 가능한 데이터 손실 범위 |

예시:

- RTO 10분: 서비스 복구 목표 10분
- RPO 1분: 데이터 손실 허용 범위 1분

RTO/RPO는 실제 성능을 자동으로 보장하는 수치가 아니라 운영 목표이다.

GTID 기반 비동기 복제에서는 Replica에 적용되지 않은 트랜잭션이 있을 수 있으므로 RPO 0을 보장하지 않는다.

## 8. 장애 대응 핵심 명령어 모음

| 목적 | 명령어 |
|---|---|
| 복제 상태 확인 | `SHOW REPLICA STATUS\G` |
| MySQL 상태 확인 | `sudo systemctl status mysql` |
| TCP 연결 확인 | `nc -vz -w 3 10.0.31.42 3306` |
| 포트 리스닝 확인 | `sudo ss -lntp` |
| GTID 확인 | `SELECT @@GLOBAL.gtid_executed;` |
| GTID 집합 비교 | `GTID_SUBTRACT()` |
| GTID 반영 대기 | `WAIT_FOR_EXECUTED_GTID_SET()` |
| I/O 수신 중지 | `STOP REPLICA IO_THREAD;` |
| 복제 중지 | `STOP REPLICA;` |
| 쓰기 제한 해제 | `SET GLOBAL read_only=OFF;` |
| MySQL 오류 로그 | `sudo journalctl -u mysql -n 50 --no-pager` |

※ 복제 중지 및 쓰기 제한 변경은 서비스 동작에 영향을 주므로 실제 운영 서버에서 진단 목적으로 실행하지 않는다.

---

## 9. 최종 핵심 요약

1. **I/O 장애:** Primary와의 연결, 인증, 3306 포트 확인
2. **SQL 장애:** 복제 이벤트 적용 실패 원인과 데이터 불일치 확인
3. **복제 지연:** Replica의 처리 지연과 GTID 상태 확인
4. **수동 Failover:** 기존 Primary 격리 → Replica 승격 → WAS 연결 변경
5. **Split-Brain:** 두 DB에서 동시에 쓰기가 발생하지 않도록 방지
6. **DB 재편입:** 장애 복구된 DB를 새 Primary 기준으로 동기화
7. **RTO/RPO:** 서비스 복구 시간과 허용 데이터 손실 범위 관리

### 가장 중요한 흐름

**복제 장애 발생 → SHOW REPLICA STATUS 확인 → I/O·SQL·GTID 원인 분석 → 안전한 복구 → 필요 시 수동 Failover → 서비스 검증**

**결론:** MySQL Primary/Replica는 데이터 복제 구조이며, 수동 Failover까지 수행하려면 데이터 정합성 확인, 기존 Primary 격리, Replica 승격, 애플리케이션 연결 변경이 필요하다.
