# 12장 2교시 — AWS 마이그레이션 통합 검증 및 장애 대응

## 1. Marble 전체 아키텍처

```text
Client
   |
   v
Public ALB
   |
   +------- WEB01 (Apache :80)
   |
   +------- WEB02 (Apache :80)
                |
                v
         Apache Balancer
          (byrequests)
                |
        +-------+-------+
        |               |
        v               v
      WAS01           WAS02
 10.0.21.126:8080 10.0.22.9:8080
        |               |
        +-------+-------+
                |
                v
         DB01 Primary
        10.0.31.42:3306
                |
                | GTID 비동기 복제
                v
         DB02 Replica
        10.0.32.160:3306
```

**검증 목적:** ALB → WEB → WAS → DB 전체 경로에서 네트워크 통신과 애플리케이션 기능이 정상 동작하는지 확인한다.

---

## 2. 통합 검증 순서

### 1단계 — ALB / Target Group 확인

AWS 콘솔:

`EC2 → Target Groups → Targets`

확인 항목:
- WEB01/WEB02 등록 여부
- Health Status가 Healthy인지
- Listener와 Target Group 연결
- Health Check 경로 및 응답 코드
- Unhealthy 발생 시 Reason Code

**핵심:** ALB Healthy는 WEB이 Health Check 조건을 충족한다는 뜻이며, WAS/DB까지 정상이라는 보장은 아니다.

### 2단계 — WEB Apache 확인

WEB01/WEB02에서 실행:

```bash
sudo systemctl status apache2
sudo ss -lntp | grep ':80 '
sudo apache2ctl configtest
```

Apache HTTP 응답 확인:

```bash
curl -i --max-time 5 \
  -H "Host: marble.test" \
  http://127.0.0.1/
```

확인 항목:
- Apache 서비스 실행 상태
- TCP 80 포트 LISTEN
- 설정 문법 정상 여부
- 로컬 HTTP 응답

### 3단계 — Apache → WAS 부하 분산 확인

실제 Marble Apache 설정:

```apache
<Proxy "balancer://marblecluster">
    BalancerMember "http://10.0.21.126:8080"
    BalancerMember "http://10.0.22.9:8080"
    ProxySet lbmethod=byrequests
</Proxy>

ProxyPass "/" "balancer://marblecluster/"
ProxyPassReverse "/" "balancer://marblecluster/"
```

부하 분산 로그 확인:

```bash
sudo tail -n 30 /var/log/apache2/marble_backend.log
```

실제 로그 설정:

```apache
LogFormat "%t \"%r\" %>s backend=%{BALANCER_WORKER_NAME}e" marble_backend
```

- `backend=...10.0.21.126:8080` → WAS01 선택
- `backend=...10.0.22.9:8080` → WAS02 선택

**핵심:** 로그의 `BALANCER_WORKER_NAME`을 통해 Apache가 실제로 선택한 WAS를 확인할 수 있다.

### 4단계 — WEB → WAS 네트워크 검증

WEB01과 WEB02에서 각각 실행:

```bash
curl -i --max-time 5 http://10.0.21.126:8080/health
curl -i --max-time 5 http://10.0.22.9:8080/health
```

확인 사항:
- WEB01 → WAS01/WAS02 통신
- WEB02 → WAS01/WAS02 통신
- Security Group TCP 8080 허용
- Spring Boot 응답 상태

**핵심:** WEB01에서 WAS 연결이 성공하더라도 WEB02에서 동일하게 성공한다는 보장은 없다.

### 5단계 — WAS Spring Boot 확인

WAS01/WAS02에서 실행:

```bash
sudo systemctl status marble
sudo ss -lntp | grep ':8080 '
```

애플리케이션 확인:

```bash
curl -i http://127.0.0.1:8080/health
```

DB 연결 확인:

```bash
curl -i http://127.0.0.1:8080/health/db
```

| 결과 | 의미 |
|---|---|
| `/health` 200 | 기본 애플리케이션 정상 응답 |
| `/health/db` 200 | DB 연결 검사 정상 |
| `/health` 200, `/health/db` 503 | DB 연결 장애 가능성 |
| WAS 연결 실패 | Spring Boot 실행·포트·네트워크 확인 |

Spring Boot 로그:

```bash
sudo journalctl -u marble -n 50 --no-pager
```

**핵심:** 애플리케이션 실행 상태와 DB 연결 상태를 구분해서 확인한다.

### 6단계 — WAS → DB 연결 확인

WAS01/WAS02에서 실행:

```bash
nc -vz -w 3 10.0.31.42 3306
```

DB01에서 실행:

```bash
sudo systemctl status mysql
```

MySQL 접속 후:

```sql
SELECT 1;
```

확인 항목:
- WAS → DB01 TCP 3306 연결
- MySQL 서비스 실행
- Security Group 및 계정 권한
- Spring Boot JDBC 연결 설정

**주의:** `nc` 연결 성공은 TCP 통신 성공이며, MySQL 인증과 실제 SQL 처리가 성공했다는 의미는 아니다.

### 7단계 — DB Primary/Replica 복제 확인

DB02에서 실행:

```sql
SHOW REPLICA STATUS\G
```

주요 항목:

| 항목 | 정상 상태 예시 |
|---|---|
| Replica_IO_Running | Yes |
| Replica_SQL_Running | Yes |
| Seconds_Behind_Source | 일반적으로 0 또는 낮은 값 |
| Last_IO_Error | 오류 없음 |
| Last_SQL_Error | 오류 없음 |
| Auto_Position | GTID 자동 위치 추적 사용 시 1 |

**핵심:** DB02 복제가 중단되어도 DB01을 사용하는 서비스는 계속 동작할 수 있지만, 장애 복구에 사용할 데이터가 최신 상태가 아닐 수 있다.

## 3. HTTP 오류별 장애 대응

| 코드 | 의미 | 우선 확인 |
|---|---|---|
| 403 | 접근 거부 | 인증, 권한, CSRF, 세션 |
| 404 | 요청 경로 없음 | URL, ProxyPass, Controller |
| 500 | 서버 내부 오류 | WAS 로그, 애플리케이션, DB |
| 502 | 프록시가 유효한 응답을 받지 못함 | ALB/Apache와 백엔드 연결 |
| 503 | 서비스 이용 불가 | 대상 서버 및 서비스 상태 |
| 504 | 백엔드 응답 시간 초과 | Timeout, 네트워크, 서버 지연 |

※ 502·503·504는 ALB 또는 Apache 등 반환 주체에 따라 실제 원인이 다를 수 있다.

### 대표 장애 시나리오

**① ALB Target Unhealthy**
- Target Group Reason Code 확인
- Apache 서비스 및 Health Check 경로 확인
- WEB Security Group과 오류 로그 확인

**② WEB은 정상인데 WAS 연결 실패**
- Apache Error Log 확인
- `marble_backend.log` 확인
- WEB에서 WAS로 직접 `curl` 실행
- WAS의 Spring Boot 실행 및 8080 포트 확인

**③ `/health` 200, `/health/db` 503**
- Spring Boot JDBC URL 확인
- WAS → DB01 TCP 3306 연결
- MySQL 서비스 및 계정 권한 확인
- Spring Boot 오류 로그 분석

**④ 회원가입/로그인 시 HTTP 403**
- Spring Security/CSRF 로그 확인
- WAS01/WAS02 요청 분산 확인
- Spring Session JDBC의 세션 저장 및 조회 상태 확인

---

## 4. 장애 대응에 사용하는 핵심 로그

```bash
# Apache 오류 로그
sudo tail -n 50 /var/log/apache2/marble_error.log

# Apache → WAS 분산 로그
sudo tail -n 50 /var/log/apache2/marble_backend.log

# Spring Boot 로그
sudo journalctl -u marble -n 50 --no-pager

# MySQL 서비스 로그
sudo journalctl -u mysql -n 50 --no-pager
```

로그를 통해 **어느 계층에서 오류가 발생했는지** 확인한다.

## 5. 전체 장애 대응 흐름

```text
사용자 서비스 오류 발생
          |
          v
1. ALB Listener / Target Group 확인
          |
          v
2. WEB Apache 실행·응답 확인
          |
          v
3. Apache → WAS 연결·분산 확인
          |
          v
4. Spring Boot 실행 및 /health 확인
          |
          v
5. WAS → DB 연결 및 /health/db 확인
          |
          v
6. MySQL 서비스와 Replica 상태 확인
          |
          v
7. 장애 원인 해결
          |
          v
8. 전체 요청 경로 및 실제 기능 재검증
```

이미 특정 구간의 실패가 확인되었다면 해당 구간부터 집중적으로 점검한다.

**핵심:** 장애 발생 시 무조건 서버를 재시작하지 않고, 요청 흐름과 로그를 이용하여 원인을 좁혀 나간다.

---

## 6. 최종 핵심 요약

1. **ALB:** WEB01/WEB02 Target 상태 및 요청 분산 확인
2. **WEB:** Apache 서비스, 80 포트, Reverse Proxy 확인
3. **WAS:** Spring Boot, 8080 포트, `/health` 확인
4. **DB:** JDBC 연결, TCP 3306, `/health/db` 확인
5. **Replication:** DB02 복제 스레드 및 GTID 상태 확인
6. **로그 분석:** Apache와 Spring Boot 로그를 연결하여 장애 구간 파악
7. **통합 검증:** 개별 서비스뿐 아니라 실제 요청과 데이터 저장 기능까지 확인

### 가장 중요한 원칙

**서비스 실행 정상 ≠ 네트워크 정상 ≠ 전체 애플리케이션 정상**

서버가 정상 실행 중이어도 서버 간 통신 장애나 애플리케이션 내부 오류로 실제 서비스는 실패할 수 있다.

### 최종 결론

Marble 프로젝트에서는 AWS로 마이그레이션한 WEB/WAS/DB의 통신 경로를 기준으로 ALB Health Check, Apache Reverse Proxy, Spring Boot Health Check, MySQL 연결 및 복제 상태를 검증하는 방법을 학습했다.

**장애 대응의 핵심은 ALB → WEB → WAS → DB 요청 흐름을 이해하고, 오류 로그와 통신 결과를 이용해 문제가 발생한 위치를 찾아내는 것이다.**
