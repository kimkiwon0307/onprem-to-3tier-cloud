# 13장 2교시 — Spring Session JDBC + MySQL 세션 공유 구축

## 1. Spring Session JDBC란?

Spring Boot의 HTTP Session을 각 WAS의 메모리가 아닌 **공통 관계형 데이터베이스(MySQL)에 저장하고 조회**하도록 하는 기술이다.

### 도입 이유

WAS01에서 생성한 세션을 WAS02에서도 사용할 수 있도록 하기 위해서이다.

```text
사용자
  |
  v
ALB
  |
  +-------- WEB01 / WEB02
                 |
                 v
          Apache Balancer
                 |
          +------+------+
          |             |
          v             v
        WAS01         WAS02
          |             |
          +------+------+
                 |
                 v
           MySQL DB01
          (공통 세션 저장)
```

**핵심:** WAS 간 메모리 세션을 복사하는 것이 아니라, 여러 WAS가 동일한 MySQL 세션 저장소를 사용한다.

```text
1. MySQL 설치 및 원격 접속 설정
               ↓
2. 세션 전용 DB·계정·권한 생성
               ↓
3. SPRING_SESSION 테이블 생성
               ↓
4. Spring Session JDBC 의존성 추가
               ↓
5. application.properties 설정
               ↓
6. 세션 생성·조회 API 작성
               ↓
7. WAS01/WAS02에 동일한 애플리케이션 배포
               ↓
8. 동일 쿠키로 WAS 간 세션 공유 검증
               ↓
9. MySQL 데이터 및 장애 로그 확인
```

## 3. MySQL 세션 저장소 구축

### ① 세션 DB 생성

```sql
CREATE DATABASE session_lab
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

### ② WAS 접속 계정 생성

실습 환경의 WAS01/02가 MySQL에 접근하도록 계정을 생성한다.

```sql
CREATE USER 'session_lab'@'192.168.111.161'
IDENTIFIED BY '실습용_강력한_비밀번호';

CREATE USER 'session_lab'@'192.168.111.162'
IDENTIFIED BY '실습용_강력한_비밀번호';
```

### ③ 테이블 데이터 접근 권한 부여

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON session_lab.*
TO 'session_lab'@'192.168.111.161';

GRANT SELECT, INSERT, UPDATE, DELETE
ON session_lab.*
TO 'session_lab'@'192.168.111.162';
```

이 실습에서는 관리자가 세션 테이블을 미리 생성하므로 애플리케이션 계정에 테이블 생성 권한을 부여하지 않는다.

### ④ Spring Session JDBC 테이블

| 테이블 | 역할 |
|---|---|
| `SPRING_SESSION` | 세션 ID, 생성·접근·만료 시간 관리 |
| `SPRING_SESSION_ATTRIBUTES` | 사용자별 세션 속성 데이터 저장 |

주요 컬럼:

- `SESSION_ID`: 세션 식별자
- `CREATION_TIME`: 세션 생성 시각
- `LAST_ACCESS_TIME`: 마지막 접근 시각
- `MAX_INACTIVE_INTERVAL`: 허용되는 비활성 시간
- `EXPIRY_TIME`: 세션 만료 시각
- `ATTRIBUTE_NAME`: 세션 속성 이름
- `ATTRIBUTE_BYTES`: 직렬화된 세션 속성 값

테이블 존재 확인:

```sql
SHOW TABLES LIKE 'SPRING_SESSION%';
```

**핵심:** 세션 기본 정보와 세션 속성 정보를 별도 테이블에 저장한다.

## 4. Spring Boot 의존성 추가

Spring Boot 3.5.x 실습 기준 `build.gradle`:

```gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-jdbc'
    implementation 'org.springframework.session:spring-session-jdbc'

    runtimeOnly 'com.mysql:mysql-connector-j'
}
```

| 의존성 | 역할 |
|---|---|
| `spring-boot-starter-web` | HTTP 요청 처리 |
| `spring-boot-starter-jdbc` | JDBC 및 DataSource |
| `spring-session-jdbc` | HTTP Session을 JDBC 저장소에 관리 |
| `mysql-connector-j` | Java와 MySQL 연결 |

가장 중요한 의존성:

```gradle
implementation 'org.springframework.session:spring-session-jdbc'
```

지원되는 Spring Boot 자동 설정 환경에서는 Spring Session JDBC를 적용하기 위해 별도로 `@EnableJdbcHttpSession`을 작성할 필요가 없다.

## 5. application.properties 설정

```properties
server.port=8080

spring.datasource.url=jdbc:mysql://192.168.111.163:3306/session_lab
spring.datasource.username=session_lab
spring.datasource.password=${DB_PASSWORD}

spring.session.jdbc.initialize-schema=never
spring.session.jdbc.table-name=SPRING_SESSION

server.servlet.session.timeout=30m
```

| 설정 | 의미 |
|---|---|
| `server.port` | WAS HTTP 포트 |
| `spring.datasource.url` | 공통 MySQL 연결 주소 |
| `spring.datasource.username` | DB 접속 계정 |
| `spring.datasource.password` | 환경변수로 DB 비밀번호 전달 |
| `initialize-schema=never` | 애플리케이션 시작 시 스키마 자동 생성 방지 |
| `table-name=SPRING_SESSION` | 기본 세션 테이블 이름 |
| `session.timeout=30m` | 세션 비활성 만료 시간 30분 |

### 스키마 초기화 옵션

- `always`: 시작 시 스키마 초기화 시도
- `embedded`: 내장 DB에서 초기화
- `never`: 스키마 자동 초기화하지 않음

**운영 환경에서는 테이블을 별도 관리하고 `never`를 사용하는 방식을 고려한다.** 여러 WAS가 같은 DB를 사용하므로 각 WAS가 실행될 때마다 테이블 초기화를 시도하지 않도록 한다.

## 6. HttpSession 저장·조회 원리

실습용 Java 코드:

```java
@GetMapping("/lab/counter")
public Map<String, Object> counter(HttpSession session) {

    Integer count =
        (Integer) session.getAttribute("count");

    if (count == null) {
        count = 0;
    }

    count++;

    session.setAttribute("count", count);

    return Map.of("count", count);
}
```

### 주요 메서드

| 메서드 | 역할 |
|---|---|
| `getAttribute("count")` | 현재 세션의 속성 조회 |
| `setAttribute("count", count)` | 현재 세션에 속성 저장 |
| `HttpSession` | 사용자별 HTTP 세션 접근 |

**중요:** Java 코드에서는 일반적인 `HttpSession`을 사용하지만 Spring Session JDBC가 적용되면 세션 데이터가 공통 MySQL에 저장된다.

## 7. WAS01/WAS02 세션 공유 검증

두 WAS는 같은 Spring Boot 애플리케이션과 MySQL 세션 저장소를 사용한다.

```text
WAS01 → 192.168.111.163:3306
WAS02 → 192.168.111.163:3306
```

### ① WAS01에 요청

```bash
curl -i \
  --resolve marble-lab.test:8080:192.168.111.161 \
  -c /tmp/marble-session-cookies.txt \
  http://marble-lab.test:8080/lab/counter
```

예상 결과:

```json
{"count":1}
```

### ② 같은 쿠키로 WAS02 요청

```bash
curl -i \
  --resolve marble-lab.test:8080:192.168.111.162 \
  -b /tmp/marble-session-cookies.txt \
  -c /tmp/marble-session-cookies.txt \
  http://marble-lab.test:8080/lab/counter
```

예상 결과:

```json
{"count":2}
```

### ③ 다시 WAS01 요청

동일한 쿠키 파일을 사용하여 WAS01로 요청한다.

예상 결과:

```json
{"count":3}
```

### curl 옵션

| 옵션 | 의미 |
|---|---|
| `-i` | HTTP 응답 헤더 표시 |
| `--resolve` | 동일한 호스트 이름을 지정한 WAS IP에 연결 |
| `-c` | 쿠키 파일 저장 |
| `-b` | 저장된 쿠키를 요청에 포함 |

### 정상 판단 기준

```text
WAS01 → count 1
   |
   v
WAS02 → count 2
   |
   v
WAS01 → count 3

결론: WAS를 변경해도 세션 유지
```

**핵심:** 두 WAS에 동일한 세션 쿠키를 전달했을 때 기존 세션 속성 값이 이어지면 공통 세션 저장소가 정상 동작한다는 것을 확인할 수 있다.

## 8. MySQL 세션 데이터 검증

세션 저장 여부 확인:

```sql
USE session_lab;

SELECT COUNT(*)
FROM SPRING_SESSION;
```

세션 속성 확인:

```sql
SELECT ATTRIBUTE_NAME
FROM SPRING_SESSION_ATTRIBUTES;
```

카운터 예제에서는 `count` 속성이 나타날 수 있다.

**주의:** 세션 속성의 실제 값은 `ATTRIBUTE_BYTES`에 직렬화되어 저장되므로 단순 문자열로 보이지 않을 수 있다.

## 9. Spring Session JDBC와 HTTP 403

### 세션 공유 전

```text
GET /signup → WAS01
                 |
                 v
           CSRF Token 생성
           WAS01 세션에 저장

POST /signup → WAS02
                 |
                 v
          기존 세션을 찾지 못함
                 |
                 v
        CSRF 검증 실패 가능
                 |
                 v
              HTTP 403
```

### 세션 공유 후

```text
GET /signup → WAS01
                 |
                 v
             MySQL에
        세션 및 토큰 정보 저장

POST /signup → WAS02
                 |
                 v
           공통 MySQL에서
              세션 조회
                 |
                 v
           CSRF Token 검증
```

세션 기반 CSRF 저장 방식을 사용할 때 공통 세션 저장소를 사용하면 WAS 간 세션 불일치 문제를 해결할 수 있다.

단, **Spring Session JDBC를 적용했다고 모든 HTTP 403이 해결되는 것은 아니다.** 권한 부족, CSRF Token 누락, 쿠키 설정 오류 등도 확인해야 한다.

## 10. 장애 대응

| 장애 증상 | 예상 원인 | 확인 항목 |
|---|---|---|
| WAS 시작 실패 | DB 연결 및 설정 오류 | 애플리케이션 로그 |
| 세션 테이블 없음 | 스키마 미생성 | `SHOW TABLES` |
| SQL Access denied | DB 계정·권한 오류 | `SHOW GRANTS` |
| Connection refused | DB 서비스·포트 문제 | 3306 LISTEN, 방화벽 |
| WAS 변경 시 세션 초기화 | 쿠키 또는 저장소 불일치 | Cookie, JDBC URL |
| HTTP 403 | CSRF·세션·권한 오류 | Spring Security 로그 |
| MySQL 장애 | 공통 세션 저장소 이용 불가 | DB 서비스·연결 상태 |

### 장애 분석 순서

```text
1. WAS01/WAS02 실행 확인
             |
             v
2. WAS → MySQL 네트워크 확인
             |
             v
3. JDBC 설정과 DB 권한 확인
             |
             v
4. 세션 테이블 존재 확인
             |
             v
5. 세션 쿠키 전달 확인
             |
             v
6. WAS 간 세션 조회 확인
             |
             v
7. 로그인·CSRF 기능 검증
```

## 11. 실무 기술 선택 — JDBC와 Redis

| 구분 | Spring Session JDBC | Spring Session Redis |
|---|---|---|
| 세션 저장소 | MySQL 등 관계형 DB | Redis |
| 장점 | 기존 DB 활용 가능 | 빠른 세션 접근 및 부하 분리 |
| 단점 | MySQL 부하·장애에 의존 | Redis 운영·가용성 관리 필요 |
| 적합한 경우 | 비교적 작은 서비스, 기존 DB 활용 | 세션 트래픽 증가, 세션 부하 분리 |

Sticky Session은 사용자를 같은 서버로 보내는 기능이고, JDBC/Redis는 여러 서버가 세션을 공유하는 방식이다.

Marble은 기존 MySQL을 활용하므로 **Spring Session JDBC를 유지하는 것이 현재 프로젝트에 적절한 선택**이다.

다만 MySQL Primary 장애가 발생하면 세션 조회에도 문제가 생길 수 있다. Replica를 운영하더라도 자동 Failover가 별도로 구성되지 않았다면 자동으로 DB02로 전환되지 않는다.

## 12. Marble 실제 프로젝트 구성

| 서버 | 주소 및 역할 |
|---|---|
| WEB01/02 | Apache Reverse Proxy 및 WAS 부하 분산 |
| WAS01 | `10.0.21.126:8080` |
| WAS02 | `10.0.22.9:8080` |
| DB01 Primary | `10.0.31.42:3306` |
| DB02 Replica | `10.0.32.160:3306` |

Marble은 MySQL을 공통 세션 저장소로 활용하므로 WAS01/02로 요청이 분산되더라도 동일한 세션을 사용할 수 있도록 설계되어 있다.

### 확인해야 할 조건

- 두 WAS에 Spring Session JDBC 적용
- 동일한 DB와 세션 테이블 사용
- 브라우저 세션 쿠키 정상 전달
- 세션 생성·조회 및 만료 정상
- 실제 로그인·회원가입·CSRF 정상 작동

## 13. 최종 핵심 정리

1. **Spring Session JDBC:** WAS 간 세션을 MySQL에 공통 저장한다.
2. **세션 테이블:** `SPRING_SESSION`, `SPRING_SESSION_ATTRIBUTES`를 사용한다.
3. **의존성:** `spring-session-jdbc`가 핵심이다.
4. **설정:** 두 WAS가 동일한 DB와 세션 저장소를 사용해야 한다.
5. **쿠키:** WAS 변경 시 동일한 세션 식별자를 전달해야 한다.
6. **검증:** WAS01 → WAS02 → WAS01 순서로 요청해 세션 데이터가 이어지는지 확인한다.
7. **장애 대응:** 쿠키, WAS 설정, JDBC, DB 접근 및 세션 테이블을 확인한다.
8. **운영:** 공통 DB 장애가 세션 장애로 연결될 수 있으므로 모니터링과 DB 가용성을 고려해야 한다.

### 가장 중요한 결론

**Spring Session JDBC는 여러 WAS가 공통 MySQL에 세션 정보를 저장하고 조회하도록 하여, 특정 WAS에 사용자를 고정하지 않고도 동일한 로그인 상태를 유지할 수 있도록 하는 기술이다.**

Marble 프로젝트에서는 이 구조를 통해 WAS 이중화 환경의 세션 불일치 문제를 해결하도록 설계했다.
