# 18장 2교시 — Jenkins CI 완성 및 Jenkinsfile 왕초보 학습

## 1. 학습 목표

Marble Spring Boot 프로젝트에 Jenkins CI Pipeline을 구축한다.

GitHub에 새로운 Commit이 발생하면 Jenkins가 Poll SCM으로 변경 사항을 확인하고, 자동으로 빌드·테스트·JAR 생성·보관 작업을 수행한다.

### 최종 CI 구조

```text
GitHub (master)
       |
       | Poll SCM
       v
Jenkins Pipeline
       |
       ├── Build   : Java 컴파일
       ├── Test    : 자동 테스트
       ├── Package : 실행형 JAR 생성
       └── Archive : JAR 보관
```

이번 교시에서는 WAS 서버에 배포하지 않는다.

---

## 2. Jenkinsfile이란?

Jenkinsfile은 Jenkins가 실행할 작업의 순서를 작성한 파일이다.

예를 들어 Jenkins에 다음과 같이 지시하는 것이다.

1. GitHub의 소스코드를 가져온다.
2. Java 코드를 컴파일한다.
3. 테스트를 실행한다.
4. 실행형 JAR를 생성한다.
5. 생성된 JAR를 보관한다.

이 절차를 Jenkins Pipeline 코드로 표현한다.

### 핵심 구성

| 문법 | 의미 |
|---|---|
| `pipeline` | 전체 자동화 작업 |
| `agent any` | 작업을 실행할 Jenkins 노드 선택 |
| `stages` | 작업 단계들을 묶는 영역 |
| `stage` | 개별 작업 단계 |
| `steps` | 실제 수행할 작업 |
| `sh` | Linux 명령어 실행 |
| `triggers` | Jenkins 자동 실행 조건 |
| `post` | 성공 또는 실패 후 작업 |

# 3. 왕초보용 Jenkinsfile — 간단한 버전

처음에는 아래 코드만 이해해도 충분하다.

파일 이름:

`Jenkinsfile.ci`

```groovy
pipeline {
    agent any

    triggers {
        pollSCM('H/5 * * * *')
    }

    stages {
        stage('Build') {
            steps {
                sh 'bash ./gradlew clean classes'
            }
        }

        stage('Test') {
            steps {
                sh 'bash ./gradlew test'
            }
        }

        stage('Package') {
            steps {
                sh 'bash ./gradlew bootJar'
            }
        }

        stage('Archive') {
            steps {
                archiveArtifacts artifacts: 'build/libs/app.jar'
            }
        }
    }
}
```

### 이 코드가 수행하는 작업

```text
① Jenkins가 GitHub 변경 확인
              |
              v
② 소스코드 자동 Checkout
              |
              v
③ Gradle Build
              |
              v
④ Gradle Test
              |
              v
⑤ Gradle bootJar
              |
              v
⑥ Jenkins Archive
```

**중요:** Jenkins Job을 `Pipeline script from SCM`으로 설정하면 Declarative Pipeline은 기본적으로 작업 시작 시 소스코드를 Checkout한다. 따라서 이 간단한 버전에서는 `Checkout` Stage를 따로 작성하지 않아도 된다.

단, 기본 Checkout을 비활성화한 설정이 있다면 별도로 Checkout을 작성해야 한다.

### 실행 전제 조건

- Jenkins에 Pipeline, Git Plugin이 설치되어 있어야 한다.
- GitHub Repository와 Credentials가 Job에 등록되어 있어야 한다.
- Jenkins Job이 `Pipeline script from SCM`으로 설정되어 있어야 한다.
- `master` 브랜치의 Script Path가 `Jenkinsfile.ci`여야 한다.
- Jenkins 빌드 환경에 필요한 JDK가 설치되어 있어야 한다.
- 프로젝트에 Gradle Wrapper가 있어야 한다.
- `build.gradle`에서 `bootJar` 출력 이름을 `app.jar`로 설정해야 한다.

예시:

```groovy
tasks.named('bootJar') {
    archiveFileName = 'app.jar'
}
```

이 설정이 없으면 생성되는 JAR 이름이 달라 Archive가 실패할 수 있다.

# 4. 왕초보용 Jenkinsfile 문법 자세히 이해하기

## 4.1 `pipeline`

```groovy
pipeline {

}
```

Jenkins에게 자동화 작업의 시작과 끝을 알려준다.

Pipeline에 필요한 여러 설정을 이 블록 안에 작성한다.

## 4.2 `agent any`

```groovy
agent any
```

Jenkins가 사용 가능한 실행 노드를 선택하도록 한다.

- `agent`: 작업을 실행할 장소 지정
- `any`: 사용할 수 있는 노드 중 하나 선택

학습 환경에서는 Jenkins Controller에서 직접 빌드를 수행할 수 있지만, 실무에서는 별도 빌드 Agent를 사용하는 것이 권장된다.

## 4.3 `triggers`

```groovy
triggers {
    pollSCM('H/5 * * * *')
}
```

Pipeline을 언제 자동 실행할지 설정하는 부분이다.

`pollSCM`은 Jenkins가 GitHub 저장소의 변경 사항을 주기적으로 확인하는 기능이다.

`H/5 * * * *`는 약 5분 간격으로 확인한다는 의미이다.

**5분마다 무조건 빌드하는 것이 아니라 새로운 빌드 대상 Commit이 있을 때 실행한다.**

## 4.4 `stages`

```groovy
stages {

}
```

실행할 여러 작업 단계를 묶는 영역이다.

예를 들어 Build, Test, Package, Archive를 작성할 수 있다.

## 4.5 `stage`

```groovy
stage('Build') {

}
```

하나의 작업 단계를 정의한다.

`Build`는 작업의 이름이며, 원하는 이름으로 지정할 수 있다.

Jenkins는 Stage별 성공·실패 상태를 표시한다.

## 4.6 `steps`

```groovy
steps {

}
```

해당 Stage에서 실제 실행할 작업을 작성하는 영역이다.

예를 들어 Linux 명령어, 파일 보관, 로그 출력 등을 작성한다.

## 4.7 `sh`

```groovy
sh 'bash ./gradlew test'
```

Jenkins가 Linux Shell 명령어를 실행하도록 한다.

여기서 중요한 차이가 있다.

- `sh`: Jenkins Pipeline 명령
- `bash ./gradlew test`: Linux에서 실제 실행하는 명령어

즉, Jenkins가 `sh`를 통해 Linux에 Gradle 테스트 실행을 요청하는 것이다.

# 5. Gradle 명령어 상세 해석

## 5.1 Build

```bash
bash ./gradlew clean classes
```

| 명령어 | 역할 |
|---|---|
| `bash` | Bash로 스크립트 실행 |
| `./gradlew` | Gradle Wrapper 실행 |
| `clean` | 이전 Gradle 빌드 산출물 삭제 |
| `classes` | 메인 Java 소스 컴파일 및 리소스 처리 |

### 실행 원리

```text
build.gradle 확인
        |
        v
필요한 라이브러리 준비
        |
        v
Java 소스 컴파일
        |
        v
build/classes/ 생성
```

**컴파일 성공은 애플리케이션 기능이 정상이라는 의미는 아니다.**

## 5.2 Test

```bash
bash ./gradlew test
```

Gradle 테스트를 실행한다.

대표적으로 다음 작업이 수행된다.

1. 테스트 소스코드 컴파일
2. 테스트 실행
3. 성공·실패 판정
4. 테스트 결과 보고서 생성

테스트 결과 위치:

```text
build/reports/tests/test/index.html
build/test-results/test/
```

테스트가 실패하면 일반적으로 Gradle 명령이 실패 상태로 종료되고 Jenkins의 다음 Stage로 진행하지 않는다.

단, 테스트 코드가 없으면 `NO-SOURCE`로 표시될 수 있으므로 실제 테스트 실행 여부를 확인해야 한다.

## 5.3 Package

```bash
bash ./gradlew bootJar
```

Spring Boot 실행형 JAR를 생성한다.

### 실행 결과

```text
build/
   └── libs/
       └── app.jar
```

`app.jar` 안에는 애플리케이션 클래스와 실행에 필요한 라이브러리 등이 포함된다.

Marble은 Spring Boot 내장 Tomcat을 사용하므로 다음과 같이 실행할 수 있다.

```bash
java -jar app.jar
```

실행형 JAR를 만든다는 것과 실제 서버에서 정상 기동한다는 것은 별도의 검증이다.

## 5.4 Archive

```groovy
archiveArtifacts artifacts: 'build/libs/app.jar'
```

Jenkins 빌드 결과에 JAR 파일을 보관한다.

| 부분 | 역할 |
|---|---|
| `archiveArtifacts` | Jenkins 산출물 보관 기능 |
| `artifacts:` | 보관 대상 파일 지정 |
| `build/libs/app.jar` | 보관할 JAR 경로 |

### Archive를 사용하는 이유

생성한 JAR를 해당 Jenkins 빌드 기록에 연결해 보관하기 위해서이다.

```text
Jenkins Build #1
    └── app.jar

Jenkins Build #2
    └── app.jar

Jenkins Build #3
    └── app.jar
```

각 빌드에서 생성된 산출물을 관리할 수 있다.

# 6. 기존 Jenkinsfile의 추가 옵션 자세히 이해하기

왕초보용 Jenkinsfile에서는 생략했지만, 이전 수업에서는 다음 옵션도 사용했다.

## 6.1 기본 Checkout 비활성화

```groovy
skipDefaultCheckout(true)
```

Jenkins의 기본 Checkout을 생략한다.

다음 명령어로 Checkout을 직접 제어하려는 경우 사용한다.

```groovy
stage('Checkout') {
    steps {
        checkout scm
    }
}
```

`checkout scm`은 Jenkins Job에 설정된 Git 저장소에서 소스코드를 가져온다.

처음에는 기본 자동 Checkout을 사용해도 되므로 이 옵션을 생략해도 된다.

## 6.2 실행 시간 표시

```groovy
timestamps()
```

Jenkins Console Output에 시간을 표시한다.

로그에서 어느 단계가 얼마나 걸렸는지 확인할 때 도움이 된다.

## 6.3 중복 빌드 방지

```groovy
disableConcurrentBuilds()
```

동일 Jenkins Job의 동시 실행을 막는다.

특히 나중에 배포까지 연결했을 때 여러 배포가 겹치는 상황을 줄이기 위해 사용한다.

## 6.4 Gradle Daemon 옵션

```bash
--no-daemon
```

Gradle이 장시간 유지되는 Daemon을 재사용하지 않도록 요청한다.

CI에서 Gradle 실행 프로세스의 생명주기를 관리할 때 사용하는 옵션이다.

## 6.5 Gradle 병렬 작업 제한

```bash
--max-workers=1
```

Gradle의 최대 병렬 Worker 수를 1개로 제한한다.

EC2의 CPU와 메모리가 적을 때 자원 사용을 제어하기 위해 사용한다.

## 6.6 Gradle JVM 메모리 제한

```bash
-Dorg.gradle.jvmargs="-Xmx512m -XX:MaxMetaspaceSize=256m"
```

| 옵션 | 설명 |
|---|---|
| `-Dorg.gradle.jvmargs` | Gradle JVM 실행 옵션 지정 |
| `-Xmx512m` | JVM Heap 최대 크기 512MB |
| `-XX:MaxMetaspaceSize=256m` | Metaspace 최대 크기 256MB |

이 값은 Gradle JVM에 적용되는 설정이며 Jenkins 서버 전체 메모리 사용량을 제한하지 않는다.

## 6.7 테스트 결과 등록

```groovy
junit testResults: 'build/test-results/test/TEST-*.xml',
      allowEmptyResults: false
```

Gradle의 테스트 XML 결과를 Jenkins에 등록한다.

- `junit`: Jenkins JUnit Plugin의 테스트 결과 처리 기능
- `testResults`: 테스트 결과 파일 위치
- `allowEmptyResults: false`: 테스트 결과가 하나도 없으면 실패 처리

왕초보용에서는 생략했지만, 실제 CI 검증에서는 추가하는 것이 좋다.

## 6.8 JAR 보관 검증 강화

```groovy
archiveArtifacts(
    artifacts: 'build/libs/app.jar',
    fingerprint: true,
    allowEmptyArchive: false
)
```

- `fingerprint: true`: Jenkins 산출물 Fingerprint 기록
- `allowEmptyArchive: false`: 보관 대상이 없으면 실패 처리

## 6.9 빌드 성공·실패 메시지

```groovy
post {
    success {
        echo 'Build SUCCESS'
    }

    failure {
        echo 'Build FAILED'
    }
}
```

- `post`: Pipeline 종료 후 수행할 처리
- `success`: 성공했을 때 실행
- `failure`: 실패했을 때 실행
- `echo`: Jenkins 로그에 메시지 출력

# 7. 왕초보용과 운영 보강형 비교

| 구분 | 왕초보용 | 운영 보강형 |
|---|---|---|
| Git Checkout | Jenkins 기본 자동 Checkout | 직접 Checkout 가능 |
| Poll SCM | 사용 | 사용 |
| Gradle Build | 기본 명령어 | 자원 제한 옵션 추가 |
| Test | 테스트 실행 | JUnit 보고서 검증 |
| Package | JAR 생성 | JAR 존재 및 크기 검사 |
| Archive | JAR 보관 | Fingerprint 및 누락 방지 |
| 동시 실행 | 기본 동작 | 중복 실행 제한 |
| 로그 | 기본 로그 | 시간 및 오류 처리 보강 |

### 학습 순서

**1단계 — 간단하게 먼저 성공시키기**

Build → Test → Package → Archive

**2단계 — 검증 강화**

JUnit 결과 확인, JAR 존재 여부 검사

**3단계 — 운영 보강**

메모리 제한, 로그, 동시 실행 방지, 보관 정책

처음부터 모든 옵션을 암기할 필요는 없다.

# 8. 장애 대응

| 장애 | 원인 후보 | 확인 방법 |
|---|---|---|
| Build 실패 | Java 버전·컴파일 오류 | Console Output |
| Test 실패 | 테스트 코드·환경 문제 | 테스트 보고서 |
| `test NO-SOURCE` | 테스트 코드 없음 | `src/test/java` |
| JAR 생성 실패 | `bootJar` 설정 | `build.gradle` |
| JAR 파일 이름 불일치 | 출력 파일명 설정 | `build/libs/` |
| Archive 실패 | 파일 경로·생성 실패 | Workspace |
| 메모리 부족 | Gradle·Jenkins 자원 부족 | `free -h`, `df -h` |

### 기본 장애 분석 순서

```text
Checkout 성공?
      |
      v
Build 성공?
      |
      v
Test 성공?
      |
      v
JAR 생성?
      |
      v
Archive 성공?
```

실패한 Stage를 먼저 확인하고 Console Output에서 최초 오류를 찾아 원인을 분석한다.

# 9. 최종 핵심 정리

1. Jenkinsfile은 CI/CD 작업을 정의한 코드 파일이다.
2. `pipeline`은 전체 작업, `stage`는 개별 작업 단계이다.
3. `steps`에는 실제 실행할 작업을 작성한다.
4. `sh`는 Jenkins에서 Linux 명령어를 실행할 때 사용한다.
5. `clean classes`는 Java 코드를 컴파일한다.
6. `test`는 테스트를 실행한다.
7. `bootJar`는 Spring Boot 실행형 JAR를 생성한다.
8. `archiveArtifacts`는 생성된 파일을 Jenkins 빌드 기록에 보관한다.
9. Poll SCM은 GitHub의 새 Commit을 감지하여 Pipeline을 실행한다.
10. 테스트·패키징·배포 성공 여부는 각각 별도로 검증해야 한다.

### 가장 중요한 한 문장

**Jenkinsfile은 수동으로 수행하던 Linux 빌드 명령어를 Jenkins가 정해진 순서에 따라 자동 실행하도록 작성한 파일이다.**
