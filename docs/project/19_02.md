# 19장 2교시 — Jenkins CD: JAR 교체 및 WAS01/02 순차 배포

## 1. 학습 목표

18장 CI에서 생성한 `app.jar`를 WAS 서버에 배포하고, 새로운 버전이 정상 동작하는지 검증하는 방법을 학습한다.

### 이번 교시 핵심

1. 기존 JAR 백업
2. 새 JAR 파일 준비 및 교체
3. `systemctl`을 통한 Spring Boot 재시작
4. `/health`를 이용한 정상 여부 확인
5. WAS01 → WAS02 순차 배포
6. Jenkins Pipeline으로 배포 작업 자동화
7. 장애 발생 시 로그 분석

**19장 2교시에서는 배포 성공·실패 감지까지 학습한다. 자동 Rollback은 19장 3교시에서 다룬다.**

# 3. 배포 전 상태 확인

배포를 시작하기 전에 기존 서비스가 정상인지 확인한다.

### 서비스 상태

```bash
sudo systemctl status marble
```

- `systemctl`: systemd 서비스 관리
- `status`: 현재 서비스 상태 확인
- `marble`: 서비스 이름

### JAR 파일 확인

```bash
ls -lh /opt/marble/app.jar
```

```bash
ls -lh /opt/marble-deploy/incoming/app.jar
```

- `ls`: 파일 목록 확인
- `-l`: 자세한 정보
- `-h`: 사람이 읽기 쉬운 파일 크기 표시

### 배포 전 Health Check

```bash
curl -fsS --max-time 3 http://127.0.0.1:8080/health
```

- `curl`: HTTP 요청
- `-f`: HTTP 오류 상태에서 실패 처리
- `-s`: 진행 표시 생략
- `-S`: 오류가 발생하면 메시지 표시
- `--max-time 3`: 요청 최대 3초 제한

**기존 서비스가 비정상이라면 원인부터 확인하고 배포를 진행한다.**

# 4. 기존 JAR 백업

새로운 JAR에 문제가 발생하면 이전 파일을 이용해 복구할 수 있어야 한다.

## 4.1 백업 디렉터리 생성

```bash
sudo mkdir -p /var/backups/marble
```

```bash
sudo chmod 700 /var/backups/marble
```

| 명령어 | 의미 |
|---|---|
| `mkdir` | 디렉터리 생성 |
| `-p` | 필요한 상위 디렉터리까지 생성 |
| `chmod` | 파일·디렉터리 권한 설정 |
| `700` | 소유자만 읽기·쓰기·접근 가능 |

## 4.2 날짜가 포함된 백업 파일명 생성

```bash
BACKUP_NAME="app.jar.$(date +%Y%m%d_%H%M%S).bak"
```

해석:

- `BACKUP_NAME`: 변수 이름
- `$()`: 명령어 실행 결과를 가져옴
- `date`: 현재 날짜·시간 출력
- `%Y%m%d_%H%M%S`: 연월일_시분초 형식

결과 예시:

```text
app.jar.20261026_093000.bak
```

## 4.3 기존 파일 백업

```bash
sudo cp -p /opt/marble/app.jar \
  "/var/backups/marble/$BACKUP_NAME"
```

- `cp`: 파일 복사
- `-p`: 파일 속성을 최대한 유지
- 첫 번째 경로: 현재 JAR
- 두 번째 경로: 백업 파일

### 검증

```bash
sudo ls -lh "/var/backups/marble/$BACKUP_NAME"
```

**JAR를 교체하기 전에 반드시 기존 정상 버전을 보관한다.**

# 5. 신규 JAR 파일 교체

SCP로 받은 파일은 다음 위치에 있다고 가정한다.

```text
/opt/marble-deploy/incoming/app.jar
```

운영 JAR를 곧바로 덮어쓰지 않고, 임시 파일로 준비한다.

## 5.1 새 파일 준비

```bash
sudo install \
  -o marble \
  -g marble \
  -m 640 \
  /opt/marble-deploy/incoming/app.jar \
  /opt/marble/app.jar.new
```

| 옵션 | 의미 |
|---|---|
| `install` | 파일 복사 및 속성 지정 |
| `-o marble` | 소유자를 `marble`로 설정 |
| `-g marble` | 그룹을 `marble`로 설정 |
| `-m 640` | 파일 권한 설정 |
| `app.jar.new` | 임시 신규 JAR |

`640` 권한은 다음과 같다.

```text
소유자: 읽기 + 쓰기
그룹: 읽기
기타: 권한 없음
```

## 5.2 신규 파일 검증

```bash
sudo ls -lh /opt/marble/app.jar.new
```

```bash
sudo sha256sum /opt/marble/app.jar.new
```

전송한 원본 JAR와 SHA-256 값이 일치하는지도 확인할 수 있다.

## 5.3 실제 파일 교체

```bash
sudo mv -f /opt/marble/app.jar.new /opt/marble/app.jar
```

- `mv`: 파일 이동 또는 이름 변경
- `-f`: 기존 대상이 있어도 확인 없이 교체
- `app.jar.new`: 준비된 새 파일
- `app.jar`: 실제 서비스에서 사용하는 파일

같은 파일시스템 내에서 준비된 JAR의 이름을 변경하면 파일 교체 시점을 명확하게 관리할 수 있다.

**JAR 파일 교체가 완료되어도 실행 중인 Spring Boot 프로세스가 자동으로 새 버전으로 바뀌지는 않는다.**

# 6. Spring Boot 서비스 재시작

Marble은 systemd로 Spring Boot JAR를 실행한다.

주요 서비스 설정:

```ini
[Service]
User=marble
WorkingDirectory=/opt/marble
ExecStart=/usr/bin/java -jar /opt/marble/app.jar
Restart=on-failure
```

| 설정 | 의미 |
|---|---|
| `User=marble` | 서비스 실행 계정 |
| `WorkingDirectory` | 실행 작업 경로 |
| `ExecStart` | Java 애플리케이션 실행 명령 |
| `Restart=on-failure` | 비정상 종료 시 재시작 정책 |

## 6.1 서비스 재시작

```bash
sudo systemctl restart marble
```

기존 프로세스를 종료하고 새로운 JAR를 사용해 서비스를 다시 시작하도록 요청한다.

## 6.2 실행 상태 확인

```bash
sudo systemctl is-active marble
```

정상 결과:

```text
active
```

## 6.3 포트 확인

```bash
sudo ss -lntp | grep ':8080'
```

| 명령어 | 의미 |
|---|---|
| `ss` | 소켓 상태 조회 |
| `-l` | LISTEN 중인 소켓 |
| `-n` | 숫자로 주소·포트 표시 |
| `-t` | TCP |
| `-p` | 프로세스 정보 표시 |
| `grep` | 원하는 문자열 검색 |

### 핵심

`systemctl is-active`가 `active`라고 해서 실제 애플리케이션 기능까지 정상이라는 의미는 아니다.

따라서 Health Check가 추가로 필요하다.

# 7. Health Check

## 7.1 기본 검증

```bash
curl -fsS http://127.0.0.1:8080/health
```

Marble 애플리케이션의 `/health`가 HTTP 200 응답을 반환하는지 확인한다.

## 7.2 Health Check를 여러 번 반복하는 이유

Spring Boot는 시작하는 데 시간이 필요할 수 있다.

서비스 재시작 직후 첫 번째 HTTP 요청이 실패했다고 곧바로 배포 실패로 처리하면 정상적인 시작 지연을 장애로 판단할 수 있다.

### 반복 확인 예시

```bash
healthy=0

for i in {1..12}; do
    if curl -fsS --max-time 3 \
      http://127.0.0.1:8080/health; then

        healthy=1
        break
    fi

    sleep 5
done

test "$healthy" -eq 1
```

| 구문 | 의미 |
|---|---|
| `healthy=0` | 정상 확인 전 초기값 |
| `for` | 반복문 |
| `{1..12}` | 최대 12회 반복 |
| `if` | 조건 검사 |
| `curl` | HTTP 요청 |
| `healthy=1` | 정상 상태 표시 |
| `break` | 반복 종료 |
| `sleep 5` | 5초 대기 |
| `test ... -eq 1` | 최종 결과 확인 |

### 반드시 기억할 점

**배포 완료는 단순히 JAR를 복사하고 재시작했다는 뜻이 아니라, 새 서비스가 정상적으로 응답하는지 검증했다는 뜻이다.**

다만 `/health` HTTP 200만으로 모든 비즈니스 기능, DB 연결 및 로드밸런서 경유 트래픽까지 정상임을 보장하지는 않는다.

# 8. 배포 스크립트의 기본 구조

앞에서 실습한 여러 Linux 명령어를 하나의 Bash 스크립트로 작성할 수 있다.

예시 파일:

```text
/usr/local/sbin/marble-deploy
```

### 핵심 코드

```bash
#!/usr/bin/env bash
set -euo pipefail

INCOMING="/opt/marble-deploy/incoming/app.jar"
LIVE="/opt/marble/app.jar"
BACKUP_DIR="/var/backups/marble"

# 1. 파일 확인
test -s "$INCOMING"
test -s "$LIVE"

# 2. 기존 JAR 백업
mkdir -p "$BACKUP_DIR"
chmod 700 "$BACKUP_DIR"

BACKUP_FILE="$BACKUP_DIR/app.jar.$(date +%Y%m%d_%H%M%S).bak"
cp -p "$LIVE" "$BACKUP_FILE"

# 3. 신규 JAR 준비 및 교체
install -o marble -g marble -m 640 \
  "$INCOMING" "$LIVE.new"

mv -f "$LIVE.new" "$LIVE"

# 4. 서비스 재시작
systemctl restart marble

# 5. Health Check
for i in {1..12}; do
    if systemctl is-active --quiet marble &&
       curl -fsS --max-time 3 \
         http://127.0.0.1:8080/health > /dev/null; then

        echo "DEPLOY SUCCESS"
        exit 0
    fi

    sleep 5
done

echo "DEPLOY FAILED" >&2
exit 1
```

### 주요 문법 해석

| 문법 | 의미 |
|---|---|
| `#!/usr/bin/env bash` | Bash로 스크립트 실행 |
| `set -e` | 일반적인 명령 실패 시 실행 중단 |
| `set -u` | 정의되지 않은 변수 사용 방지 |
| `set -o pipefail` | 파이프라인 내부 명령의 실패 감지 |
| `INCOMING=...` | 변수에 경로 저장 |
| `"$INCOMING"` | 변수 값 사용 |
| `test -s` | 파일이 있고 크기가 0보다 큰지 확인 |
| `cp -p` | 기존 파일 백업 |
| `install` | 파일 복사와 권한 설정 |
| `mv -f` | 파일 교체 |
| `systemctl restart` | 서비스 재시작 |
| `curl` | HTTP 정상 여부 확인 |
| `exit 0` | 성공 |
| `exit 1` | 실패 |

### 왜 `exit 0`, `exit 1`이 중요할까?

Jenkins는 Shell 명령어의 종료 코드를 통해 작업 성공과 실패를 구분할 수 있다.

```text
exit 0 → 성공 → 다음 Stage 진행

exit 1 → 실패 → Pipeline 중단
```

**이 스크립트는 자동 복구 기능이 없는 학습용 기본 예시다.** Health Check가 실패하면 Jenkins에 실패를 전달하지만, 이전 JAR를 자동 복원하지는 않는다.

스크립트는 LAB 서버에서 검증한 뒤 사용해야 하며, 운영 적용 전에는 파일 무결성·백업 충돌 방지·최소 권한·트래픽 처리·복구 절차를 보강해야 한다.

# 9. Jenkins에서 원격 배포 스크립트 실행

Jenkins가 WAS에 접속해 배포 스크립트를 실행할 수 있다.

### 기본 SSH 명령

```bash
ssh marble-deploy@LAB_WAS01_IP \
  'sudo -n /usr/local/sbin/marble-deploy'
```

| 구문 | 의미 |
|---|---|
| `ssh` | WAS 서버 연결 |
| `marble-deploy@...` | 배포 전용 계정 |
| `sudo -n` | 비밀번호 입력 없이 sudo 실행 |
| `marble-deploy` 스크립트 | JAR 백업·교체·재시작·검증 |

### 계정 권한 설계

일반 배포 계정에게 모든 root 권한을 주기보다는 지정된 배포 스크립트만 실행하도록 허용한다.

예시 sudoers:

```text
marble-deploy ALL=(root) NOPASSWD: /usr/local/sbin/marble-deploy ""
```

스크립트는 root 소유로 관리하고 일반 배포 계정이 수정할 수 없게 해야 한다.

또한 위 설정은 비밀번호 없이 해당 스크립트를 실행할 권한을 부여하므로, 스크립트 내부에서 읽는 파일·경로와 외부 입력도 안전하게 관리해야 한다.

# 10. WAS01 → WAS02 순차 배포

## 왜 순차 배포를 사용할까?

WAS01과 WAS02를 동시에 재시작하면 두 서버 모두 요청을 처리하지 못할 수 있다.

따라서 한 서버의 배포와 검증이 끝난 후 다음 서버를 배포한다.

```text
WAS01 배포
      |
      ├── 실패 → WAS02 배포 중단
      |
      └── 성공
            |
            v
        WAS02 배포
            |
            ├── 실패 → 배포 실패
            |
            └── 성공 → 배포 완료
```

### 장점

- 두 서버를 동시에 재시작하는 상황을 피할 수 있다.
- WAS01에서 오류가 발생하면 WAS02 배포를 중단할 수 있다.
- 단계별 로그 분석이 쉽다.

### 주의할 점

순차 배포만으로는 완전한 무중단 배포가 보장되지 않는다.

실제 운영에서는 로드밸런서가 배포 중인 WAS로 요청을 전달하지 않도록 하는 조치, 기존 연결 처리, 배포 후 재등록 등을 고려해야 한다.

또한 WAS01 배포는 성공했지만 WAS02가 실패하면 두 서버 버전이 서로 다를 수 있다.

# 11. Jenkinsfile 왕초보용 구조

다음은 **Jenkins에서 WAS01/02의 배포 스크립트를 순서대로 실행한다는 원리를 보여주는 최소 예시**다.

```groovy
stage('Deploy WAS01') {
    steps {
        sh 'ssh marble-deploy@LAB_WAS01_IP "sudo -n /usr/local/sbin/marble-deploy"'
    }
}

stage('Deploy WAS02') {
    steps {
        sh 'ssh marble-deploy@LAB_WAS02_IP "sudo -n /usr/local/sbin/marble-deploy"'
    }
}
```

### 코드 해석

| 코드 | 의미 |
|---|---|
| `stage('Deploy WAS01')` | WAS01 배포 단계 |
| `steps` | 실제 실행 작업 |
| `sh` | Linux 명령어 실행 |
| `ssh` | WAS 서버 연결 |
| `sudo -n` | 배포 스크립트 실행 |
| `stage('Deploy WAS02')` | 두 번째 WAS 배포 단계 |

위 두 Stage는 전체 Jenkinsfile의 `stages` 안에 추가하는 부분 코드이다.

실제 사용하려면 Jenkins Credentials를 이용한 SSH 인증, 신뢰할 수 있는 Host Key 등록, 사전 파일 전송이 필요하다.

# 12. CI/CD Jenkinsfile은 반드시 분리해야 할까?

**아니다. Jenkinsfile 하나로 CI와 CD를 모두 관리할 수도 있다.**

## 방식 A — 하나로 통합

```text
Jenkinsfile
    |
    ├── Build
    ├── Test
    ├── Package
    ├── Archive
    ├── Deploy WAS01
    └── Deploy WAS02
```

### 장점
- 전체 실행 흐름을 한눈에 볼 수 있다.
- 처음 학습하기 쉽다.
- Pipeline 관리 파일이 하나다.

### 주의
- Poll SCM 자동 실행 시 배포까지 자동으로 진행되지 않도록 조건을 설정해야 한다.
- 특정 이전 버전의 산출물을 다시 배포할 때 추가 로직이 필요할 수 있다.

## 방식 B — CI/CD 분리

```text
Jenkinsfile.ci
    |
    ├── Build
    ├── Test
    ├── Package
    └── Archive

Jenkinsfile.cd
    |
    ├── CI 산출물 선택
    ├── Deploy WAS01
    └── Deploy WAS02
```

### 장점
- 빌드와 배포를 독립적으로 실행할 수 있다.
- 승인된 CI 산출물을 선택하여 배포할 수 있다.
- 자동 빌드와 운영 배포의 권한·실행 시점을 구분하기 쉽다.

### 이번 학습의 선택

처음에는 원리를 이해하기 위해 간단한 구조로 학습한다.

기존 `Jenkinsfile.ci`는 유지하고, CD 실습을 별도 Job으로 검증할 수 있다. 이후 원하면 단일 Jenkinsfile에 CI와 CD를 통합할 수 있다.

**Jenkinsfile을 하나로 만들든 분리하든, 안전한 배포와 장애 복구가 더 중요하다.**

# 13. CI 산출물을 CD에서 다시 사용하는 이유

CI가 이미 `app.jar`를 빌드하고 테스트했는데, CD에서 다시 빌드하면 결과가 달라질 가능성이 있다.

따라서 CD는 가능하면 **CI에서 검증한 바로 그 산출물**을 사용해야 한다.

Jenkins에서 별도 Job을 사용하는 경우 `copyArtifacts` 기능을 활용할 수 있다.

```groovy
copyArtifacts(
    projectName: 'marble-ci',
    selector: specific("${params.CI_BUILD_NUMBER}"),
    filter: 'build/libs/app.jar'
)
```

| 문법 | 역할 |
|---|---|
| `copyArtifacts` | 다른 Jenkins Job의 산출물 가져오기 |
| `projectName` | 산출물을 만든 Job |
| `selector` | 어떤 빌드의 산출물을 선택할지 지정 |
| `specific` | 특정 빌드 번호 선택 |
| `filter` | 가져올 파일 선택 |

이 코드를 사용하려면 Copy Artifact Plugin과 Job 간 접근 권한 등 사전 설정이 필요하다.

# 14. 배포 장애 대응

## 장애 ① SSH 인증 실패

```text
Permission denied (publickey)
```

확인할 사항:

- Jenkins Credential
- SSH 개인 키
- WAS `authorized_keys`
- 원격 계정
- Host Key 신뢰 설정

## 장애 ② SCP 권한 오류

```text
scp: Permission denied
```

확인 명령:

```bash
ls -ld /opt/marble-deploy/incoming
```

배포 계정이 해당 디렉터리에 파일을 기록할 권한이 있는지 확인한다.

## 장애 ③ Spring Boot 재시작 실패

```bash
sudo systemctl status marble
```

```bash
sudo journalctl -u marble -n 100 --no-pager
```

`journalctl` 옵션:

- `-u marble`: marble 서비스 로그
- `-n 100`: 최근 100줄
- `--no-pager`: 페이지 도구 없이 출력

주요 원인:

- JDK 버전 불일치
- 설정 파일 누락
- 잘못된 JAR 파일
- DB 연결 실패
- 8080 포트 충돌

## 장애 ④ Health Check 실패

```bash
sudo ss -lntp | grep ':8080'
```

```bash
curl -v --max-time 5 http://127.0.0.1:8080/health
```

```bash
sudo journalctl -u marble -n 100 --no-pager
```

점검 순서:

```text
서비스 실행 상태
      ↓
포트 LISTEN 여부
      ↓
HTTP 응답 확인
      ↓
애플리케이션 로그 분석
      ↓
필요 시 DB·설정 확인
```

## 장애 ⑤ WAS01 성공, WAS02 실패

```text
WAS01 → 신규 버전
WAS02 → 기존 버전 또는 장애 상태
```

이런 상황에서는 배포를 즉시 완료로 처리하면 안 된다.

원인을 분석하고, 다음 교시에서 배우는 Rollback 정책에 따라 두 WAS의 상태를 일관되게 복구해야 한다.

# 16. 최종 핵심 정리

1. CD는 CI 산출물을 실제 배포 환경에 적용하고 검증하는 과정이다.
2. 신규 JAR 교체 전 기존 JAR를 백업한다.
3. 새로운 JAR는 임시 파일로 준비한 뒤 교체한다.
4. 파일을 바꿨다면 Spring Boot 서비스를 재시작해야 새 코드가 실행된다.
5. 서비스 프로세스 실행 상태와 실제 HTTP 정상 응답은 구분해야 한다.
6. Health Check는 재시도를 포함해 구성할 수 있다.
7. WAS01 성공 후 WAS02를 배포하는 방식이 순차 배포다.
8. Jenkins는 Linux 배포 스크립트의 종료 코드를 통해 성공·실패를 판정한다.
9. CI와 CD를 하나의 Jenkinsfile로 만들 수도, 별도로 분리할 수도 있다.
10. 순차 배포만으로 무중단이 보장되지는 않는다.
11. 배포 실패 시 자동 복구하는 Rollback은 19장 3교시에서 진행한다.

### 면접 답변 예시

**Q. Jenkins를 이용해 Spring Boot 애플리케이션을 어떻게 배포하나요?**

Jenkins CI에서 빌드와 테스트를 통과한 실행형 JAR를 생성하고 보관합니다. 이후 CD에서 해당 산출물을 WAS 서버로 전달합니다.

WAS에서는 기존 JAR를 백업한 뒤 신규 파일로 교체하고, systemd로 Spring Boot 서비스를 재시작합니다. 이후 `/health`를 호출하여 정상 응답을 확인합니다.

WAS01의 배포가 성공하면 WAS02를 순차적으로 배포하도록 구성합니다. 장애가 발생하면 해당 단계에서 배포를 중단하고 로그를 분석하며, 다음 단계에서 자동 Rollback 기능을 추가할 계획입니다.
