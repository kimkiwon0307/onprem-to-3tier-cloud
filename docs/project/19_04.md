# Marble 프로젝트 — Jenkins CI/CD 통합 구축 가이드

**학습 범위:** 18장 CI + 19장 1\~2교시 CD
**환경:** AWS EC2, Ubuntu 24.04, Spring Boot, Gradle, Jenkins
**배포 방식:** Jenkins + SSH/SCP + systemd
**자동 Rollback:** 미구현

> 이 문서는 Marble 프로젝트의 CI/CD 구축 과정을 처음부터 복습할 수 있도록 정리한 실습 가이드다. 명령어마다 사용 목적과 주요 옵션을 설명한다.

### 2-2. Java 환경 확인

```bash
# 설치된 Java 실행 버전 확인
java -version

# Java 컴파일러(JDK) 설치 여부 확인
```

`java`는 Java 애플리케이션 실행에 필요하고, `javac`는 Java 소스코드 컴파일에 사용된다.

Jenkins 실행에 JRE만 설치된 경우, Gradle 컴파일을 위해 프로젝트에 맞는 JDK를 추가 설치해야 한다.

예를 들어 JDK 21이 필요한 환경이라면:

```bash
# 패키지 목록 갱신
sudo apt update

# JDK 21 설치
sudo apt install -y openjdk-21-jdk
```

실제 Spring Boot 프로젝트의 Java Toolchain 설정과 호환되는 버전을 확인해야 한다.

### 2-3. Git과 SSH 클라이언트 확인

```bash
# Git 설치 여부 확인
git --version

# SSH 클라이언트 확인
ssh -V

# SCP 사용 가능 여부 확인
command -v scp
```

설치되지 않은 경우:

```bash
# Git과 SSH 클라이언트 설치
sudo apt install -y git openssh-client
```

### 왜 필요한가?

- Git: GitHub에서 소스코드를 가져온다.
- Java/JDK: Gradle 빌드 및 테스트에 사용한다.
- SSH: Jenkins에서 WAS에 원격 명령을 실행한다.
- SCP: Jenkins에서 WAS로 JAR 파일을 전달한다.

```groovy
    archiveFileName = 'app.jar'
}
```

**이유:** Jenkins와 WAS 배포 스크립트에서 항상 `app.jar`라는 파일명을 사용하기 위해서다.

## 4. Gradle 빌드 명령어 이해

| 명령어                            | 목적                     |
| ------------------------------ | ---------------------- |
| `bash ./gradlew clean classes` | 기존 결과 정리 후 메인 코드 컴파일   |
| `bash ./gradlew test`          | 자동 테스트 실행              |
| `bash ./gradlew bootJar`       | Spring Boot 실행형 JAR 생성 |
| `ls -lh build/libs/`           | 생성한 JAR 확인             |
| `sha256sum build/libs/app.jar` | JAR 체크섬 확인             |

### 빌드

```bash
# 기존 빌드 결과를 정리하고 Java 코드 컴파일
bash ./gradlew clean classes \
  --no-daemon \
  --max-workers=1
```

### 테스트

```bash
# 프로젝트 자동 테스트 실행
bash ./gradlew test \
  --no-daemon \
  --max-workers=1
```

테스트 결과는 기본적으로 다음 경로에 생성된다.

```text
build/reports/tests/test/
build/test-results/test/
```

**주의:** `test`가 `NO-SOURCE`라면 실제 실행한 테스트가 없다는 뜻이다.

### JAR 생성

```bash
# Spring Boot 실행형 JAR 생성
bash ./gradlew bootJar \
  --no-daemon \
  --max-workers=1

# JAR 목록과 파일 크기 확인
ls -lh build/libs/

# app.jar가 존재하고 비어 있지 않은지 검사
test -s build/libs/app.jar

# JAR 파일의 SHA-256 확인
sha256sum build/libs/app.jar
```

### Gradle 옵션

| 옵션                | 의미                                  |
| ----------------- | ----------------------------------- |
| `--no-daemon`     | 지속 실행되는 Gradle Daemon의 재사용을 피하도록 요청 |
| `--max-workers=1` | 최대 병렬 Worker 수를 1개로 제한              |

소규모 Jenkins EC2에서 자원 사용을 줄이기 위해 설정했다.

# PART 2. Jenkins와 WAS 네트워크 연결

## 5. AWS Security Group 설정

**설정 위치: AWS Console**

Jenkins에서 WAS로 SSH 연결을 하려면 네트워크 통신이 가능해야 한다.

### WAS Security Group

| 방향      | 프로토콜 | 포트 | 허용 대상                  |
| ------- | ---- | -- | ---------------------- |
| Inbound | TCP  | 22 | Jenkins Security Group |

Jenkins Security Group의 Outbound도 WAS TCP 22 통신이 허용되어야 한다.

WAS는 Private Subnet에 있으므로 인터넷 전체에 SSH를 공개하지 않는다.

### 왜 필요한가?

Jenkins가 WAS에 JAR 파일을 전달하고 배포 명령어를 실행하기 위해서다.

### 5-1. WAS SSH 서비스 확인

**실행 서버: WAS01과 WAS02**

```bash
# SSH 서비스 상태 확인
sudo systemctl status ssh

# SSH 서비스 실행 여부 확인
sudo systemctl is-active ssh

# TCP 22번 포트 LISTEN 확인
sudo ss -lntp | grep ':22'
```

SSH 서버가 아직 설치되지 않은 LAB 환경이라면:

```bash
# SSH 서버 설치
sudo apt update
sudo apt install -y openssh-server

# SSH 서비스 자동 시작 및 즉시 실행
sudo systemctl enable --now ssh
```

기존에 SSH로 관리 중인 서버라면 불필요하게 SSH 구성을 변경하지 않는다.

### 5-2. Jenkins에서 WAS 연결 검사

**실행 서버: Jenkins EC2**

```bash
# WAS01의 SSH 포트에 TCP 연결 가능한지 확인
nc -zv -w 3 10.0.21.126 22

# WAS02의 SSH 포트에 TCP 연결 가능한지 확인
nc -zv -w 3 10.0.22.9 22
```

옵션 설명:

| 옵션     | 의미           |
| ------ | ------------ |
| `nc`   | 네트워크 연결 검사   |
| `-z`   | 포트 접근 여부만 검사 |
| `-v`   | 자세한 메시지 출력   |
| `-w 3` | 연결 대기 시간 제한  |

TCP 22 연결에 성공했다고 해서 SSH 사용자 인증까지 성공한 것은 아니다.

**실행 서버: WAS01/02 각각**

### 6-1. 서비스 상태 확인


기존 Marble 서비스에는 다음과 같은 핵심 설정이 있다고 가정한다.

```ini

# 애플리케이션 실행 디렉터리
WorkingDirectory=/opt/marble

# Spring Boot JAR 실행
ExecStart=/usr/bin/java -jar /opt/marble/app.jar

# 비정상 종료 시 재시작
Restart=on-failure
```

이미 존재하는 `marble.service`를 다시 만들 필요는 없다.

# PART 4. SSH 공개 키 인증 구축

## 9. Jenkins 배포용 SSH 키 생성

**실행 위치: 관리용 Linux PC 또는 WSL**

Jenkins와 WAS가 사용할 SSH 인증 키를 생성한다.

```bash
# SSH 키 보관용 디렉터리 생성
mkdir -p ~/.ssh

# SSH 디렉터리 권한 설정
chmod 700 ~/.ssh

# 배포 전용 Ed25519 SSH 키 생성
ssh-keygen -t ed25519 \
  -f ~/.ssh/marble_lab_cd \
  -C "marble-jenkins-cd"
```

암호를 입력할지 묻는 화면이 표시된다.

실습에서는 자동화에 맞는 키 관리 방식을 선택하되, 실제 조직에서는 개인 키 암호 및 Credentials 보관 정책을 따른다.

### 생성 파일

```text
~/.ssh/marble_lab_cd
    → 개인 키 (외부 공개 금지)

~/.ssh/marble_lab_cd.pub
    → 공개 키 (WAS에 등록)
```

### 옵션 설명

| 옵션           | 의미         |
| ------------ | ---------- |
| `-t ed25519` | SSH 키 알고리즘 |
| `-f`         | 저장 파일 이름   |
| `-C`         | 키 식별용 설명   |

### 공개 키 확인

```bash
# WAS에 등록할 공개 키 내용 확인
cat ~/.ssh/marble_lab_cd.pub
```

공개 키는 WAS01과 WAS02 모두에 등록한다.

**개인 키는 GitHub에 Commit하지 않는다.**

## 10. WAS에 공개 키 등록

**실행 서버: WAS01과 WAS02 각각**

### 10-1. SSH 디렉터리 생성

```bash
# marble-deploy 계정의 SSH 설정 디렉터리 생성
sudo install -d \
  -o marble-deploy \
  -g marble-deploy \
  -m 700 \
  /home/marble-deploy/.ssh
```

### 10-2. authorized_keys 작성

```bash
# SSH 접속을 허용할 공개 키 등록
sudo nano /home/marble-deploy/.ssh/authorized_keys
```

관리 PC에서 확인한 공개 키 내용을 **한 줄로 붙여 넣고 저장**한다.

### 10-3. 권한 설정

```bash
# 파일 소유자를 배포 계정으로 변경
sudo chown marble-deploy:marble-deploy \
  /home/marble-deploy/.ssh/authorized_keys

# 소유자만 읽기·쓰기 가능하도록 제한
sudo chmod 600 \
  /home/marble-deploy/.ssh/authorized_keys

# SSH 디렉터리 권한 재확인
sudo chmod 700 /home/marble-deploy/.ssh
```

### 왜 700과 600인가?

```text
700 : 소유자만 읽기·쓰기·접근

600 : 소유자만 읽기·쓰기
```

SSH 서버는 계정의 `.ssh` 디렉터리나 키 파일에 잘못된 권한이 있으면 인증을 거부할 수 있다.

## 11. SSH Host Key 검증

**실행 서버: WAS01/02 및 Jenkins**

SSH 사용자 인증과 별개로, 접속하려는 서버가 올바른 WAS인지 확인해야 한다.

### 11-1. WAS에서 Host Key 지문 확인

각 WAS에서:

```bash
# 서버 SSH Host Key의 지문 확인
sudo ssh-keygen -lf \
  /etc/ssh/ssh_host_ed25519_key.pub
```

출력된 지문을 안전하게 확인하고 기록한다.

### 11-2. Jenkins에서 서버 공개 Host Key 조회

```bash
# WAS01 SSH Host Key 조회
ssh-keyscan -t ed25519 10.0.21.126

# WAS02 SSH Host Key 조회
ssh-keyscan -t ed25519 10.0.22.9
```

`ssh-keyscan`은 Host Key를 조회하는 도구다.

**주의:** 조회한 결과를 바로 신뢰해서는 안 된다. 각 WAS에서 직접 확인한 지문과 일치하는지 비교해야 한다.

조회한 키의 지문을 확인하려면:

```bash
# WAS01 조회 결과의 지문 확인
ssh-keyscan -t ed25519 10.0.21.126 2>/dev/null \
  | ssh-keygen -lf -
```

### 11-3. Jenkins의 known_hosts 등록

```bash
# Jenkins SSH 설정 디렉터리 생성
sudo install -d \
  -o jenkins \
  -g jenkins \
  -m 700 \
  /var/lib/jenkins/.ssh
```

```bash
# 검증을 마친 WAS01/02의 Host Key 등록
sudo nano /var/lib/jenkins/.ssh/known_hosts
```

앞서 조회하고 지문을 확인한 두 서버의 Host Key를 입력한다.

```bash
# Jenkins 계정에 소유권 부여
sudo chown jenkins:jenkins \
  /var/lib/jenkins/.ssh/known_hosts

# known_hosts 권한 설정
sudo chmod 600 \
  /var/lib/jenkins/.ssh/known_hosts
```

이제 Jenkins는 `StrictHostKeyChecking=yes` 설정으로 서버 Host Key를 검사할 수 있다.

별도 Jenkins Agent에서 배포한다면 해당 Agent 실행 환경의 `known_hosts`도 준비해야 한다.

Jenkinsfile에 모든 Linux 명령어를 길게 넣는 대신, WAS에 배포 스크립트를 만들어 사용한다.

```text
Jenkinsfile.ci

```

**Jenkinsfile은 작업 순서와 원격 실행을 관리하고, Bash 스크립트는 WAS 내부의 실제 배포 작업을 담당한다.**

## 14. 배포 Bash 스크립트 작성

**실행 서버: WAS01과 WAS02 각각**

### 14-1. 파일 생성

```bash
# 시스템 관리 스크립트 디렉터리로 이동
cd /usr/local/sbin

# 배포 스크립트 직접 작성
sudo nano marble-deploy
```

아래 내용을 입력한다.

```bash
#!/usr/bin/env bash

# 오류 발생 시 중단, 미정의 변수 사용 방지,
# 파이프라인 내부 명령 오류 감지
set -euo pipefail

# 1. 자주 사용할 경로를 변수로 정의

# Jenkins가 전송한 신규 JAR
INCOMING="/opt/marble-deploy/incoming/app.jar"

# 실제 Spring Boot가 실행하는 JAR
LIVE="/opt/marble/app.jar"

# 기존 JAR 백업 디렉터리
BACKUP_DIR="/var/backups/marble"

# Spring Boot 정상 상태 확인 주소
HEALTH_URL="http://127.0.0.1:8080/health"


# 2. 배포 전 파일 확인

echo "=== 1. Check Files ==="

# 신규 JAR 존재 및 파일 크기 확인
test -s "$INCOMING"

# 기존 JAR 존재 및 파일 크기 확인
test -s "$LIVE"


# 3. 배포 전 기존 서비스 정상 확인

echo "=== 2. Pre Health Check ==="

# 기존 서비스가 실행 중인지 확인
systemctl is-active --quiet marble

# 현재 HTTP 응답 코드 확인
HTTP_CODE=$(curl -sS -o /dev/null \
  -w '%{http_code}' \
  --max-time 3 "$HEALTH_URL")

# HTTP 200이 아니면 배포 중단
test "$HTTP_CODE" = "200"


# 4. 기존 JAR 백업

echo "=== 3. Backup ==="

# 백업 디렉터리 생성 및 접근 권한 설정
install -d -o root -g root -m 700 "$BACKUP_DIR"

# 다른 백업과 이름이 겹치지 않도록 고유 파일명 생성
BACKUP_FILE=$(mktemp "$BACKUP_DIR/app.jar.XXXXXXXX.bak")

# 현재 사용 중인 JAR 백업
cp -p "$LIVE" "$BACKUP_FILE"

# 백업 파일 경로 출력
echo "Backup: $BACKUP_FILE"


# 5. 새로운 JAR를 임시 파일로 준비

echo "=== 4. Prepare ==="

# 배포 받은 JAR를 서비스 디렉터리에 임시 파일로 복사
# 소유자 및 파일 권한도 함께 지정
install -o marble -g marble -m 640 \
  "$INCOMING" "$LIVE.new"

# 복사한 파일의 내용이 원본과 같은지 검사
cmp -s "$INCOMING" "$LIVE.new"


# 6. 실제 서비스 JAR 교체

echo "=== 5. Replace ==="

# 준비한 JAR를 실제 실행 파일명으로 변경
mv -f "$LIVE.new" "$LIVE"


# 7. Spring Boot 서비스 재시작

echo "=== 6. Restart ==="

# 새로운 JAR로 서비스를 다시 실행
systemctl restart marble


# 8. Health Check 재시도

echo "=== 7. Health Check ==="

# 최대 12회 검사
for i in {1..12}; do

    # 서비스가 실행 중인 경우 HTTP 상태 확인
    if systemctl is-active --quiet marble; then

        # 요청 실패 시 코드가 비어 있거나 000일 수 있음
        CODE=$(curl -sS -o /dev/null \
          -w '%{http_code}' \
          --max-time 3 "$HEALTH_URL" || true)

        # 응답 코드가 정확히 200이면 성공
        if [ "$CODE" = "200" ]; then
            echo "DEPLOY SUCCESS"
            exit 0
        fi
    fi

    # 정상 응답이 아니면 5초 후 다시 확인
    sleep 5
done


# 9. 재시도 후에도 정상 응답이 없으면 실패

echo "DEPLOY FAILED" >&2

# Jenkins가 실패를 감지할 수 있도록 종료 코드 1 반환
exit 1
```

### 이 스크립트의 동작 순서

```text
신규 JAR가 있는가?
       |
       v
기존 Marble 서비스가 정상인가?
       |
       v
기존 app.jar 백업
       |
       v
신규 app.jar 준비 및 내용 비교
       |
       v
기존 app.jar 교체
       |
       v
systemctl restart marble
       |
       v
/health HTTP 200 확인
       |
       +-- 성공 → exit 0
       |
       +-- 실패 → exit 1
```

**자동 Rollback은 포함하지 않았다.**

따라서 JAR 교체 후 Health Check가 실패하면 Pipeline은 중단되지만 새 JAR가 자동으로 이전 버전으로 되돌아가지는 않는다.

## 15. 배포 스크립트 명령어 해설

| 명령어                   | 목적                   |
| --------------------- | -------------------- |
| `set -euo pipefail`   | 기본 오류 감지             |
| `test -s`             | 파일 존재 및 크기 검사        |
| `systemctl is-active` | 서비스 실행 상태 확인         |
| `curl`                | HTTP 상태 코드 조회        |
| `install -d`          | 디렉터리 생성 및 권한 설정      |
| `mktemp`              | 고유한 백업 파일명 생성        |
| `cp -p`               | 기존 JAR 백업            |
| `install -o -g -m`    | 파일 복사 및 소유자·권한 지정    |
| `cmp -s`              | 두 파일 내용 비교           |
| `mv -f`               | 준비된 JAR로 교체          |
| `systemctl restart`   | Spring Boot 재시작      |
| `sleep 5`             | 다음 Health Check까지 대기 |
| `exit 0`              | 성공 종료                |
| `exit 1`              | 실패 종료                |

### `cp`와 `mv` 차이

```bash
# 원본 파일은 남기고 복사본 생성
cp old.jar backup.jar

# 파일 이름 변경 또는 위치 이동
mv new.jar app.jar
```

### `install`을 사용하는 이유

```bash
# 파일을 복사하면서 소유자와 권한 설정
install -o marble -g marble -m 640 \
  incoming.jar app.jar.new
```

`cp`로 복사한 뒤 `chown`, `chmod`를 각각 실행하는 대신 소유자와 권한을 함께 지정할 수 있다.

### `cmp -s`를 사용하는 이유

```bash
# 두 파일이 실제로 같은 내용인지 검사
cmp -s original.jar copied.jar
```

복사한 JAR의 내용이 원본과 같은지 확인한다.

### Health Check를 반복하는 이유

Spring Boot는 시작하는 데 시간이 필요하다.

재시작 직후 HTTP 요청이 실패하더라도 잠시 후 정상적으로 실행될 수 있으므로 제한된 횟수로 재검사한다.

## 17. 배포 계정의 sudo 권한 설정

**실행 서버: WAS01과 WAS02 각각**

Jenkins는 `marble-deploy` 사용자로 WAS에 SSH 접속한다.

하지만 애플리케이션을 재시작하고 root 소유 디렉터리에 백업을 만들려면 관리자 권한이 필요하다.

그래서 배포 스크립트만 제한적으로 sudo 실행을 허용한다.

### 17-1. sudoers 파일 생성

```bash
# marble-deploy 계정의 sudo 권한 설정
sudo nano /etc/sudoers.d/marble-deploy
```

내용:

```text
marble-deploy ALL=(root) NOPASSWD: /usr/local/sbin/marble-deploy ""
```

### 설정 의미

| 부분              | 의미                 |
| --------------- | ------------------ |
| `marble-deploy` | 적용할 사용자            |
| `ALL`           | 호스트 조건             |
| `(root)`        | root 권한으로 실행       |
| `NOPASSWD`      | sudo 비밀번호 입력 없이 실행 |
| 마지막 스크립트 경로     | 실행을 허용할 명령         |
| `""`            | 추가 인자 없이 실행하도록 제한  |

### 17-2. 권한 및 문법 검증

```bash
# sudoers 파일 권한 설정
sudo chmod 440 /etc/sudoers.d/marble-deploy

# sudoers 문법 검사
sudo visudo -cf /etc/sudoers.d/marble-deploy
```

정상이라면 문법 검사가 성공해야 한다.

### 주의

`marble-deploy`에게 모든 sudo 명령을 허용하는 설정은 사용하지 않는다.

```text
# 피해야 할 예
marble-deploy ALL=(ALL) NOPASSWD: ALL
```

# PART 7. Jenkinsfile CI/CD 통합 구축

## 18. 통합 Jenkinsfile 작성

**실행 위치: 개발자 PC의 Marble GitHub 프로젝트**

기존 학습 파일인 `Jenkinsfile.ci`를 CI/CD 통합 파일로 사용한다.

```bash
# 프로젝트 디렉터리 이동
cd ~/marble_project

# Jenkins Pipeline 파일 수정
nano Jenkinsfile.ci
```

### 최종 Jenkinsfile

```groovy
// Marble 통합 CI/CD Pipeline
pipeline {

    // Jenkins에서 실행 가능한 노드 사용
    agent any

    // Pipeline 실행 옵션
    options {

        // 자동 Checkout을 생략하고 Checkout Stage에서 직접 수행
        skipDefaultCheckout(true)

        // 같은 Job의 빌드가 동시에 실행되지 않도록 설정
        disableConcurrentBuilds()

        // Console Output에 시간 표시
        timestamps()
    }

    // GitHub 변경 감지
    triggers {

        // 약 5분마다 SCM 변경 확인
        // 새로운 변경이 있으면 Pipeline 실행
        pollSCM('H/5 * * * *')
    }

    // 배포 대상 WAS IP를 변수로 관리
    environment {
        WAS01 = '10.0.21.126'
        WAS02 = '10.0.22.9'
    }

    stages {

        // =====================================
        // 1. GitHub 소스코드 가져오기
        // =====================================
        stage('Checkout') {
            steps {

                // Job에 설정된 GitHub 저장소 Checkout
                checkout scm
            }
        }

        // =====================================
        // 2. Java 컴파일
        // =====================================
        stage('Build') {
            steps {

                // Gradle Wrapper로 빌드
                sh 'bash ./gradlew clean classes --no-daemon --max-workers=1'
            }
        }

        // =====================================
        // 3. 자동 테스트
        // =====================================
        stage('Test') {
            steps {

                // Gradle 테스트 실행
                sh 'bash ./gradlew test --no-daemon --max-workers=1'

                // 테스트 XML 결과를 Jenkins에 등록
                // 테스트 결과가 없으면 실패
                junit testResults: 'build/test-results/test/TEST-*.xml',
                      allowEmptyResults: false
            }
        }

        // =====================================
        // 4. Spring Boot JAR 생성
        // =====================================
        stage('Package') {
            steps {

                // 실행형 JAR 생성
                sh 'bash ./gradlew bootJar --no-daemon --max-workers=1'

                // 생성된 app.jar 존재 여부 확인
                sh 'test -s build/libs/app.jar'
            }
        }

        // =====================================
        // 5. 빌드 산출물 보관
        // =====================================
        stage('Archive') {
            steps {

                // Jenkins 빌드 기록에 JAR 보관
                archiveArtifacts(
                    artifacts: 'build/libs/app.jar',
                    fingerprint: true,
                    allowEmptyArchive: false
                )
            }
        }

        // =====================================
        // 6. WAS01 배포
        // =====================================
        stage('Deploy WAS01') {
            steps {

                // Jenkins Credentials에 등록한 SSH 개인 키 사용
                withCredentials([
                    sshUserPrivateKey(
                        credentialsId: 'marble-lab-ssh',
                        keyFileVariable: 'SSH_KEY',
                        usernameVariable: 'SSH_USER'
                    )
                ]) {

                    // 여러 Linux 명령어 실행
                    sh '''
                        set -eu

                        # WAS01 배포 시작 메시지
                        echo "=== Deploy WAS01: $WAS01 ==="

                        # Jenkins에서 WAS01으로 app.jar 전송
                        scp -i "$SSH_KEY" -o BatchMode=yes -o StrictHostKeyChecking=yes \
                          build/libs/app.jar \
                          "$SSH_USER@$WAS01:/opt/marble-deploy/incoming/app.jar"

                        # WAS01에서 배포 스크립트 실행
                        # 기존 JAR 백업 → JAR 교체 → 서비스 재시작 → Health Check
                        ssh -i "$SSH_KEY" -o BatchMode=yes -o StrictHostKeyChecking=yes \
                          "$SSH_USER@$WAS01" \
                          'sudo -n /usr/local/sbin/marble-deploy'
                    '''
                }
            }
        }

        // =====================================
        // 7. WAS02 배포
        // =====================================
        stage('Deploy WAS02') {
            steps {

                // WAS02 접속용 SSH Credentials 사용
                withCredentials([
                    sshUserPrivateKey(
                        credentialsId: 'marble-lab-ssh',
                        keyFileVariable: 'SSH_KEY',
                        usernameVariable: 'SSH_USER'
                    )
                ]) {

                    sh '''
                        set -eu

                        # WAS02 배포 시작 메시지
                        echo "=== Deploy WAS02: $WAS02 ==="

                        # Jenkins에서 WAS02로 app.jar 전송
                        scp -i "$SSH_KEY" -o BatchMode=yes -o StrictHostKeyChecking=yes \
                          build/libs/app.jar \
                          "$SSH_USER@$WAS02:/opt/marble-deploy/incoming/app.jar"

                        # WAS02에서 배포 스크립트 실행
                        ssh -i "$SSH_KEY" -o BatchMode=yes -o StrictHostKeyChecking=yes \
                          "$SSH_USER@$WAS02" \
                          'sudo -n /usr/local/sbin/marble-deploy'
                    '''
                }
            }
        }
    }

    // Pipeline 종료 후 실행
    post {

        // 전체 작업 성공 시
        success {
            echo 'Marble CI/CD SUCCESS'
        }

        // 빌드 또는 배포 실패 시
        failure {
            echo 'Marble CI/CD FAILED - Check Console Output'
        }
    }
}
```

### 왜 이 구조를 선택했나?

1. CI와 CD의 전체 흐름을 하나의 Jenkinsfile에서 볼 수 있다.
2. WAS01/02의 IP는 `environment`에서 변수로 관리한다.
3. WAS01 배포에 실패하면 WAS02로 진행하지 않는다.
4. 실제 배포 명령은 WAS의 Bash 스크립트가 담당한다.
5. 자동 Rollback을 추가하지 않아 학습 범위를 제한할 수 있다.

**이 Jenkinsfile은 별도의 DEPLOY 체크박스가 없는 자동 배포형이다.**

따라서 Poll SCM이 새 Commit을 감지하거나 Jenkins Job을 수동 실행하면, 앞 단계가 모두 성공할 경우 배포까지 진행한다.

## 19. Jenkinsfile 핵심 문법 해설

### 19-1. pipeline / agent

```groovy
pipeline {
    agent any
}
```

- `pipeline`: 전체 작업 정의
- `agent any`: 실행 가능한 Jenkins 노드 사용

### 19-2. stages / stage / steps

```groovy
stages {
    stage('Build') {
        steps {
            sh 'bash ./gradlew clean classes'
        }
    }
}
```

- `stages`: 전체 단계 묶음
- `stage`: 하나의 작업 단위
- `steps`: 실제 작업
- `sh`: Linux 명령어 실행

### 19-3. environment

```groovy
environment {
    WAS01 = '10.0.21.126'
    WAS02 = '10.0.22.9'
}
```

여러 Stage에서 사용할 변수를 지정한다.

Shell에서는 다음과 같이 참조한다.

```bash
# WAS01 환경 변수 사용
echo "$WAS01"

# WAS02 환경 변수 사용
echo "$WAS02"
```

### 19-4. withCredentials

```groovy
withCredentials([
    sshUserPrivateKey(
        credentialsId: 'marble-lab-ssh',
        keyFileVariable: 'SSH_KEY',
        usernameVariable: 'SSH_USER'
    )
])
```

Jenkins Credentials에 등록한 SSH 인증 정보를 사용한다.

- `SSH_KEY`: 개인 키 임시 파일의 경로
- `SSH_USER`: SSH 사용자명

### 19-5. SCP

```bash
# WAS에 JAR 파일 전송
scp -i "$SSH_KEY" \
  build/libs/app.jar \
  "$SSH_USER@$WAS01:/opt/marble-deploy/incoming/app.jar"
```

실제 Jenkinsfile에서는 `BatchMode`와 `StrictHostKeyChecking` 옵션도 사용한다.

### 19-6. SSH

```bash
# WAS의 배포 스크립트 실행
ssh -i "$SSH_KEY" \
  "$SSH_USER@$WAS01" \
  'sudo -n /usr/local/sbin/marble-deploy'
```

SCP는 파일 전송이고, SSH는 원격 배포 스크립트 실행이다.

# PART 9. GitHub 반영 및 자동 실행

## 22. Jenkinsfile Commit & Push

**실행 위치: 개발자 PC**

```bash
# 프로젝트 디렉터리 이동
cd ~/marble_project

# 변경 파일 확인
git status

# 통합 Jenkinsfile 등록
git add Jenkinsfile.ci

# build.gradle도 수정했다면 추가
git add build.gradle

# 변경 사항 Commit
git commit -m "ci: integrate marble build test and was deployment"

# GitHub master 브랜치에 Push
git push origin master
```

### 이후 동작

```text
GitHub Push
    ↓
Jenkins Poll SCM
    ↓
새 Commit 감지
    ↓
Checkout
    ↓
Build
    ↓
Test
    ↓
Package
    ↓
Archive
    ↓
Deploy WAS01
    ↓
Deploy WAS02
```

`H/5 * * * *`는 약 5분 간격으로 변경을 검사하며, Push 직후 무조건 즉시 실행한다는 의미는 아니다.

새 Commit이 감지되어 실행되면 CI와 CD가 하나의 Pipeline 안에서 이어진다.

**Jenkinsfile이나 README만 수정해서 Push해도 Pipeline이 시작될 수 있으므로, 배포 자동 실행 설정을 알고 사용해야 한다.**

### 대표 장애

| 장애              | 원인 후보          | 확인 방법               |
| --------------- | -------------- | ------------------- |
| Checkout 실패     | GitHub PAT·브랜치 | Jenkins Credentials |
| Build 실패        | Java·Gradle 환경 | Console Output      |
| Test 실패         | 테스트 코드·의존성     | JUnit 보고서           |

| SCP 권한 오류       | 수신 디렉터리 권한     | `ls -ld`            |
| sudo 실패         | sudoers 설정 오류  | `visudo -cf`        |
| 서비스 재시작 실패      | Java·환경 변수·JAR | `journalctl`        |
| Health Check 실패 | 앱 기동·DB·포트     | `curl`, `ss`, 로그    |

### Health Check 실패 시

```bash
# 현재 서비스 상태 확인
```

# PART 13. 기술 선택 이유

## 28. 왜 Jenkins를 사용했는가?

- GitHub 변경 사항을 감지해 CI를 자동 실행할 수 있다.
- Gradle을 이용해 빌드·테스트·JAR 생성을 자동화할 수 있다.
- SSH/SCP를 통해 AWS EC2 기반 WAS에 배포할 수 있다.
- Jenkinsfile로 작업 흐름을 코드로 관리할 수 있다.
- Jenkins 서버의 설치·운영과 CI/CD 동작 원리를 함께 학습할 수 있다.

## 29. 왜 Poll SCM을 사용했는가?

GitHub Webhook을 사용하지 않고 Jenkins가 GitHub의 변경 사항을 주기적으로 확인하도록 구성했다.

Jenkins에 외부에서 접근할 수 있는 Webhook 수신 주소를 별도로 구성하지 않아도 되는 장점이 있다.

단, 변경 감지까지 지연이 발생할 수 있고 GitHub를 주기적으로 조회한다.

## 30. 왜 SCP를 사용했는가?

- 기존 SSH 인프라를 활용할 수 있다.
- 설정과 파일 전송 원리를 이해하기 쉽다.
- 소규모 WAS01/02 구조에 적용하기 쉽다.
- Jenkins Credentials로 인증 정보를 관리할 수 있다.

대안으로 S3 + SSM, CodeDeploy 등을 사용할 수 있다.

## 31. 왜 순차 배포를 사용했는가?

WAS01과 WAS02를 동시에 재시작하지 않고, 첫 번째 서버의 배포와 기본 Health Check가 성공한 뒤 다음 서버를 배포하기 위해서다.

단, Apache의 트래픽 제외·복귀 기능까지 구현한 것은 아니므로 무중단 배포를 보장하지 않는다.
