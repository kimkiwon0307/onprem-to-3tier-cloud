# Marble 프로젝트 — Jenkins CD 구축 (2교시 핵심 정리)

## 1. 학습 목표

Jenkins CI에서 생성한 `app.jar`를 WAS01/02에 자동으로 배포하는 과정을 이해한다.

**최종 배포 흐름**

```text
Jenkins CI 성공
      ↓
build/libs/app.jar 생성
      ↓
Jenkins Credentials로 SSH 인증
      ↓
SCP로 WAS01에 JAR 전송
      ↓
SSH로 WAS01 배포 스크립트 실행
      ↓
기존 JAR 백업 → 신규 JAR 교체
      ↓
systemd 서비스 재시작
      ↓
/health 정상 확인
      ↓
WAS02 동일 작업
      ↓
Jenkins Pipeline SUCCESS
```

### 서버 정보

| 서버 | IP | 역할 |
|---|---|---|
| Jenkins | Jenkins EC2 | 빌드 및 배포 실행 |
| WAS01 | `10.0.21.126` | Spring Boot |
| WAS02 | `10.0.22.9` | Spring Boot |

## 2. SSH 인증 구조

Jenkins에서 WAS로 자동 접속하려면 SSH 공개 키 인증이 필요하다.

```text
[Jenkins 서버]
개인 키 (Private Key)
        |
        | SSH 접속
        v
[WAS01 / WAS02]
공개 키 (Public Key)
authorized_keys
```

| 구분 | 위치 |
|---|---|
| 개인 키 | Jenkins Credentials |
| 공개 키 | WAS01/02의 `authorized_keys` |
| SSH 접속 사용자 | `marble-deploy` |
| Jenkins Credential ID | `marble-was-ssh` |

### 실제 SSH 키 경로

```text
/var/lib/jenkins/.ssh/marble_deploy
→ 개인 키

/var/lib/jenkins/.ssh/marble_deploy.pub
→ 공개 키
```

키를 생성할 때 사용한 명령어:

```bash
# Jenkins 계정으로 SSH 키 쌍 생성
sudo -u jenkins ssh-keygen -t ed25519 \
  -f /var/lib/jenkins/.ssh/marble_deploy \
  -C "jenkins-marble-deploy" \
  -N ""
```

옵션 설명:

- `ssh-keygen`: SSH 키 생성
- `-t ed25519`: 키 알고리즘
- `-f`: 키 저장 경로
- `-C`: 구분용 설명
- `-N ""`: 키 암호 없이 생성

**중요:** 현재는 SSH 인증과 배포가 성공했으므로 키를 다시 생성하지 않는다.

## 3. Jenkins Credentials

Jenkins에서 SSH 개인 키와 사용자명을 관리한다.

```text
Kind       : SSH Username with private key
ID         : marble-was-ssh
Username   : marble-deploy
Private Key: SSH 개인 키
```

Jenkinsfile에서는 다음과 같이 사용한다.

```groovy
withCredentials([
    sshUserPrivateKey(
        credentialsId: 'marble-was-ssh',
        keyFileVariable: 'SSH_KEY',
        usernameVariable: 'SSH_USER'
    )
])
```

### 각 항목의 의미

| 항목 | 역할 |
|---|---|
| `credentialsId` | 사용할 Jenkins Credential의 ID |
| `SSH_KEY` | 개인 키 임시 파일 경로를 담는 변수 |
| `SSH_USER` | SSH 접속 사용자명을 담는 변수 |

**Credential ID와 Username은 다르다.**

```text
Credential ID = marble-was-ssh
Linux Username = marble-deploy
```

## 4. Jenkins와 WAS 연결 확인

**실행 위치: Jenkins EC2**

```bash
# WAS01 SSH 포트 연결 확인
nc -zv -w 3 10.0.21.126 22

# WAS02 SSH 포트 연결 확인
nc -zv -w 3 10.0.22.9 22
```

- `nc`: 네트워크 연결 검사
- `-z`: 포트 접근 검사
- `-v`: 상세 정보 출력
- `-w 3`: 3초 연결 제한

AWS Security Group에서 WAS TCP 22번 포트를 Jenkins Security Group에 허용해야 한다.

이 명령은 네트워크 연결만 검사하며, SSH 인증 성공까지 보장하지는 않는다.

## 5. SCP — JAR 파일 전송

Jenkins에서 WAS01로 `app.jar`를 전송한다.

```bash
# Jenkins에서 WAS01로 신규 JAR 전송
scp -i "$SSH_KEY" \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  build/libs/app.jar \
  "$SSH_USER@$WAS01:/opt/marble-deploy/incoming/app.jar"
```

### 명령어 설명

| 명령어 | 의미 |
|---|---|
| `scp` | 원격 서버로 파일 복사 |
| `-i` | 사용할 SSH 개인 키 지정 |
| `BatchMode=yes` | 대화형 인증 입력 방지 |
| `StrictHostKeyChecking=yes` | 등록된 서버 Host Key 검증 |
| `build/libs/app.jar` | Jenkins의 빌드 결과물 |
| `incoming/app.jar` | WAS에 신규 JAR를 받을 위치 |

### 왜 별도 디렉터리로 전송할까?

```text
/opt/marble-deploy/incoming/app.jar
→ 새로 전송받는 JAR

/opt/marble/app.jar
→ Spring Boot가 실제 사용하는 JAR
```

파일 전송과 실제 애플리케이션 교체를 분리하기 위해서다.

## 6. SSH — WAS 배포 스크립트 실행

JAR 전송이 끝나면 WAS에서 배포 스크립트를 실행한다.

```bash
# WAS01의 배포 스크립트 원격 실행
ssh -i "$SSH_KEY" \
  -o BatchMode=yes \
  -o StrictHostKeyChecking=yes \
  "$SSH_USER@$WAS01" \
  'sudo -n /usr/local/sbin/marble-deploy'
```

### 핵심 명령어

```bash
sudo -n /usr/local/sbin/marble-deploy
```

- `sudo`: 관리자 권한 실행
- `-n`: 비밀번호를 묻지 않고 실행
- `marble-deploy`: 실제 WAS 배포 스크립트

WAS에는 `marble-deploy` Linux 계정이 해당 스크립트를 제한적으로 실행할 수 있도록 sudoers 설정이 필요하다.

**SCP는 파일 전송, SSH는 원격 명령 실행이다.**

## 7. WAS 배포 스크립트

배포 스크립트 위치:

```text
/usr/local/sbin/marble-deploy
```

### 왕초보용 핵심 예제

아래는 동작 원리를 이해하기 위한 간단한 예시다. 실제 구축한 서버의 스크립트가 다를 수 있으므로 성공한 기존 파일을 덮어쓰지 않는다.

```bash
#!/bin/bash

# 명령어 실패 시 스크립트 중단
set -e

# 기존 JAR 백업
cp /opt/marble/app.jar \
   /var/backups/marble/app.jar.bak

# 신규 JAR 복사 및 권한 설정
install -o marble -g marble -m 640 \
  /opt/marble-deploy/incoming/app.jar \
  /opt/marble/app.jar.new

# 신규 JAR로 교체
mv -f /opt/marble/app.jar.new \
  /opt/marble/app.jar

# Spring Boot 서비스 재시작
systemctl restart marble

# HTTP Health Check
# 기동 지연 시 최대 5회 재시도
curl -f --retry 5 --retry-delay 3 \
  --retry-connrefused --max-time 5 \
  http://127.0.0.1:8080/health

# 성공 메시지
echo "DEPLOY SUCCESS"
```

**전제:** 기존 JAR와 신규 JAR가 존재하고 `/var/backups/marble` 디렉터리가 미리 생성되어 있어야 한다. 또한 이 예제의 백업 파일은 배포할 때마다 덮어써질 수 있다.

### 중요한 명령어 정리

| 명령어 | 사용하는 이유 |
|---|---|
| `set -e` | 명령어 오류 발생 시 일반적으로 중단 |
| `cp` | 기존 JAR 백업 |
| `install` | 새 JAR 복사 및 소유자·권한 설정 |
| `mv` | 실제 서비스 JAR 교체 |
| `systemctl restart` | Spring Boot 재시작 |
| `curl` | `/health` 정상 확인 |
| `echo` | 배포 결과 출력 |

## 8. systemd와 Health Check

### systemd

Marble은 다음 실행 명령어를 사용한다.

```ini
ExecStart=/usr/bin/java -jar /opt/marble/app.jar
```

JAR 파일을 교체한 뒤에는 재시작해야 새로운 버전이 실행된다.

```bash
# Marble 서비스 재시작
sudo systemctl restart marble

# 서비스 상태 확인
sudo systemctl status marble
```

### Health Check

```bash
# HTTP 상태 확인
curl -f http://127.0.0.1:8080/health
```

정상 응답:

```json
{"status":"UP"}
```

Spring Boot는 재시작 후 기동 시간이 필요하기 때문에 `curl`의 재시도 기능을 사용했다.

```bash
curl -f --retry 5 --retry-delay 3 \
  --retry-connrefused --max-time 5 \
  http://127.0.0.1:8080/health
```

| 옵션 | 역할 |
|---|---|
| `-f` | HTTP 400/500 계열 응답을 오류로 처리 |
| `--retry 5` | 최대 5회 재시도 |
| `--retry-delay 3` | 3초 간격으로 재시도 |
| `--retry-connrefused` | 연결 거부도 재시도 |
| `--max-time 5` | 요청당 시간 제한 |

## 9. WAS01 → WAS02 순차 배포

Jenkinsfile에서는 WAS IP를 변수로 관리한다.

```groovy
environment {
    WAS01 = '10.0.21.126'
    WAS02 = '10.0.22.9'
}
```

배포 순서:

```text
Deploy WAS01
      ↓
SCP 파일 전송
      ↓
SSH 배포 스크립트 실행
      ↓
Health Check 성공
      ↓
Deploy WAS02
      ↓
동일한 과정 수행
      ↓
Pipeline SUCCESS
```

**WAS01 배포에 실패하면 WAS02 Stage는 실행하지 않는다.**

### 순차 배포 이유

두 WAS를 동시에 재시작하는 일을 피하고, 첫 번째 WAS의 기본 검증이 성공했을 때 다음 서버로 배포하기 위해서다.

다만 현재 방식은 트래픽 드레이닝을 구현하지 않았으므로 완전한 무중단 배포를 보장하지 않는다.

## 10. 실제 발생한 장애와 해결 과정

### 장애 ① Credentials ID 오류

```text
Could not find credentials entry
with ID 'marble-lab-ssh'
```

**원인**

Jenkinsfile에 작성한 ID와 실제 Jenkins Credentials ID가 일치하지 않았다.

**해결**

```groovy
credentialsId: 'marble-was-ssh'
```

실제로 등록한 Credential ID로 수정했다.

### 장애 ② SSH 개인 키 오류

```text
Load key "****": error in libcrypto
Permission denied (publickey).
```

**확인 내용**

SSH 클라이언트가 개인 키를 정상적으로 읽지 못했다.

개인 키의 형식, 내용, 줄바꿈, 등록 방식 등을 점검해야 하는 오류였다.

이후 키 읽기 오류는 사라졌으나, 당시 어떤 설정이 직접적인 원인이었는지는 확정된 로그가 없다.

### 장애 ③ SSH Username 오류

```text
marble-was-ssh@10.0.21.126:
Permission denied (publickey).
```

**원인**

Credential ID를 실제 Linux Username으로 잘못 설정했다.

**해결**

```text
Credential ID : marble-was-ssh
Username      : marble-deploy
```

그 결과 SSH 접속 대상이 올바르게 변경되었다.

```text
marble-deploy@10.0.21.126
marble-deploy@10.0.22.9
```

### 장애 ④ Spring Boot 재시작 후 연결 거부

```text
curl: (7) Failed to connect to 127.0.0.1 port 8080
Warning: Will retry in 3 seconds.
```

**원인 후보**

Spring Boot가 재시작 직후 아직 8080 포트를 열지 않았던 것으로 판단된다.

**결과**

재시도 후 정상 응답을 확인했다.

```text
{"status":"UP"}
DEPLOY SUCCESS
```

이는 Health Check 재시도가 효과적으로 동작한 사례다.

## 11. 배포 후 검증 명령어

**실행 위치: WAS01과 WAS02 각각**

```bash
# Spring Boot 서비스 실행 여부
sudo systemctl is-active marble

# 8080 포트 LISTEN 확인
sudo ss -lntp | grep ':8080'

# Health Check
curl -fsS http://127.0.0.1:8080/health

# 실제 배포된 JAR 확인
ls -lh /opt/marble/app.jar

# JAR 파일 체크섬 확인
sha256sum /opt/marble/app.jar

# 이전 JAR 백업 확인
sudo ls -lh /var/backups/marble/

# 서비스 최근 로그
sudo journalctl -u marble -n 50 --no-pager
```

두 WAS의 JAR 체크섬이 동일하면 동일한 JAR가 적용됐는지 검증하는 데 도움이 된다.

## 13. 현재 구현 범위와 한계

| 항목 | 상태 |
|---|---|
| Jenkins CI 결과물 자동 배포 | 구현 |
| SSH/SCP 파일 전송 | 구현 |
| WAS01/02 순차 배포 | 구현 |
| 기존 JAR 백업 | 배포 스크립트에 포함 |
| systemd 재시작 | 구현 |
| Health Check | 구현 |
| 자동 Rollback | 미구현 |
| Blue/Green | 미구현 |
| 완전한 무중단 배포 | 보장하지 않음 |

**주의:** WAS01 성공 후 WAS02가 실패하면 서버 사이에 서로 다른 애플리케이션 버전이 존재할 수 있다. 자동 Rollback은 구현하지 않았기 때문에 필요하면 관리자가 백업 파일로 수동 복구해야 한다.

## 14. 2교시 최종 핵심 요약

| 핵심 개념 | 한 줄 설명 |
|---|---|
| SSH 개인 키 | Jenkins가 인증에 사용 |
| SSH 공개 키 | WAS가 인증 검증에 사용 |
| Credentials | Jenkins의 인증 정보 관리 |
| SCP | JAR 파일 전송 |
| SSH | WAS 배포 스크립트 실행 |
| `cp` | 기존 JAR 백업 |
| `install` | 새로운 JAR 준비 |
| `mv` | JAR 교체 |
| `systemctl` | Spring Boot 재시작 |
| `curl` | 배포 후 정상 응답 확인 |
| 순차 배포 | WAS01 성공 후 WAS02 진행 |

### 반드시 기억할 흐름

```text
CI 성공
   ↓
SCP : JAR 전송
   ↓
SSH : 배포 명령 실행
   ↓
cp : 기존 JAR 백업
   ↓
install : 신규 JAR 준비
   ↓
mv : 신규 JAR 교체
   ↓
systemctl : 서비스 재시작
   ↓
curl : Health Check
   ↓
WAS02 동일 작업
   ↓
CD 성공
```

### 최종 한 줄 정리

**Marble 프로젝트의 CD는 Jenkins에서 생성한 Spring Boot JAR를 SSH/SCP로 WAS01/02에 순차 전송하고, Bash 스크립트로 기존 JAR 백업·신규 JAR 교체·systemd 재시작·Health Check를 자동으로 수행하는 배포 구조다.**
