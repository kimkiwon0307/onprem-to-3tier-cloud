
# A과정 01단계 — 3-Tier 아키텍처 및 네트워크 설계 복습

> **학습 목적:** 기존 VMware 기반 3-Tier 구성과 AWS 확장 구조를 이해하고, 운영 명령어와 장애 대응·기술 면접 답변을 자신의 말로 설명한다.
>
> **범위:** A과정 1/20단계. 이 문서는 1단계 수업 및 면접 문답을 정리한 복습 노트이다. **실제 구축 완료·실습 검증을 새로 주장하는 문서는 아니다.** 명령어 출력과 Apache 예시는 별도 표시했다.

## 1. 프로젝트 아키텍처

### 1.1 VMware On-Premises 3-Tier

```text
[Client]
    | HTTP :80
    v
[WEB01]  Apache HTTP Server  192.168.111.141
    | HTTP :8080
    v
[WAS01]  Spring Boot / Java  192.168.111.142
    | MySQL TCP :3306
    v
[DB01]   MySQL                192.168.111.143
```

- OS: Ubuntu 24.04 / VMware 가상머신
- 세 서버는 초기 실습에서 `192.168.111.0/24` 대역에 위치했다. **역할을 나눴지만, 서브넷을 계층별로 격리한 것은 아니다.**
- 해당 구성은 계층별 **1대**이므로 고가용성/자동 장애 전환을 제공하지 않는다.

| 계층 | 구성 기술 | 주요 역할 | 주요 포트 |
|---|---|---|---|
| WEB | Apache HTTP Server | HTTP 요청 수신, 리버스 프록시를 통한 WAS 요청 전달 | TCP 80 |
| WAS | Spring Boot / Java (내장 Tomcat 등) | 비즈니스 로직 처리, DB 접속 | TCP 8080 |
| DB | MySQL | 데이터 저장·조회, SQL 처리 | TCP 3306 |
| 관리 | SSH | 원격 서버 관리 | TCP 22 |

### 1.2 AWS로 확장된 프로젝트 구조

```text
[Client] → [ALB] → [WEB01 / WEB02 : Apache]
                              ↓
                    [WAS01 / WAS02 : Spring Boot]
                              ↓
                    [MySQL Primary / Replica]
```

- **ALB의 대상은 WEB01/02**이며, **WAS01/02로의 분산은 Apache가 담당**했다.
- 서버를 두 대 배치했다는 사실만으로 무중단 전환이 검증된 것은 아니다. Apache 백엔드의 장애 감지·재시도 설정과 실제 장애 테스트가 필요하다.
- AWS 네트워크 보안과 상세 구축 절차는 A과정 후속 단계에서 다룬다.

## 2. 핵심 개념

### 2.1 3-Tier로 분리하는 이유

1. **역할 분리:** WEB(HTTP 진입점)·WAS(비즈니스 로직)·DB(데이터)를 분리해 관리한다.
2. **자원 관리:** CPU·메모리·디스크 자원의 계층 간 경합을 줄이고 필요한 계층만 확장할 수 있다.
3. **장애 분석:** 문제를 WEB, WAS, DB 구간으로 나눠 점검할 수 있다.
4. **보안 설계:** 네트워크와 권한을 별도로 설계해 직접 접근을 제한할 수 있다.

**주의:** 3-Tier 자체가 반드시 저렴하거나 장애 분석을 쉽게 만들어 주는 것은 아니다. 서버 간 네트워크 구간·운영 복잡도는 증가하고, 각 계층이 한 대뿐이면 단일 장애 지점(SPOF)이 남는다.

### 2.2 회원가입 요청의 흐름

1. 사용자가 브라우저에서 회원가입 요청을 전송한다.
2. Apache WEB이 요청을 수신해 WAS로 전달한다(리버스 프록시 설정 시).
3. WAS에서 입력 검증 및 회원가입 로직을 수행한다.
4. WAS가 MySQL에 SQL을 실행한다.
5. DB 결과를 받아 WAS → WEB → 클라이언트 순서로 응답한다.

### 2.3 IP와 포트

- **IP 주소:** 통신할 대상 서버·인터페이스를 식별한다.
- **포트:** 대상 서버에서 어떤 서비스와 통신할지를 식별한다.
- 예: `192.168.111.142:8080` = WAS IP와 애플리케이션 포트.
- **같은 `/24` 대역:** 일반적인 이더넷 구성에서는 같은 서브넷 통신이 기본 게이트웨이를 거치지 않고 직접 이루어진다.

### 2.4 Reverse Proxy, 로드밸런싱, 장애 전환

| 개념 | 의미 |
|---|---|
| Reverse Proxy | 클라이언트 요청을 대신 받아 내부 백엔드 서버로 전달 |
| Load Balancing | 여러 서버에 요청을 분산 |
| Health Check / 장애 감지 | 대상 서버의 정상 여부 판단 |
| Failover | 장애 대상 대신 정상 대상을 통해 서비스를 이어가도록 전환 |

**AWS ALB 헬스체크와 Apache 백엔드 장애 감지는 별개**이다. 프로젝트의 ALB는 WEB 대상 그룹을 확인하므로, ALB의 WEB 상태가 `healthy`라고 WAS 상태까지 보장되지는 않는다.

## 3. 명령어 복습 (점검용)

> 아래 명령어는 수업에서 배운 **점검 방법**이다. 예시 IP는 초기 VMware 환경 기준이며, AWS 환경에서는 해당 서버의 사설 IP와 서비스 이름을 사용한다. 실제 출력은 환경에 따라 다르다.

### 3.1 IP 주소와 라우팅 테이블

```bash
ip -br addr
ip route
```

- `ip -br addr`: 인터페이스와 IP 주소를 간략하게 확인 (`-br`: brief).
- `ip route`: 목적지별 라우팅 경로와 기본 게이트웨이를 확인.
- `default via ...`: 구체적인 경로가 없을 때 사용할 기본 게이트웨이.

### 3.2 서비스가 포트를 열고 있는지 확인

```bash
sudo ss -lntp
```

- `-l`: LISTEN 중인 소켓 / `-n`: IP·포트를 숫자로 출력 / `-t`: TCP / `-p`: 관련 프로세스.
- **LISTEN** 상태는 프로세스의 수신 대기 여부를 의미한다. 서비스의 전체 기능 정상 여부와는 다르다.

### 3.3 WEB에서 WAS로 TCP 연결 가능 여부 확인

```bash
nc -vz 192.168.111.142 8080
```

- `nc`: 네트워크 연결 점검 / `-v`: 상세 출력 / `-z`: 연결 가능 여부 검사.
- 성공해도 **애플리케이션 기능 또는 DB 연동까지 정상이라는 뜻은 아니다.**

### 3.4 HTTP 애플리케이션 응답 확인

```bash
curl -i http://192.168.111.142:8080/health
```

- `curl`: HTTP 등의 요청 전송 / `-i`: 응답 헤더 표시.
- `HTTP 200`은 해당 요청에 대한 정상 응답이다. 실제 사용자 기능까지 모두 보장하지는 않는다.

### 3.5 WEB Apache 서비스 및 오류 로그 확인

```bash
sudo systemctl status apache2
sudo tail -n 100 /var/log/apache2/error.log
```

- `systemctl status`: systemd 서비스 상태를 조회.
- `tail -n 100`: 파일의 마지막 100줄을 읽어 최근 오류 단서를 찾는다.

### 3.6 WAS 애플리케이션 상태·로그 확인

```bash
sudo systemctl status marble.service
sudo journalctl -u marble.service -n 100 --no-pager
```

- 프로젝트 WAS 서비스명은 **`marble.service`** (`marlbe` 아님).
- `journalctl -u`: 지정한 서비스 유닛의 로그 확인.
- `-n 100`: 최근 100줄 / `--no-pager`: 페이지 구분 프로그램 없이 바로 출력.

### 3.7 CPU 과부하 점검

```bash
top
ps -eo pid,user,%cpu,%mem,cmd --sort=-%cpu | head
```

- `top`: 실시간 CPU·메모리와 프로세스 사용량 확인.
- `ps -eo`: 지정한 열을 모든 프로세스에 대해 출력.
- `--sort=-%cpu`: CPU 사용률 내림차순.
- `| head`: 상위 일부 결과만 출력.
- **CPU 100%만으로 즉시 재시작하지 않는다.** 서비스 지연, 오류율, 로그, 원인과 변경 영향을 함께 판단한다.

추가 심화 명령어(수업 중 언급):

```bash
top -H -p <JAVA_PID>
```

- 해당 Java 프로세스 내부의 스레드별 CPU 사용량을 확인할 때 활용한다.

## 4. Apache 리버스 프록시·로드밸런싱 설정 개념

### 4.1 WAS 한 대로 요청 전달하는 예시

```apache
ProxyPass "/" "http://192.168.111.142:8080/"
ProxyPassReverse "/" "http://192.168.111.142:8080/"
```

- `ProxyPass`: 수신한 요청을 WAS로 전달한다.
- `ProxyPassReverse`: 백엔드가 반환한 일부 리다이렉션 응답 헤더를 프록시 주소에 맞게 조정한다.

### 4.2 WAS 두 대를 분산하는 예시

```apache
<Proxy "balancer://marble-was">
    BalancerMember "http://10.0.21.126:8080" retry=10
    BalancerMember "http://10.0.22.9:8080" retry=10
    ProxySet lbmethod=byrequests
</Proxy>

ProxyPass "/" "balancer://marble-was/"
ProxyPassReverse "/" "balancer://marble-was/"
```

- `BalancerMember`: WAS01/02를 백엔드 대상으로 등록.
- `lbmethod=byrequests`: 요청 수 기준 분산.
- `retry=10`: 오류로 제외된 백엔드에 대한 재시도 대기 시간(초).
- Apache는 백엔드 연결 오류를 통해 수동적으로 장애를 감지할 수 있으며, 주기적인 별도 능동 체크는 `mod_proxy_hcheck`와 관련 설정이 필요하다.
- 실제 자동 장애 전환 수준은 설정·실패 유형·검증 결과에 따라 다르다.

> **중요:** 위 Apache 설정은 **학습용 예시**이며, 당시 프로젝트 서버의 설정 파일 원본을 그대로 기록한 것이 아니다. 후속 단계에서 실제 서버 설정을 확인하여 비교한다.

## 5. 실무 장애 대응 흐름

### 5.1 WAS CPU 100% 발생

1. CPU 사용률이 일시적인지 지속적인지 확인 (`top`, `ps`).
2. WAS의 응답 시간, 오류율, `/health`, 애플리케이션 로그를 확인.
3. 서비스가 정상이고 긴급하지 않으면 원인 분석 후 보고·작업 계획 수립.
4. 지연·504 오류 등이 실제로 발생하면 긴급도를 높여 조치 검토.
5. WAS02의 상태·처리 용량·세션 영향을 확인하고 가능하다면 WAS01로의 신규 요청을 안전하게 우회.
6. 장애 증거를 수집한 뒤 WAS01 분석·복구. 복구 후 기능·자원·로그 확인 및 트래픽 재편입.

**주의:** WAS가 두 대여도 Apache가 자동으로 장애를 감지·우회한다고 무조건 가정하지 않는다. WAS01을 갑자기 중지하면 일부 요청이 실패할 수 있다.

### 5.2 HTTP 502 Bad Gateway 발생

**핵심:** 502가 표시되더라도 무조건 WAS 장애라고 결론 내리지 말고 **오류를 반환한 지점**을 찾는다.

1. **ALB:** Target Group의 WEB01/02 상태와 오류 발생 지점 확인.
2. **WEB(Apache):** `systemctl status apache2`, Apache `error.log` 확인.
3. **WEB → WAS:** `nc -vz <WAS_IP> 8080`, `curl -i http://<WAS_IP>:8080/health` 점검.
4. **WAS:** `systemctl status marble.service`, `journalctl -u marble.service ...` 점검.
5. **DB:** WAS 로그에 DB 연결 문제가 드러나면 MySQL·3306·DB 인증 상태 확인.
6. **검증:** 조치 후 ALB 경유 웹 접속과 실제 사용자 기능을 확인.

**502와 504의 차이(개념):** 502는 게이트웨이/프록시가 정상적이지 않은 업스트림 응답을 받는 등의 상황에서, 504는 업스트림 응답 대기 시간이 초과된 상황에서 발생할 수 있다. 실제 원인은 로그와 구성에 따라 확인한다.

## 6. 1단계 면접 질문 및 답변 (실제 수업 문답 정리)

### Q1. 왜 WEB, WAS, DB를 한 서버가 아닌 3-Tier로 분리했나요?

**답변**

WEB, WAS, DB를 분리하면 역할과 자원을 독립적으로 관리할 수 있고, 특정 계층에 부하가 발생했을 때 다른 계층의 자원과 분리해 대응할 수 있습니다. 장애가 발생해도 WEB·WAS·DB 중 어느 구간에 문제가 있는지 범위를 좁혀 점검할 수 있으며, 필요하면 특정 계층만 확장하기가 쉽습니다. 다만 서버 간 통신과 관리가 복잡해지고, 단일 서버로 구성된 계층은 여전히 장애 지점이 됩니다.

### Q2. WAS CPU 사용률이 100%이면 WEB과 DB에는 영향이 없나요? 어떻게 대응하나요?

**답변**

서버 자원은 분리되어 있지만 요청 흐름으로 연결되어 있어 간접적 영향이 있을 수 있습니다. WAS가 요청을 제때 처리하지 못하면 WEB에서 응답 지연이나 오류가 발생할 수 있고, DB 연결이 오래 유지되거나 요청 특성이 달라지면 DB에도 영향이 생길 수 있습니다. `top`, `ps`로 CPU 점유 프로세스를 확인하고 로그, 응답 시간, 오류 여부를 살펴보겠습니다.

### Q3. Java 프로세스가 CPU 100%인데 서비스는 정상입니다. 즉시 종료하거나 재시작하나요?

**답변**

CPU 사용률만으로 바로 종료하지 않겠습니다. 먼저 사용량이 지속되는지, 실제 사용자 지연·오류가 있는지, Java 프로세스와 로그를 확인하겠습니다. 긴급한 서비스 영향이 없다면 원인을 보고하고 영향이 적은 시간대에 변경을 진행하겠습니다. 장애가 임박하거나 서비스가 악화된다면 승인된 긴급 대응 절차에 따라 조치하겠습니다.

### Q4. WAS01 CPU 100%와 504 오류가 발생하고 WAS02는 정상입니다. 우선 무엇을 하나요?

**답변**

WAS02가 추가 트래픽을 감당할 수 있는지 먼저 확인하겠습니다. 이후 Apache의 WAS 백엔드 분산 설정과 장애 처리 상태를 확인하여 WAS01로의 신규 요청을 우회하는 방안을 검토하겠습니다. 장애 증거를 확보하고 WAS01 원인을 분석해 복구한 뒤, 정상 동작을 확인하고 분산 대상에 다시 포함하겠습니다.

### Q5. WAS01 장애 시 ALB Target Group에서 WAS01을 제외하면 되나요?

**답변**

아닙니다. 제 프로젝트의 ALB Target Group은 WEB01/02를 대상으로 트래픽을 분산합니다. WAS01/02의 분산은 WEB 서버의 Apache가 담당하므로 WAS01 장애 대응은 Apache의 백엔드 설정과 상태를 확인해야 합니다.

### Q6. WAS01이 종료된 것을 Apache는 어떻게 알고, 어떻게 WAS02로 요청을 보내나요?

**답변**

Apache는 WAS01로 요청을 보내다가 연결 오류가 발생하면 백엔드를 오류 상태로 판단할 수 있습니다. WAS02가 로드밸런싱 그룹에 등록되어 있고 장애 처리 설정이 적절하면 정상 대상으로 요청을 전달할 수 있습니다. 다만 주기적 헬스체크는 기본 연결 실패 감지와 별개이며 `mod_proxy_hcheck` 같은 추가 설정이 필요합니다. 실제 Failover는 테스트로 확인해야 합니다.

### Q7. Apache가 WAS01 연결에 실패했을 때 WAS02로 분산하려면 미리 무엇을 설정해야 하나요?

**답변**

Apache의 로드밸런싱 그룹에 WAS01과 WAS02를 모두 `BalancerMember`로 등록해야 합니다. 그리고 장애 감지 및 재시도 설정도 점검해야 WAS01 문제가 발생했을 때 WAS02로 요청을 전달할 수 있습니다.

### Q8. ALB → WEB → WAS → DB 환경에서 HTTP 502가 발생하면 어떻게 점검하나요?

**답변**

먼저 ALB와 WEB 중 어느 구간에서 502가 발생했는지 확인하고 ALB Target Group 상태와 Apache 오류 로그를 점검하겠습니다. WEB에서 WAS로 TCP 8080 연결이 가능한지 `nc`로 확인하고, `curl`로 WAS `/health` 응답을 검증하겠습니다. WAS 문제라면 `systemctl status marble.service`와 `journalctl`로 서비스와 로그를 확인합니다. DB 연결 문제가 의심될 때는 WAS 로그를 근거로 DB를 추가 점검하고, 조치 후에는 실제 사용자 기능까지 검증하겠습니다.

## 8. 이번 단계 핵심 암기 요약

- **3-Tier:** WEB(요청 진입) → WAS(로직) → DB(데이터).
- **장점:** 역할·자원 분리, 구간별 장애 분석, 독립적 확장 가능.
- **단점:** 서버 간 네트워크 및 운영 복잡도 증가; 계층별 단일 서버는 SPOF.
- **ALB와 Apache 구분:** ALB → WEB01/02, Apache → WAS01/02.
- **TCP 연결과 서비스 정상은 다름:** `nc` 성공 ≠ `/health` 성공 ≠ 회원가입 기능 정상.
- **장애 대응:** 증상 파악 → 로그/자원/네트워크 확인 → 원인 좁히기 → 영향 최소화 → 복구 → 재검증.
- **면접 원칙:** '구성했다'와 '장애 전환까지 검증했다'를 구분해 설명.
